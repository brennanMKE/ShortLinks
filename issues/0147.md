## Description

Batch create does not deduplicate (sending the same batch twice creates two sets of links, [docs/using-api-tokens.md](../docs/using-api-tokens.md)), and campaign create has no retry guard. Agents retry after timeouts. Support an `Idempotency-Key` request header on `POST /api/links`, `POST /api/campaigns` and `POST /api/campaigns/{slug}/links/batch`, and an `idempotency_key` argument on the matching MCP tools.

## Long Description

- New table `idempotency_keys (user_id, key, method, path, request_sha256, status, response_body, created_at)`, primary key `(user_id, key)`, with a new migration and down migration.
- First request with a key: process it, store the status and body. Repeat with the same key and the same body hash: replay the stored response with an `Idempotent-Replayed: true` header. Same key with a different body: 422 `idempotency_key_reused`. A key still in flight: 409 `idempotency_key_in_progress`.
- Keys are 1–255 printable ASCII characters. Records expire after 24 hours; prune them in the existing retention job.
- Without the header, behaviour is unchanged.

## Acceptance criteria

- Middleware or helper tests cover first use, replay (no second link created, verified by counting rows), body mismatch, concurrent in-flight requests, expiry, per-user isolation and the migration round trip.
- [docs/using-api-tokens.md](../docs/using-api-tokens.md) explains the header and updates the batch warning.
- `go test ./...` passes against a clean migration replay.

## Root cause

None of the create endpoints could tell a retry from a new request. An agent that timed out and retried would create a second link, campaign or batch.

## Fix

Added the `internal/idempotency` package, a store plus middleware. It wraps the three create routes as `requireAPI(idem(handler))`, so auth, rate limiting and read-only refusals happen before a key is claimed.

**Claiming a key.**
- The hash covers method, path and the raw body, capped at 1 MiB to match `decodeJSON`. Over that cap the request gets 413 `request_too_large`.
- `INSERT … ON CONFLICT DO NOTHING` claims the key with a fresh `claim_id`.

**When the key already exists.**
- A different hash gets 422 `idempotency_key_reused`.
- A completed row is replayed with its stored status, `Content-Type` and `Location`, plus `Idempotent-Replayed: true`.
- A pending row gets 409 `idempotency_key_in_progress`, with `Retry-After: 1`.

**Completing a request.**
- Only 2xx and 4xx responses are stored.
- A 5xx or a panic releases the key, and the panic is re-raised.
- `Complete` and `Release` act only when the `claim_id` still matches. A stale owner that finishes after another request has reclaimed its key therefore writes and deletes nothing, and logs a warning.

**Timing.**
- Handlers run under a 90 s context deadline.
- A pending row older than 120 s with the same hash can be reclaimed by one caller, using an atomic UPDATE.
- If `Complete` fails, it is retried once. If it fails again, the row is left pending rather than released, so a retry can't run the handler again within that window.

**Expiry.** Keys expire after 24 hours. `Claim` deletes an expired row it finds, and the retention `Sweeper` gains a `WithPrune` hook that prunes expired rows hourly.

**Scope.** Keys are per user, shared across all of a user's tokens and their browser session. In dev mode the wrapper isn't mounted and the header is ignored.

**Migration.** `000018_create_idempotency_keys` (up and down). It cascades from `users` and adds a `created_at` index for pruning.

## Gotchas

- **Deploy:** migration `000018` must run on each instance (sstools, ocsf, dustalmanac) before this ships.
- **Local databases:** anyone with a local DB already at version 18 from the pre-fix commit must drop and recreate `idempotency_keys`, because `claim_id` was added in place.
- **The handler can still run twice in two rare cases:**
  - it ignores its deadline and runs past 120 s;
  - both `Complete` attempts fail and the client retries after 120 s.

  Neither can corrupt the stored record.
- **Test prerequisite:** the migration test assumes the test DB already has 000018 applied.
