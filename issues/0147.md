# 0147 — A retried create can make duplicate links or campaigns, which is risky for agents that retry on timeouts

| | |
|---|---|
| **Status** | open |
| **Module** | handlers / db / middleware |
| **Platform** | All |
| **Phase** | 16 — Agent API and MCP |
| **First seen** | 2026-11-18 |

## Description

Batch create does not deduplicate (sending the same batch twice creates two sets of links, [docs/using-api-tokens.md](../docs/using-api-tokens.md)), and campaign create has no retry guard. Agents retry after timeouts. Support an `Idempotency-Key` request header on `POST /api/links`, `POST /api/campaigns` and `POST /api/campaigns/{slug}/links/batch`, and an `idempotency_key` argument on the matching MCP tools.

## Long Description

- New table `idempotency_keys (user_id, key, method, path, request_sha256, status, response_body, created_at)`, primary key `(user_id, key)`, with a new migration and down migration.
- First request with a key: process it, store the status and body. Repeat with the same key and the same body hash: replay the stored response with an `Idempotent-Replayed: true` header. Same key with a different body: 422 `idempotency_key_reused`. A key still in flight: 409 `idempotency_key_in_progress`.
- Keys are 1–255 printable ASCII characters. Records expire after 24 hours; prune them in the existing retention job.
- Without the header, behaviour is unchanged.

## Acceptance criteria

- Middleware or helper tests cover first use, replay (no second link created, verified by counting rows), body mismatch, concurrent in-flight requests, expiry, per-user isolation and the migration round trip.
- [docs/using-api-tokens.md](../docs/using-api-tokens.md) explains the header and updates the batch warning.
- `go test ./...` passes against a clean migration replay.
