# 0093 — Login assertion failures discard protocol.Error DevInfo, hiding the actual cause

| | |
|---|---|
| **Status** | open |
| **Module** | auth |
| **Platform** | All |
| **First seen** | 2026-07-30 |

## Description

`FinishLogin` logs assertion failures with `s.log.Warn("login: validating assertion", "err", err)` (`internal/auth/login.go:193`). go-webauthn returns a `*protocol.Error` whose `Error()` method returns **only** the `Details` field (`protocol/errors.go:18-20`) — the `DevInfo` field, which carries the specific failing check, is silently dropped. The result is that many distinct failures all log the same useless string:

```
WARN login: validating assertion err="Error validating the authenticator response"
```

Three different checks in `AuthenticatorData.Verify` produce that exact text — RP ID hash mismatch (`protocol/authenticator.go:405`), User Present not set (`:411`), and User Verified not set (`:418`) — and their `DevInfo` values are what distinguish them (`"User verification required but flag not set by authenticator"`, etc.). Diagnosing [#0092](0092.md) required eliminating two of the three by reading library source and reasoning about check ordering, when the answer was already in a field the server had in hand and threw away.

This is a diagnosability defect, not a security one: `DevInfo` is developer-facing text from the library, is never returned to the client (the handler still returns a generic 401), and goes only to the server journal.

## Steps to reproduce

1. Cause any assertion validation failure (e.g. reproduce [#0092](0092.md), or tamper with a stored public key).
2. `sudo journalctl -u shortlinks --since "10 min ago" | grep -i "login:"`.
3. Observe the `err=` value is the generic category string with no indication of which check failed.

## Expected behavior

The warning includes the library's `DevInfo` so the exact failing check is named in the log.

## Actual behavior

Only the generic `Details` string is logged. Distinct root causes are indistinguishable.

## Scope / deliverables

- In `FinishLogin`, `errors.As` the validation error into `*protocol.Error` and include `DevInfo` as a separate structured log attribute when present (empty/absent `DevInfo` must not add a noisy empty field).
- Apply the same treatment to the other `protocol.Error`-producing warn sites in the auth ceremonies where the same information is being dropped — `login: parsing assertion` (`login.go:142`) and the equivalent registration/recovery validation warnings — so the improvement is consistent rather than one-off.
- A test asserting that a validation failure carrying `DevInfo` surfaces it in the log record (capture via a `slog` handler writing to a buffer).

## Acceptance criteria

- [ ] A `*protocol.Error` with non-empty `DevInfo` logs that text alongside `err`.
- [ ] A non-`protocol.Error` failure, or one with empty `DevInfo`, logs exactly as before with no empty attribute.
- [ ] The HTTP response is unchanged — still a generic 401 with `{"error":"authentication failed"}`; `DevInfo` never reaches the client.
- [ ] `go build ./...`, `go vet ./...`, `gofmt -l internal/auth/` clean.
- [ ] `go test ./...` passes, including the new test, and the new test name is observed in the run output.

## Out of scope

- Changing what the client is told. The generic 401 is deliberate (it prevents account/credential probing) and stays exactly as is.
- Restructuring logging elsewhere in the codebase.

## Notes

- Keep the attribute developer-facing and clearly separate from `err`, e.g. `s.log.Warn("login: validating assertion", "err", err, "info", perr.DevInfo)`, so existing log greps on `err=` keep working.
- `protocol.Error` also carries `Type` (e.g. `verification_error`) and a wrapped `Err`. `DevInfo` is the field that actually disambiguates; `Type` is the same for all three checks in question and is not worth logging.
