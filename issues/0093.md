# 0093 — Login assertion failures discard protocol.Error DevInfo, hiding the actual cause

## Description

`FinishLogin` logs assertion failures with `s.log.Warn("login: validating assertion", "err", err)` (`internal/auth/login.go:193`). go-webauthn returns a `*protocol.Error` whose `Error()` method returns **only** the `Details` field (`protocol/errors.go:18-20`) — the `DevInfo` field, which carries the specific failing check, is silently dropped. The result is that many distinct failures all log the same useless string:

```
WARN login: validating assertion err="Error validating the authenticator response"
```

Three different checks in `AuthenticatorData.Verify` produce that exact text — RP ID hash mismatch (`protocol/authenticator.go:405`), User Present not set (`:411`), and User Verified not set (`:418`) — and their `DevInfo` values are what distinguish them (`"User verification required but flag not set by authenticator"`, etc.). Diagnosing [#0092](0092.md) required eliminating two of the three by reading library source and reasoning about check ordering, when the answer was already in a field the server had in hand and threw away.

This is a diagnosability defect, not a security one: `DevInfo` is developer-facing text from the library, is never returned to the client (the handler still returns a generic 401), and goes only to the server journal.

## Steps to reproduce

1. Cause any assertion validation failure (e.g. reproduce [#0092](0092.md), or tamper with a stored public key).
2. `sudo journalctl -u shortlinks --since "10 min ago" | grep -i "login:"`.
3. Observe the `err=` value is the generic category string with no indication of which check failed.

## Expected behavior

The warning includes the library's `DevInfo` so the exact failing check is named in the log.

## Actual behavior

Only the generic `Details` string is logged. Distinct root causes are indistinguishable.

## Scope / deliverables

- In `FinishLogin`, `errors.As` the validation error into `*protocol.Error` and include `DevInfo` as a separate structured log attribute when present (empty/absent `DevInfo` must not add a noisy empty field).
- Apply the same treatment to the other `protocol.Error`-producing warn sites in the auth ceremonies where the same information is being dropped — `login: parsing assertion` (`login.go:142`) and the equivalent registration/recovery validation warnings — so the improvement is consistent rather than one-off.
- A test asserting that a validation failure carrying `DevInfo` surfaces it in the log record (capture via a `slog` handler writing to a buffer).

## Acceptance criteria

- [ ] A `*protocol.Error` with non-empty `DevInfo` logs that text alongside `err`.
- [ ] A non-`protocol.Error` failure, or one with empty `DevInfo`, logs exactly as before with no empty attribute.
- [ ] The HTTP response is unchanged — still a generic 401 with `{"error":"authentication failed"}`; `DevInfo` never reaches the client.
- [ ] `go build ./...`, `go vet ./...`, `gofmt -l internal/auth/` clean.
- [ ] `go test ./...` passes, including the new test, and the new test name is observed in the run output.

## Out of scope

- Changing what the client is told. The generic 401 is deliberate (it prevents account/credential probing) and stays exactly as is.
- Restructuring logging elsewhere in the codebase.

## Root cause

`(*protocol.Error).Error()` returns `e.Details` and nothing else (`protocol/errors.go:18-20`). `Details` is a shared category constant — `ErrVerification` is declared once with `Details: "Error validating the authenticator response"` and the three `AuthenticatorData.Verify` checks each return it via `.WithInfo(...)`, which populates `DevInfo` and leaves `Details` untouched. Passing the error to slog as `"err", err` therefore prints the category and discards the discriminator.

## Fix

Added `ceremonyWarnArgs(err error) []any` in `login.go`. It always yields `"err", err`, then `errors.As`-es into `*protocol.Error` and appends `"info", perr.DevInfo` when that field is non-empty. Applied at the two warn sites that can receive a `*protocol.Error` — `login: parsing assertion` (`login.go:142`) and `login: validating assertion` (`login.go:193`).

The other three warn sites in `FinishLogin` were deliberately left alone: `login: resolving credential` and `login: consuming challenge` receive store errors, and `login: decoding client challenge` receives a base64 error. None can carry `DevInfo`, so routing them through the helper would add indirection for no gain.

The issue's scope anticipated equivalent sites in `registration.go` and `recovery.go`; `grep` for `log.Warn`/`log.Error` across `internal/auth` confirms **`login.go` is the only file with ceremony warn sites**, so there was nothing else to convert.

## Verification

- **Regression proven both ways.** Reverting only the `login: validating assertion` call site to `"err", err` (leaving the helper compiled so the unit test still builds) makes `TestLogin_ValidationFailureLogsDevInfo` fail with the exact real-world symptom: `err="Error validating origin"` and no `info=` attribute. Restoring the call site makes it pass.
- `TEST_DATABASE_URL=… go test ./internal/auth/ -run 'TestCeremonyWarnArgs|TestLogin_ValidationFailureLogsDevInfo' -v` — both pass, observed by name, including all four `TestCeremonyWarnArgs` subtests (DevInfo present, DevInfo empty, wrapped error, plain error).
- `TEST_DATABASE_URL=… go test ./...` — all packages pass except `internal/config/TestLoad_DefaultsApplied`, confirmed pre-existing on clean `main` (env-sensitive, needs `BASE_URL`); this branch does not touch `internal/config`.
- `go build ./...`, `go vet ./...`, `gofmt -l internal/auth/` all clean.
- The HTTP response is unchanged — `FinishLogin` still returns `ErrLoginFailed`, asserted inside `TestLogin_ValidationFailureLogsDevInfo`.

## Files changed

- `internal/auth/login.go` — new `ceremonyWarnArgs` helper; applied at the `login: parsing assertion` and `login: validating assertion` warn sites.
- `internal/auth/login_test.go` — new `TestCeremonyWarnArgs` (table test over the four error shapes) and `TestLogin_ValidationFailureLogsDevInfo` (end-to-end, captures real slog output through a buffer handler).

## Gotchas

- **Inducing a `DevInfo`-carrying failure in a test is the awkward part.** The natural trigger (a UV=false assertion) belongs to [#0092](0092.md) and its test helper lives on that branch, so this test instead re-points the virtual authenticator's relying party at `https://attacker.example` after registration. Origin verification runs early in `CollectedClientData.Verify` and attaches expected/received origins to `DevInfo`, giving a real, self-contained failure with no cross-branch dependency.
- **Reverting `login.go` wholesale does not demonstrate the regression** — it breaks the build, because `TestCeremonyWarnArgs` references the helper. Only the call site can be reverted to show the before/after.
- `errors.As` unwraps, so a `*protocol.Error` wrapped in `fmt.Errorf("%w")` still surfaces its `DevInfo`. Covered by a subtest so a future refactor that wraps these errors does not silently lose the attribute.

## Notes

- Keep the attribute developer-facing and clearly separate from `err`, e.g. `s.log.Warn("login: validating assertion", "err", err, "info", perr.DevInfo)`, so existing log greps on `err=` keep working.
- `protocol.Error` also carries `Type` (e.g. `verification_error`) and a wrapped `Err`. `DevInfo` is the field that actually disambiguates; `Type` is the same for all three checks in question and is not worth logging.
