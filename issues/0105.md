## Description

**This is the feature that makes the whole campaigns system worth using.** A campaign is normally a set of links created at once — one destination promoted across several channels. Creating eight links one at a time through the existing form, and remembering to type `utm_campaign=summer-fair` identically eight times, is exactly the failure mode `docs/utm.md` warns about under "Canonical casing".

Batch mode on the campaign detail page: one destination URL, then a row per channel. Each row supplies source, medium, content, and an optional placement. Generate one short link per row, all assigned to the campaign, with the campaign's UTM defaults prefilled into each row.

## Scope / deliverables

- Batch create UI on the campaign detail view: one destination field, a repeatable row (source, medium, content, placement, optional per-row title), add/remove row controls.
- **Prefill each row from the campaign's `default_utm_*` values** ([#0098](0098.md)). Prefilled values remain **editable** — the campaign supplies a starting point, never a lock. That is the decided behavior; do not implement a locked field.
- A batch endpoint, or a documented decision to loop the existing single-create endpoint client-side. **Prefer one server call**: a partial failure halfway through a client-side loop leaves the campaign in a state the user did not ask for and cannot easily undo.
- **The batch path must bypass link deduplication, or vary something that is actually baked into the URL.** This is confirmed, not speculative — see the note below.
- Each created link gets `campaign_id`, the five discrete UTM columns, `placement`, and the composed `destination_url` — consistent with single create ([#0099](0099.md)).
- Suggested convention for print rows, documented rather than enforced: `utm_medium=print`, `utm_source=flyer`, `utm_content` or `placement` set to the location.

## Acceptance criteria

- [ ] Creating N rows yields exactly N links, all assigned to the campaign, each with discrete UTM columns matching what was baked into its `destination_url`.
- [ ] **Partial failure is handled deliberately and stated**: either the batch is atomic (all or nothing) or partial success is reported per row with the successes kept. Pick one, implement it, and test it — silently creating 5 of 8 links with a generic error is the failure mode to avoid.
- [ ] Short keys are unique across the batch — the collision path must hold when N links are generated in one transaction, not just one at a time.
- [ ] A row left blank is skipped rather than creating a link with empty UTM values.
- [ ] Duplicate rows (same source+medium+content) are either rejected or allowed deliberately — decide, state, test.
- [ ] Prefilled campaign defaults can be edited per row, and editing one row does not alter another.
- [ ] The existing single-link create form still works unchanged.
- [ ] `cd web && npm run check` 0 errors; `npm test` and `go test ./...` pass with new tests observed **by name**.
- [ ] **Seen running** via `./scripts/dev.sh`: create a real multi-row batch and confirm the links appear in the campaign's links table with correct per-row values.

## Out of scope

- QR codes for the generated links — [#0106](0106.md).
- Editing an existing batch as a batch. Rows become ordinary links once created and are edited individually.
- Importing rows from CSV.
- Templates or saved channel sets beyond the campaign's own defaults.

## Notes

- `web/src/lib/utm.ts` already holds `composeUtmUrl` with 25 unit tests. Batch composition is N calls to the same pure helper — resist writing a second composition path.
- Row state management is the fiddly part in Svelte 5; keep the row model in a pure module with unit tests rather than inline in the component, per `docs/frontend.md`.
- [#0095](0095.md) improves the guidance text on these same five fields and ships first. The batch rows should carry that guidance too, in whatever compact form fits a repeating row — likely the placeholder half of #0095 rather than the per-field hint text, which would be unreadable repeated eight times.

> **Confirmed by [#0099](0099.md)'s review — the dedup trap is real and is still open.** `placement` is **not** baked into `destination_url`, so two batch rows differing *only* in `placement` compose to a byte-identical URL and hit `CreateOrReactivateLink`'s duplicate path. You get **one** link, not two — which for print placements means two poster locations sharing a single short link, defeating the per-location attribution [#0106](0106.md) exists to enable.
>
> #0099 changed that branch to **forward-merge** the requested `campaign_id`/UTM/`placement` onto the matched row rather than silently discarding them. That was the right call for a genuine duplicate submit, but **it does not fix this** — it converts "row 2's placement is silently ignored" into "row 2's placement silently overwrites row 1's". For a batch that is arguably worse, because the failure is now last-write-wins on a shared row instead of a no-op.
>
> Options, to decide here: bypass dedup entirely for the batch endpoint; extend the dedup key beyond `destination_url` alone (e.g. include `placement`); or bake something per-row into the URL. Whichever you pick, **test the two-rows-differing-only-in-placement case explicitly** — it is the one that looks fine in every other test.

## Root cause

Not a defect — the authoring ergonomics that make the campaigns system worth using, plus the confirmed dedup trap the issue was filed around.

## Fix

`links.Store.CreateLinksBatch` inserts every row unconditionally inside one transaction, never consulting `CreateOrReactivateLink` or looking up by `destination_url`. New `POST /api/campaigns/{slug}/links/batch` (atomic, capped at 50 non-blank rows, runs the [#0024](0024.md) URL filter), a devstore twin, pure row helpers in `campaigns.ts`, and a `BatchCreateLinks.svelte` panel on the campaign detail view.

**Dedup bypassed entirely**, and review strengthened the reasoning beyond what the code first argued: inside a batch, exact-duplicate rows are already rejected at the handler, so an extended dedup key could only ever match **pre-existing** links — and matching one means forward-merging onto it, which can silently move a link out of another campaign and last-write-wins its metadata. For a *create* endpoint, unconditional insert is the only semantics that cannot surprise.

Decisions, all stated and tested: **atomic** (one transaction, whole request validated before any insert); **blank rows skipped** and reported via `skipped_blank_rows`; **duplicate rows rejected** on `source+medium+content+placement` — deliberately including placement, unlike the acceptance criterion's shorthand, because applying that literally would reject the exact case this issue exists to enable.

`npm run check` 193 files / 0 errors; `npm test` **364 passing** (from 333); `go build`, `go vet`, `go test ./... -race` clean apart from the pre-existing `internal/config` failure; placeholder intact; `shortlinks_test` left empty.

## Gotchas

- **A batch is not N single creates, and key generation is where that bites.** The collision-retry must query the **open transaction**, not the pool, or row 2 cannot see row 1's uncommitted insert. Mutating `tx.QueryRow` → `s.pool.QueryRow` fails with `links: key already taken`.
- **Bypassing dedup changes a contract**: "create the same link twice, get one link" no longer holds on this path. Submitting an identical 2-row batch twice yields **4 links**. The UI mitigates the common paths — button disabled while submitting, form reset on success — leaving only a lost-response-then-retry window. Acceptable, but it is a divergence from single-create and is now documented in both doc comments and `docs/utm.md`. [#0106](0106.md) builds QR sheets on these links; a doubled batch means doubled sheets.
- **A new endpoint that runs the URL filter must also write the audit entry.** `BatchCreateLinks` initially did neither, and the doc comment justified only the missing *denied link row* — which is genuinely unattributable — while staying silent on the audit entry, which has no such problem. The result: the same blocked URL was visible in the admin audit view through single-create and **invisible** through batch, making the endpoint a filter-probing route with zero visibility and defeating [#0025](0025.md)'s coverage of #0024.
- **A bolded deliverable can go missing without any test noticing.** Three of the five campaign `default_utm_*` values were read nowhere in the batch path, so the same campaign prefilled `flyer`/`print` in single-create and nothing in batch. The omission was *design-correct* — prefilling identical values into every row makes rows 2..N duplicates of row 1 and breaks blank-row skipping — but that reasoning lived nowhere. **Prefill row 1 only** satisfies both.
- **Prefilling row 1 then enabled submit on an untouched form.** `canSubmit` counted non-blank rows, and row 1 was now non-blank at mount, so the button read "Create 1 link" before anything was typed and produced "Destination URL is required" on click. A fix creating a regression two lines away.
- **The duplicate-row guard flagged blank rows against each other**, so three or more blank rows disabled submit entirely — the exact "add eight rows, fill some in" workflow. Found in the browser, and a unit test had **encoded the bug as expected behaviour**.
- **Error row numbers must survive the blank-row filter.** `[filled, blank, blank, dup]` reported "row 2 duplicates row 1" while the UI labelled them Row 1 and Row 4.
- **A test whose fixture has no leading blank row cannot pin `origIndex`.** With `[good, evil]` the original index equals the filtered index, so the assertion passes under either implementation — the same shape [#0104](0104.md)'s review flagged. One leading blank row makes it fail correctly.
- **The devstore twin was not atomic while its comment said it was.** A `genKey` failure on row 3 left rows 1 and 2 in `s.links`, contradicting the real store. Dev-only, but #0106's UI work runs against `scripts/dev.sh` and [#0098](0098.md)'s Gotchas are precisely about devstore divergence surfacing two issues later.

## Downstream constraints

1. **Two campaign-link endpoints, two contracts**: batch is **atomic, 50 non-blank rows**; assign ([#0099](0099.md)) is **non-atomic, 50 keys, client-chunked**. Both caps now have exported client twins (`MAX_BATCH_CREATE_ROWS_PER_REQUEST`, `MAX_ASSIGN_KEYS_PER_REQUEST`).
2. **`link.denied` entries now arrive with `target_id = NULL`** from the batch path. Any consumer assuming that action always points at a link row must handle nil — the Svelte admin view already does (`targetLabel` renders the bare type). Filter on `metadata.batch` to separate the two sources.
3. **[#0106](0106.md)**: per-location QR attribution works because placement-only rows now produce distinct keys — but there is **no idempotency key** on this endpoint, so a double-submitted batch means a doubled QR sheet.
4. **[#0108](0108.md)**: `docs/utm.md` now carries the dedup-bypass rationale and the double-submit contract change. It still lacks the print-row convention (`utm_medium=print`, `utm_source=flyer`, placement as the location), which lives only in `docs/campaigns-plan.md:310`.

## Follow-ups

- No idempotency key on batch create; a lost response followed by a retry doubles the batch.
- `role="alert"` sits on every duplicate-row note, so eight rows could announce eight live regions at once. One summary alert would be kinder.
- An archived campaign accepts batch create — consistent with assign, which also does, so not a new gap, but neither was deliberately decided.
