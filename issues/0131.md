## Description

Add an idempotent command, `shortlinks portiko-import`, that copies each ShortLinks user into Portiko as follows:
- an account with a new opaque `subject`
- the email as a verified `identifiers` row
- each passkey whose `user_handle` was captured (#0127), copied into Portiko's `passkey_credentials`

It then records that `subject` on the ShortLinks user (`users.subject`), so the user signs in with their existing passkey and never re-enrolls.

## Long Description

**Field mapping** (the two schemas are nearly the same because Portiko was ported from ShortLinks):

| ShortLinks `passkey_credentials` | Portiko `passkey_credentials` |
|---|---|
| `credential_id`, `public_key`, `aaguid`, `sign_count`, `device_name`, `created_at`, `last_used_at` | same columns |
| `backup_eligible`, `backup_state` | same. **Backup Eligible must be copied exactly**: go-webauthn compares it on every assertion, and a wrong value enrolls fine and then fails every login (see Portiko's migration 000001 comment). |
| `user_handle` (from #0127) | `user_handle` |
| — | `rp_id` = the instance's `WEBAUTHN_RP_ID` |

`users.email` becomes a Portiko `identifiers` row (`kind='email'`, `is_primary`, `verified_at` = the ShortLinks `created_at`). ShortLinks verified it by magic link when the account was created. `users.active=false` accounts are imported but stay deactivated through ShortLinks' own check in #0132. Portiko's `users.active` stays true, because deactivation is a ShortLinks permission decision.

**Accounts whose handles differ:** see #0127. If one account's credentials report different handles, decide whether Portiko accepts that per credential. Its login builds `passkey.User{Handle: cred.UserHandle}` from the credential being used, so it may already work. If not, change Portiko upstream or import only one handle family and send the rest through recovery. Prove the chosen approach with a test.

**Credentials with no captured handle** aren't imported. The command prints them per user, and the cutover (#0135) tells those users to recover through Portiko: an emailed code, then a new passkey attached to the same subject.

**Requirements:**
- A migration adds `users.subject TEXT UNIQUE` (nullable) to ShortLinks.
- Re-running the command never duplicates rows, and it imports any handles captured since the previous run.
- A `--dry-run` flag prints the counts: users, credentials imported, and credentials skipped for missing handles.
- One transaction per user.
- An audit row is written per imported user.

## Expected behavior

After import, a user whose handle was captured completes a Portiko sign-in at `/id/signin` with the same passkey, and Portiko issues tokens whose `sub` equals that user's `users.subject`.

## Notes

- Test with `virtualwebauthn`: register through the current ShortLinks flow, log in once (which captures the handle), import, then sign in through Portiko with the same virtual authenticator.
- This runs separately per instance (three databases), like the migrations do today.

## Root cause

The embedded provider (#0130) starts empty, and ShortLinks' accounts and passkeys live only in its own tables, so nobody could sign in through Portiko without re-enrolling. Nothing mapped a ShortLinks user to a Portiko subject either.

## Fix

- **Migration 000024** adds `users.subject TEXT UNIQUE` (nullable).
- **`shortlinks portiko-import [--dry-run]`** (`cmd/shortlinks/portiko_import.go`, `internal/idp/import.go`). It reads the same environment as `serve`, so it runs once per instance. With `PORTIKO_ENABLED` off it prints a note and does nothing (`idp.Import` returns nil).
- **Per user:** a Portiko transaction finds the account (by the recorded `users.subject`, else by verified email) or creates it with a `usr_` subject, plus the email as a verified, primary identifier (`verified_at` = ShortLinks `created_at`). It inserts each credential that has a `user_handle`, copying `backup_eligible` and `backup_state` exactly, with `rp_id` = `WEBAUTHN_RP_ID`. An existing credential is left alone (Portiko owns its sign count afterwards), and one owned by a different Portiko account fails that user rather than moving it. Then a ShortLinks transaction sets `users.subject` where it is NULL and writes an `account.portiko_imported` audit row. Users that nothing changed get no audit row on re-runs.
- **Safe to re-run:** a crash between the two commits is repaired by the next run, which adopts the account by email. Handles captured since the last run are picked up. A failing user is rolled back and reported, and the rest continue (non-zero exit).
- **`--dry-run`** runs the same logic and rolls back. It does not create or migrate the `portiko` schema; a missing schema counts as empty.
- **ShortLinks is never modified beyond `users.subject` and the audit rows.** Credentials, sessions and other tables are only read (the test snapshots them).
- **Different handles on one account:** no upstream change needed. Portiko's login builds `passkey.User{Handle: cred.UserHandle}` from the credential used, and the test proves two handle families on one account both sign in. Credentials without a handle are skipped and listed per user for #0135's recovery path.
- Portiko's `users.active` stays true; deactivation remains ShortLinks' check (#0132).
- Docs: `docs/configuration.md`, `DEPLOYMENT.md`.

- switch off: nil report, no `portiko` schema
- dry run: 4 users, 3 importable, 1 skipped; no schema, no subjects
- import: 4 accounts, 3 credentials, all with BE/BS and `rp_id` copied, emails normalized, `users.subject` set, 4 audit rows
- second import: 0 created, 0 imported, 3 already present; subjects unchanged; counts identical (no duplicates)
- ShortLinks tables (credentials, users columns, sessions) byte-identical before and after
- subject wiped on Bob: re-adopted by email, same subject, no duplicate account
- Carol's handle restored: next run imports it
- provider started over the imported data: Alice's two passkeys (two handle families), Bob's and Carol's all complete `/id/accounts/v1/login/finish` with the same virtual authenticators, and the new Portiko session's account subject equals `users.subject`.

## Review round 1

Opus asked for changes; all done in new commits (after merging main).

- **Account takeover closed.** Matching a user to a Portiko account by email could attach user B to an account whose subject already belongs to ShortLinks user A. Now, before the Portiko transaction commits, the import checks `SELECT id FROM users WHERE subject = $1 AND id <> $2` in ShortLinks. A hit fails that user, rolls back the Portiko transaction and appears in the report as `FAILED <email>: portiko account ... already belongs to ShortLinks user N; not merging (resolve by hand)`. The command exits non-zero.
- **Email matching** is case-insensitive (`lower(value) = lower($1)`) and requires `verified_at IS NOT NULL`.
- **Adoptions are listed.** Users matched to an existing account by email, rather than by recorded subject, print under the counts as `matched an existing Portiko account by verified email (review)`. This includes the crash-recovery case.
- **Tests** (`internal/idp/import_takeover_test.go`): two legacy rows differing only by email case (second fails, no credential reaches Portiko, still safe on re-run); A imported, A's email changed, B registers with A's old address (B fails, no subject, no credential added); an unverified identifier is not adopted; adoption is printed in the output.
- **Known limit:** a dry run cannot see the collision, because it records no subjects. The real run reports it.
- **Verification:** fresh DB migrated to 24, `go vet ./...` clean and `go test -count=1 -p 1 ./...` passes in every package. The DB was dropped.
- Files: `internal/idp/import.go`, `internal/idp/import_takeover_test.go`, `issues/0131.md`.
