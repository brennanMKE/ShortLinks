# 0131 — Import existing ShortLinks accounts and passkeys into the embedded Portiko provider

| | |
|---|---|
| **Status** | open |
| **Module** | auth / db |
| **Platform** | All |
| **Phase** | 13 — Embedded provider |
| **First seen** | 2026-11-12 |

## Description

Add an idempotent command, `shortlinks portiko-import`, that copies each ShortLinks user into Portiko as follows:
- an account with a new opaque `subject`
- the email as a verified `identifiers` row
- each passkey whose `user_handle` was captured (#0127), copied into Portiko's `passkey_credentials`

It then records that `subject` on the ShortLinks user (`users.subject`), so the user signs in with their existing passkey and never re-enrolls.

## Long Description

**Field mapping** (the two schemas are nearly the same because Portiko was ported from ShortLinks):

| ShortLinks `passkey_credentials` | Portiko `passkey_credentials` |
|---|---|
| `credential_id`, `public_key`, `aaguid`, `sign_count`, `device_name`, `created_at`, `last_used_at` | same columns |
| `backup_eligible`, `backup_state` | same. **Backup Eligible must be copied exactly**: go-webauthn compares it on every assertion, and a wrong value enrolls fine and then fails every login (see Portiko's migration 000001 comment). |
| `user_handle` (from #0127) | `user_handle` |
| — | `rp_id` = the instance's `WEBAUTHN_RP_ID` |

`users.email` becomes a Portiko `identifiers` row (`kind='email'`, `is_primary`, `verified_at` = the ShortLinks `created_at`). ShortLinks verified it by magic link when the account was created. `users.active=false` accounts are imported but stay deactivated through ShortLinks' own check in #0132. Portiko's `users.active` stays true, because deactivation is a ShortLinks permission decision.

**Accounts whose handles differ:** see #0127. If one account's credentials report different handles, decide whether Portiko accepts that per credential. Its login builds `passkey.User{Handle: cred.UserHandle}` from the credential being used, so it may already work. If not, change Portiko upstream or import only one handle family and send the rest through recovery. Prove the chosen approach with a test.

**Credentials with no captured handle** aren't imported. The command prints them per user, and the cutover (#0135) tells those users to recover through Portiko: an emailed code, then a new passkey attached to the same subject.

**Requirements:**
- A migration adds `users.subject TEXT UNIQUE` (nullable) to ShortLinks.
- Re-running the command never duplicates rows, and it imports any handles captured since the previous run.
- A `--dry-run` flag prints the counts: users, credentials imported, and credentials skipped for missing handles.
- One transaction per user.
- An audit row is written per imported user.

## Expected behavior

After import, a user whose handle was captured completes a Portiko sign-in at `/id/signin` with the same passkey, and Portiko issues tokens whose `sub` equals that user's `users.subject`.

## Notes

- Test with `virtualwebauthn`: register through the current ShortLinks flow, log in once (which captures the handle), import, then sign in through Portiko with the same virtual authenticator.
- This runs separately per instance (three databases), like the migrations do today.
