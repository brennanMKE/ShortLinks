# 0086 — E2E: account & passkey management UI

## Description

Automate the Account view — profile info and the passkey/credentials management UI
(list, rename, revoke). Depends on [#0080](0080.md); part of [#0079](0079.md).

## Important dev-mode caveat

In dev (`STORAGE=json`) the credentials store is **stubbed**: `GET
/account/credentials` returns an empty list and there are no real passkeys.
So the *populated* credential-management flows (rename/revoke of a real passkey)
**cannot** be exercised against the dev build, and adding a passkey needs a
WebAuthn ceremony that `safaridriver` can't drive (see #0079 / #0081).

**Decision for this issue:** automate what the dev build actually renders — the
Account view chrome, the empty-credentials state, and any request/response wiring
that is observable — and document the rest as covered by `account.test.ts` (unit)
plus manual device verification. If the harness can inject a fake credential into
the dev store, extend to rename/revoke; otherwise defer those to a note.

## Scope / scenarios to automate

- **Account view renders** for the logged-in admin (email/identity, the passkeys
  section).
- **Empty credentials state** is shown (matches the dev stub) without error.
- **Rename / revoke UI (conditional).** If a credential can be seeded into the dev
  store, assert rename (`PATCH /account/credentials/{id}`) and revoke
  (`DELETE …/{id}`) update the list. If not, document the gap.

## Preconditions

- Fresh-seed dev server; `AccountPage` page object. Optional: a harness hook to
  seed a fake credential row into the dev store.

## Acceptance criteria

- [ ] Account view renders for the auto-logged-in admin.
- [ ] Empty-credentials state asserted (no error).
- [ ] Rename/revoke either automated (if a credential can be seeded) or explicitly
      documented as deferred to unit + manual, with the reason.

## Out of scope

- Passkey *registration* ceremony (safaridriver can't drive WebAuthn).
- Recovery flow — #0081.

## Notes

- Consider a small dev-only seam to inject a credential into the devstore for test
  purposes; weigh it against keeping dev code clean. If added, it must be guarded
  by `DevMode()` like the other dev-only paths.
