## Description

Backend rollups for a campaign: total clicks, clicks over time, per-link breakdown, and channel breakdowns. Answers the plan's three questions — how many clicks in total and over time, which channel or placement drove them, and what links belong to the campaign.

All queries group on `clicks.campaign_id` ([#0100](0100.md)), never on `utm_campaign` strings. That is the point of the FK: renaming a campaign does not orphan its metrics, and casing drift in `utm_campaign` (a documented hazard in `docs/utm.md`) cannot fragment the numbers.

## Scope / deliverables

Extend `internal/clicks/stats.go`. **Reuse the existing `breakdown` helper and its `allowedDimensions` allowlist** rather than writing new interpolation logic — that allowlist is what keeps dimension names out of raw SQL.

```go
func (s *StatsStore) CampaignStats(ctx, campaignID int64, from, to time.Time) (CampaignStats, error)
func (s *StatsStore) CampaignClicksOverTime(ctx, campaignID int64, from, to time.Time) (TimeseriesResult, error)
func (s *StatsStore) CampaignClicksByLink(ctx, campaignID int64, from, to time.Time) ([]LinkBucket, error)
func (s *StatsStore) CampaignSeriesByLink(ctx, campaignID int64, from, to time.Time) ([]LinkSeries, error)
```

`CampaignStats` returns total clicks, the bot-excluded count ([#0101](0101.md)), and per-dimension breakdowns for source, medium, content, and referer.

`CampaignSeriesByLink` powers the multi-series chart in [#0104](0104.md). **Cap the series count at 5–8 and fold the remainder into an "Other" series** — a campaign with 30 fliers otherwise renders as spaghetti. The cap belongs in the query layer so the frontend cannot forget it.

Endpoints, following existing `/api/` conventions:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/campaigns/{slug}/stats` | Stats, optional `from` / `to` |

Also fill in the link count and total clicks that [#0098](0098.md) stubbed as 0 on `GET /api/campaigns`, and extend `GET /api/campaigns/{slug}` to return metadata, links, and stats in one payload — mirroring how `GET /api/links/{key}` already returns detail plus `utm_stats` plus `timeseries`, so the frontend patterns carry over.

## Conventions to preserve

These already hold across `stats.go` and must not drift:

- Non-nil empty slices, so JSON serializes as `[]` and never `null`.
- Half-open `[from, to)` window.
- UTC day bucketing via `date_trunc('day', clicked_at AT TIME ZONE 'UTC')`.
- `YYYY-MM-DD` string dates.
- The `(none)` sentinel and the 20-row `breakdownLimit`.

**Default window: the campaign's `starts_at` to `ends_at` when both are set, clamped to today; otherwise the existing 30-day default.** A campaign chart that ignores the campaign's own dates is the wrong default.

## Acceptance criteria

DB integration tests, matching the existing bar on `stats.go`:

- [ ] Empty campaign returns zeros and `[]`, not `null` and not an error.
- [ ] Single link, then multiple links, aggregate correctly.
- [ ] Clicks outside the window are excluded; boundary behavior matches the half-open `[from, to)` convention at both ends.
- [ ] **Clicks on a since-unassigned link remain attributed to the campaign** — the denormalization's whole purpose, asserted directly here as well as in [#0100](0100.md).
- [ ] Bot clicks are excluded from totals and breakdowns, and the excluded count is returned.
- [ ] A campaign with more links than the series cap returns exactly the cap plus one "Other" series, and **the "Other" series' totals reconcile with the overall total** — a fold that loses clicks is worse than no fold.
- [ ] Default window follows the campaign's dates when set, and falls back to 30 days when not.
- [ ] **Ownership**: user A cannot read stats for user B's campaign.
- [ ] `EXPLAIN` confirms `idx_clicks_campaign_time` carries the timeseries query, with `Index Cond` on **both** `campaign_id` and `clicked_at`. Two amendments from what shipped since this issue was written: a residual **`Filter: (NOT is_bot)` node is expected and is not a failure** — [#0101](0101.md) deliberately left the partial predicate as `WHERE campaign_id IS NOT NULL` so the same index also serves the bot-inclusive excluded-count query — and asserting the index by **name alone is not sufficient**, since [#0100](0100.md) demonstrated that a name-grep passes against an index with the columns reversed. Assert the two-column `Index Cond`, or read column order from `pg_indexes.indexdef`.
- [ ] **Do not extend `idx_clicks_campaign_time`'s partial predicate** to `AND is_bot = FALSE`, and do not add a migration to do so. This issue's own excluded-count requirement needs `is_bot = TRUE` rows, which such an index cannot serve. See #0101's resolution for the measurements.
- [ ] **Reuse an existing bot-exclusion spelling rather than inventing a fifth.** The tree already has three (`AND c.is_bot = FALSE` correlated subquery, `ON … AND c.is_bot = FALSE` join, `FILTER (WHERE NOT is_bot)`), and this issue's `link_count`/`total_clicks` would add another. Cross-check the new counts against an existing site rather than only asserting absolute numbers.
- [ ] **A campaign whose every click is a bot click must still appear** in any campaign-level list or aggregate. The `LEFT JOIN … ON` vs `WHERE` trap from #0101 generalizes: putting the predicate in `WHERE` collapses the `GROUP BY` and the row disappears. Test it directly.
- [ ] `go build ./...`, `go vet ./...`, `gofmt -l` clean; `go test ./...` passes with new tests observed **by name** against the live `shortlinks_test` database.

## Root cause

Not a defect — the read side of the campaigns feature.

## Fix

Four campaign-scoped queries extracted as window-resolved, `rowQuerier`-taking functions so the standalone and transactional paths run **the same SQL** rather than two copies. `breakdown` was refactored into a package-level `dimensionBreakdown` shared with the per-link path, with `utm_content`/`referer` added to `allowedDimensions` — one validated interpolation site instead of two that could drift.

The interface is the interesting part. `campaignStatsProvider` exposes exactly **two composite methods** — `CampaignSummary` (stats + timeseries) and `CampaignRollup` (+ by-link + series-by-link) — each reading its whole payload inside one `REPEATABLE READ`, read-only transaction. The four per-fragment methods are not on the interface, so a handler **cannot** assemble one response from reads taken at different instants. That is stronger than hoisting the transaction into the handler, which would have left the split representable for the next endpoint to reintroduce.

`campaigns.Store` gained `link_count`/`total_clicks` via two **correlated subqueries** rather than `JOIN`+`GROUP BY`, reusing the bot-exclusion spelling from `links.Store`, so a campaign with only bot clicks — or no links — never disappears from the list.

## Verification

`go build`, `go vet` clean; `go test ./... -race` green apart from the pre-existing `internal/config` failure; `npm run check` 187/0; `npm test` 222 passing. `internal/clicks/stats.go` is now gofmt-clean, reducing the repo-wide `gofmt -l` list to two known files. DB left at v12, statistics and reloptions clean.

Two review rounds, both `REQUEST CHANGES`, then approve. **Three of the first round's four blocking findings were about evidence rather than logic** — the query code held up against everything thrown at it, but three headline claims in the report survived mutation:

- The transaction assertion counted `BEGIN`s, so switching every read from the transaction to the pool, *and* downgrading `RepeatableRead` → `ReadCommitted`, both left the suite green.
- The transaction covered 7 of 15 round trips: `timeseries`, `by_link` and `series_by_link` each got their own snapshot **in the same response body**. Measured under concurrent writers: **92 of 200 responses** had a timeseries that didn't sum to `click_count`.
- A comment claimed `total_clicks` was cross-checked against a neighbouring site. It wasn't — the test asserted two absolutes. And the numbers genuinely disagree: `total_clicks` is all-time while `stats.click_count` is windowed, so a campaign with 5 clicks 60 days ago returns `total_clicks=5, stats.click_count=0` — #0101's "Total clicks: 5" above "No click data yet", one issue later.

The replacement guards are load-bearing: concurrent writers assert `sum(by_source) == click_count` and `sum(timeseries.days) == click_count` on every call, and both mutants die at **iteration 0–1** against runs of 40–100 iterations — roughly 30× headroom, with an `iterations < 10` floor preventing a vacuous pass on a slow machine.

## Gotchas

- **A test that leaves rows behind changes the fixture for everything downstream, and the failure surfaces somewhere unrelated.** The concurrency tests broke the `EXPLAIN` tests — `-shuffle` failed on **2 of 3 seeds** on clean single runs, while file order happened to hide it. The mechanism is worth knowing: autovacuum can fire an `ANALYZE` mid-burst while ~100k rows sharing one `campaign_id` are the table's only data, writing `most_common_vals={1}, freq=1.0`; the test then deletes its rows, and **`ANALYZE` on an empty table is a documented no-op**, so the skewed histogram persists indefinitely and corrupts row estimates for every later `campaign_id` filter. The fix must disable autovacuum around the burst and run its own `ANALYZE` while it is still off, or the automatic one wins.
- **`SET (autovacuum_enabled = true)` is not the inverse of disabling it.** It writes an explicit reloption that `pg_dump` emits as `WITH (…)`, so the table stops matching a clean `migrate up` — the exact drift [#0110](0110.md) documents, introduced by the helper meant to prevent contamination. `RESET` restores absent-means-default.
- **The default window's `to` is today's UTC midnight, exclusive, so today's clicks never appear.** This is correct against the stated conventions and matches `ClicksOverTime`, but it was inherited rather than decided: it silently broke the first attempt at the concurrency test (every concurrent write fell outside the default window), and for a *live* campaign it is the steady state — `total_clicks: 51` beside `stats.click_count: 1`. See Follow-ups.
- **Parameterizing a test over two readers is not free.** Running them as sequential subtests against one write burst gave the second reader a table the writers had already grown, so it intermittently tripped the iterations floor — a false failure about pacing, not about the property. Interleaving both readers in one loop with a doubled budget fixed it (0/12 on the previously-flaky seed).
- **The narrower interface is the fix.** Everything above about snapshots would have been re-introducible if the handler kept access to the per-fragment methods.

## Downstream constraints

1. **[#0104](0104.md)**: `stats.click_count` never includes the current UTC day. Either clamp `to` to tomorrow's midnight for the campaign default, or label the window "through yesterday" — but decide, don't inherit.
2. **[#0103](0103.md)/[#0104](0104.md)**: `total_clicks` (all-time), `stats.click_count` (windowed), `link_count` (current membership) and `by_link` (historical) are four numbers on two time scales in one payload. The divergence is now *documented and pinned* by `TestCampaignsGet_TotalClicksIsAllTimeStatsClickCountIsWindowed` — do not "fix" it in the UI by making them agree; that test exists to force the decision through review.
3. **#0104**: `series_by_link` is capped at 6 + `Other`; `by_link` is uncapped. `LinkSeries.Days` omits zero-click days, so the frontend must fill gaps **per series**.
4. **[#0107](0107.md)**: use `CampaignRollup`, not the four standalone methods — they are production-dead and carry `STANDALONE:` warnings precisely because using them straddles snapshots.
5. **#0103**: dev mode returns `total_clicks: 0` and empty stats always, so a UI built against `scripts/dev.sh` cannot exercise the non-zero paths.
6. **[#0110](0110.md)**: a hard-killed concurrency test can leave `{autovacuum_enabled=false}` on `clicks`; `truncate()` now repairs it on any subsequent run, but a live-DB-vs-`migrate up` comparison could still catch it mid-window.

## Follow-ups

- **Decide the current-day exclusion** (constraint 1). It will arrive as "I clicked my own link 20 times and the number didn't move."
- The four standalone `StatsStore` methods are now test-only. Keeping them is fine — they are well tested and warn about their snapshot semantics — but they are a trap for the next caller.
- The `EXPLAIN` tests pin the planner's choice for a *narrow* window. At 150k rows a wide window closer to a full campaign's history reasonably prefers `idx_clicks_campaign_id` instead. Expected scale-dependent behavior, not a defect, but worth knowing before someone "fixes" it.
