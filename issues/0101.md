## Description

Populates the `is_bot` column added in [#0100](0100.md) and excludes flagged rows from stats.

This matters more than it looks, and it is a prerequisite for the campaigns feature being *honest* rather than merely functional. The whole point of the campaign view is comparing channels — social posts against an emailed link against printed fliers. Posting a short link in Slack, iMessage, Twitter/X, Discord, or LinkedIn triggers automated fetches of the redirect, sometimes several per post. **A flier gets none of that.** Without filtering, social is inflated by a constant that has nothing to do with human interest, and the bar chart quietly answers the wrong question.

## Scope / deliverables

- Classify at record time from the user agent, against a maintained substring list: `bot`, `crawler`, `spider`, `preview`, `facebookexternalhit`, `Slackbot`, `Twitterbot`, `Discordbot`, `WhatsApp`, `TelegramBot`, `LinkedInBot`, `headless`, `curl`, `wget`, `python-requests`.
- Keep the list in one named, exported, unit-testable place — not inline in the recorder. It will need editing as crawlers change, and that edit should be obvious and low-risk.
- Match case-insensitively.
- **Exclude `is_bot = TRUE` from link and campaign stats by default.**
- **Surface the excluded count** wherever stats are shown, rather than silently dropping it. A number that quietly shrank is worse than one that explains itself.

## Acceptance criteria

- [ ] Each substring in the list is covered by a test case using a realistic user-agent string, not the bare token.
- [ ] Classification is case-insensitive (`SlackBot`, `slackbot`, `SLACKBOT` all match).
- [ ] An empty or absent user agent does **not** classify as a bot — decide the policy deliberately and test it either way, but do not leave it accidental.
- [ ] A normal browser user agent is not flagged. Include at least Safari on iOS, Chrome on macOS, and a WebView, since those are what this app actually sees.
- [ ] Existing rows keep `is_bot = FALSE` and are unaffected.
- [ ] Stats queries exclude bots by default; the excluded count is returned alongside the totals, not computed separately by the caller.
- [ ] Recording a bot click still writes the row — it is flagged, never dropped. The data has to remain inspectable.
- [ ] `go build ./...`, `go vet ./...`, `gofmt -l` clean; `go test ./...` passes with new tests observed **by name**.

## Out of scope

- **IP-based bot detection.** Explicitly deferred by the plan.
- **Unique-visitor deduplication.** There is no cookie or visitor hash; every click is a click. One person scanning a poster twice counts twice, and that stays true.
- Retroactive classification of historical clicks. They keep `is_bot = FALSE`, which will understate bot traffic before the deploy — worth a line in the docs.
- A UI for editing the substring list.

## Notes

- **User-agent filtering is a floor, not a solution.** Some crawlers do not identify themselves, so social will still carry residual inflation after this lands. `docs/campaigns.md` ([#0108](0108.md)) should say so plainly rather than implying the filtered numbers are clean.
- Print scans have no referer and no bot noise, so they undercount relative to social in raw comparison while being cleaner signal per click. That asymmetry is worth documenting next to any chart that puts the two side by side.
- Impression volume differs by orders of magnitude between a social post and a poster. Click-through per impression is the meaningful comparison and ShortLinks cannot measure impressions — the UI should not imply the bar chart settles the question.

## Root cause

Not a defect — the honesty layer for campaign comparison. `is_bot` existed (added by [#0100](0100.md)) with nothing populating or reading it, so every social post's unfurl bots counted as interest while a printed flier got none of that inflation.

## Fix

`IsBot` in a dedicated `internal/clicks/botdetect.go`, matching case-insensitively against an exported substring list, classified in Go and passed as `$11` into #0100's existing single-statement INSERT — no extra query on the redirect path. Bot rows are **flagged, never dropped**, so the data stays inspectable. `ClickCount`, `breakdown()`, and `ClicksOverTime` all exclude bots, and `UTMStats.ExcludedBotCount` is returned from the same query via `COUNT(*) FILTER`.

Two decisions the issue left open:

**An empty or absent user agent is NOT a bot.** Absence of a UA is missing evidence rather than evidence of automation, and every crawler on the list self-identifies by default. The stronger argument is asymmetry of harm: a false positive **permanently erases a real human click** from every number with no recovery path (backfill is out of scope), while a false negative leaves residual inflation the issue already concedes user-agent filtering cannot remove. When error costs are that unequal, the conservative choice wins regardless of which population dominates UA-less traffic.

**`idx_clicks_campaign_time`'s partial predicate stays `WHERE campaign_id IS NOT NULL`** — no migration `000013`, and a residual `Filter: (NOT is_bot)` is accepted. Extending it to `AND is_bot = FALSE` would make the index **unusable for any query that doesn't also filter `is_bot = FALSE`** — including this issue's own `ExcludedBotCount` query, which sits directly beside the filtered total in the same call. That fallback reproduced at every distribution tested; the magnitudes did not, and the doc comment says so explicitly rather than quoting a ratio.

## Gotchas

- **`CUBOT` is a real Android phone brand, and a bare `"bot"` substring matches it.** Three shipping models put `CUBOT` in the device field of ordinary Chrome-on-Android UAs, so every owner's clicks would have been silently and permanently excluded. Dropping the generic `"bot"` entry isn't the fix — it catches unenumerated crawlers like `bingbot` and `AhrefsBot` — and a word-boundary rule fails because `Googlebot` has a letter before `bot`. An explicit exception list was the answer. **Substring matching on a three-letter English fragment will collide with something real; the only question is whether you find it before your users do.**
- **A number can be wrong without any test failing, if no test compares it to its neighbour.** `links.Store.click_count` stayed raw while `utm_stats.click_count` became filtered, and both ship in one payload — a link with five crawler clicks would render "Total clicks: 5" directly above "No click data yet". Every test passed because each asserted its own number in isolation.
- **`LEFT JOIN … ON` vs `WHERE` decides row membership, not just the count.** Putting `is_bot = FALSE` in `WHERE` makes a bot-only link vanish from its owner's list entirely, because `GROUP BY` collapses to nothing. The count is the visible symptom; disappearing rows are the real damage.
- **vitest does not type-check.** Making `excluded_bot_count` required broke a `Partial<T>` fixture factory: 222 tests green, `npm run check` red. Both commands are load-bearing and neither substitutes for the other.
- **A statement-count assertion is a tripwire.** Pinning "exactly 4 statements" killed a *semantics-improving* change (wrapping the reads in a transaction, since pgx's `Begin` fires `TraceQueryStart`) and reported a cause that was false. Asserting the **property** — one statement containing `FILTER (WHERE`, none matching the bare per-count shape — survives refactors and fails only for the real reason.
- **Unhedged benchmark numbers in a comment invite distrust of the comment.** "22× cost, 83× buffers" measured 1.04×/2.3× at another distribution. The *fallback* reproduced every time; the ratio never will.

## Downstream constraints

1. **[#0102](0102.md)'s `EXPLAIN` criterion needs amending** — a `Filter: (NOT is_bot)` node is **expected and correct**, not a failure, and the criterion should assert a two-column `Index Cond` rather than grepping for the index name (which #0100 proved passes on a reversed-column index). Amended in that issue.
2. **#0102 must not extend the partial predicate either** — its own excluded-count requirement needs `is_bot = TRUE` rows.
3. **"Count clicks for X excluding bots" now has three spellings in the tree** (`AND c.is_bot = FALSE` subquery, `ON … AND c.is_bot = FALSE` join, `FILTER (WHERE NOT is_bot)`). #0102's `link_count`/`total_clicks` would be a **fifth** independent implementation. Reuse one, and cross-check against an existing site rather than only asserting an absolute.
4. **The `ON`-clause trap generalizes** to any campaign-level aggregate joining `campaigns`/`links` → `clicks`: a campaign whose every click is a bot click would vanish from the campaign list. Carry an equivalent membership test.
5. **#0103** must surface `excluded_bot_count`, and will hit the same `Partial<T>` fixture-factory breakage when it adds payload fields.
6. **[#0107](0107.md)** needs an explicit decision on whether CSV export includes `is_bot = TRUE` rows.
7. **[#0108](0108.md)** now owes **three** deploy-discontinuity notes in `docs/analytics.md`: #0100's UTM fallback, #0101's bot exclusion, and the fact that pre-deploy rows are all `is_bot = FALSE` so historical bot traffic is understated — a chart spanning the deploy shows an artificial step that is not a traffic change. Plus the dedup response's `click_count` changing meaning.

## Follow-ups

- **`NotBotUserAgentSubstrings` suppresses the entire bot list, not just the generic `"bot"` entry it collides with** — so `facebookexternalhit/1.1 CUBOT` classifies as not-a-bot. Correct today with one entry and honestly documented, but every future entry silently disables the whole list for any UA containing it. Scope the exception to the generic entry when a second one lands.
- **`UTMStatsForLink`'s four reads are not in a transaction**, so under concurrent recording the breakdowns can out-sum `ClickCount` — an invariant this issue introduced and now asserts. #0102 makes it worse by adding two more dimensions to the same read. A `REPEATABLE READ` transaction is the fix.
- Bot classification is not retroactive: pre-deploy rows keep `is_bot = FALSE`.
