# 0101 — Classify and exclude bot/preview-crawler clicks

| | |
|---|---|
| **Status** | open |
| **Module** | clicks / handlers / web |
| **Platform** | All |
| **First seen** | 2026-08-07 |

## Description

Populates the `is_bot` column added in [#0100](0100.md) and excludes flagged rows from stats.

This matters more than it looks, and it is a prerequisite for the campaigns feature being *honest* rather than merely functional. The whole point of the campaign view is comparing channels — social posts against an emailed link against printed fliers. Posting a short link in Slack, iMessage, Twitter/X, Discord, or LinkedIn triggers automated fetches of the redirect, sometimes several per post. **A flier gets none of that.** Without filtering, social is inflated by a constant that has nothing to do with human interest, and the bar chart quietly answers the wrong question.

## Scope / deliverables

- Classify at record time from the user agent, against a maintained substring list: `bot`, `crawler`, `spider`, `preview`, `facebookexternalhit`, `Slackbot`, `Twitterbot`, `Discordbot`, `WhatsApp`, `TelegramBot`, `LinkedInBot`, `headless`, `curl`, `wget`, `python-requests`.
- Keep the list in one named, exported, unit-testable place — not inline in the recorder. It will need editing as crawlers change, and that edit should be obvious and low-risk.
- Match case-insensitively.
- **Exclude `is_bot = TRUE` from link and campaign stats by default.**
- **Surface the excluded count** wherever stats are shown, rather than silently dropping it. A number that quietly shrank is worse than one that explains itself.

## Acceptance criteria

- [ ] Each substring in the list is covered by a test case using a realistic user-agent string, not the bare token.
- [ ] Classification is case-insensitive (`SlackBot`, `slackbot`, `SLACKBOT` all match).
- [ ] An empty or absent user agent does **not** classify as a bot — decide the policy deliberately and test it either way, but do not leave it accidental.
- [ ] A normal browser user agent is not flagged. Include at least Safari on iOS, Chrome on macOS, and a WebView, since those are what this app actually sees.
- [ ] Existing rows keep `is_bot = FALSE` and are unaffected.
- [ ] Stats queries exclude bots by default; the excluded count is returned alongside the totals, not computed separately by the caller.
- [ ] Recording a bot click still writes the row — it is flagged, never dropped. The data has to remain inspectable.
- [ ] `go build ./...`, `go vet ./...`, `gofmt -l` clean; `go test ./...` passes with new tests observed **by name**.

## Out of scope

- **IP-based bot detection.** Explicitly deferred by the plan.
- **Unique-visitor deduplication.** There is no cookie or visitor hash; every click is a click. One person scanning a poster twice counts twice, and that stays true.
- Retroactive classification of historical clicks. They keep `is_bot = FALSE`, which will understate bot traffic before the deploy — worth a line in the docs.
- A UI for editing the substring list.

## Notes

- **User-agent filtering is a floor, not a solution.** Some crawlers do not identify themselves, so social will still carry residual inflation after this lands. `docs/campaigns.md` ([#0108](0108.md)) should say so plainly rather than implying the filtered numbers are clean.
- Print scans have no referer and no bot noise, so they undercount relative to social in raw comparison while being cleaner signal per click. That asymmetry is worth documenting next to any chart that puts the two side by side.
- Impression volume differs by orders of magnitude between a social post and a poster. Click-through per impression is the meaningful comparison and ShortLinks cannot measure impressions — the UI should not imply the bar chart settles the question.
