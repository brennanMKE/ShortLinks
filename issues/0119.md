# 0119 — Click charts never show today: the default stats window ends at midnight UTC, exclusive

| | |
|---|---|
| **Status** | open |
| **Module** | clicks / handlers |
| **Platform** | All |
| **First seen** | 2026-09-03 |

## Description

Every click chart in the product hides the clicks that happened today. The default stats window resolves `to` to **midnight of the current UTC day** and every timeseries query filters `clicked_at < to`, so the current day is outside the half-open window by construction. A click recorded now does not appear on any chart until the UTC day rolls over — up to 24 hours later, and longer for a user west of UTC whose "today" starts hours after the bucket boundary moved.

This is not caching. Clicks are written to Postgres immediately (`internal/clicks/recorder.go`, from a detached goroutine right after the redirect), every count is a live `COUNT(*)` at request time, there is no materialized view, no HTTP cache header on any JSON response, and no proxy cache in `deploy/apache/go.sstools.co.conf`. The data is in the database within milliseconds; the query simply does not ask for it.

[#0102](0102.md) predicted this exact report in its Follow-ups: *"Decide the current-day exclusion. It will arrive as 'I clicked my own link 20 times and the number didn't move.'"* It named [#0104](0104.md) as the place to decide; #0104 resolved without touching it, so the inherited behavior is still in place.

## Steps to reproduce

1. Open a short link a few times in a normal browser (not a bot user agent).
2. Load the link detail view and reload it.
3. Load the campaign detail view for a campaign that link belongs to, and reload it.

## Expected behavior

Today's clicks appear in the clicks-over-time chart and in the windowed campaign stats, within a page reload of the click happening.

## Actual behavior

- Link detail: the total **Clicks** number goes up immediately (it is an unwindowed live count), but the clicks-over-time chart has no bar for today.
- Campaign detail: the campaign's all-time `total_clicks` goes up, while the windowed `stats.click_count`, the timeseries, the per-link breakdown and the channel breakdown all stay put — the `total_clicks: 51` beside `click_count: 1` divergence #0102 already documented, which is the *steady state* for a live campaign.

## Affected code

- `internal/clicks/stats.go:180-187` — `ClicksOverTime`: `to` defaults to `today` (midnight UTC).
- `internal/clicks/stats.go:195-201` — the query's `AND clicked_at < $3`.
- `internal/clicks/stats.go:497-524` — `campaignWindow`: both the campaign-dates branch (clamped to `today`) and the 30-day fallback end at `today`.
- Every campaign read goes through `campaignWindow`: `CampaignStats`, `CampaignSummary`, `CampaignRollup` (`:327`, `:346`, `:392`), `CampaignClicksOverTime` (`:550`), `CampaignClicksByLink` (`:637`), `CampaignSeriesByLink` (`:731`).
- `internal/handlers/links.go:670` — the link-detail handler passes `zeroTime, zeroTime`, so the default is what production always uses. The API accepts no `from`/`to` from the SPA (`web/src/lib/api.ts` sends none), so no caller can opt out.

## Scope / deliverables

Decide the semantics once and apply them everywhere, rather than leaving the inherited boundary in place:

- Extend the default `to` to the **end** of the current UTC day (tomorrow's midnight), keeping the `< to` half-open form, so today is a real bucket that fills as clicks arrive. This is the recommended option: it makes the charts live, and it makes `stats.click_count` reconcile with `total_clicks` for a campaign whose clicks are all inside the window.
- Whatever is chosen, apply it to `ClicksOverTime` and `campaignWindow` together — they must not disagree, and #0102's reconciliation invariants (`sum(timeseries.days) == click_count`) must still hold.
- A partial day is a real reporting artifact: today's bar is not comparable to a full day's. If the chart implies a trend, the UI should mark today's bucket as in-progress rather than let it read as a decline.
- The campaign-dates branch clamps `to` to `today` so a future `ends_at` does not open an empty tail. Preserve that intent against the new boundary.

## Acceptance criteria

- [ ] A click recorded now appears in the link-detail clicks-over-time chart on the next reload.
- [ ] The same click appears in the campaign timeseries, `by_link`, `series_by_link` and the windowed `stats.click_count` on the next reload.
- [ ] For a campaign whose clicks all fall inside the default window, `stats.click_count` equals `total_clicks`.
- [ ] `sum(timeseries.days) == stats.click_count` still holds under the concurrent-writer tests #0102 added.
- [ ] A campaign with `ends_at` in the future still does not report buckets past today.
- [ ] `go build ./... && go test ./...` green (except the pre-existing [#0116](0116.md) `internal/config` failure); `cd web && npm run build` and `npm test` green.

## Out of scope

- The `total_clicks` (all-time) vs `stats.click_count` (windowed) divergence as a *design*. #0102's `TestCampaignsGet_TotalClicksIsAllTimeStatsClickCountIsWindowed` deliberately pins it; this issue removes the current-day component of the gap, not the windowing itself.
- Per-user timezones. Buckets stay UTC.
- A user-selectable date range in the SPA.

## Notes

- Bot filtering is a separate reason a click may not show: `is_bot = TRUE` clicks are excluded from every stat (#0101), and `BotUserAgentSubstrings` includes `"preview"`, so link-preview fetches from a messaging app are recorded but never counted. A click that never appears at all — as opposed to appearing a day late — is more likely this than the window.
- Dev mode returns `total_clicks: 0` and empty stats always (#0102 constraint 5), so `scripts/dev.sh` alone cannot exercise this. Verification needs the Postgres path.
