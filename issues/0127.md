## Description

Registration generates a random 16-byte user handle (`internal/auth/webauthn.go`, `userHandleLen`) and then throws it away. `FinishLogin` only copies it from each assertion (`internal/auth/login.go`, `NewLoginUser(rec.UserID, parsed.Response.UserHandle, …)`). Portiko requires the handle (`passkey_credentials.user_handle BYTEA NOT NULL`) and checks every assertion against it. Start recording the handle on each successful login now, so that by cutover most passkeys can be imported as they are (#0131).

## Long Description

**This ships first and on its own.** The handle exists only on the user's authenticator. The server learns it only when the passkey is used to sign in, so every day this runs before cutover means fewer re-enrollments. It doesn't depend on Portiko and should deploy to all three instances as soon as it's ready.

**Wanted:**
- A migration adds `user_handle BYTEA` (nullable) to `passkey_credentials`.
- `FinishLogin`, after `ValidateLogin` succeeds, stores `parsed.Response.UserHandle` in the same transaction that updates sign_count/backup_state, but only if the column is still NULL. If a stored handle differs from the assertion's, log a warning and keep the stored value: it should never change.
- Registration and recovery store the handle they generated (`RegistrationUser.handle`) when they insert the credential, so new passkeys have one from the start.
- The admin user detail, or a one-line query documented in `docs/passkeys.md`, can show how many credentials per instance still have no handle, to judge readiness for #0131.

**Note on handle consistency:** all of an account's passkeys should share one handle in Portiko (Portiko's `passkey.User` has one `Handle`). ShortLinks generated a new handle at each registration and recovery, so one account's passkeys may have *different* handles. Record what each credential reports. #0131 decides how Portiko represents that, which may need checking against Portiko's `internal/accounts/login.go`, since it builds `waUser` with the logged-in credential's handle.

## Expected behavior

After a user signs in once, their credential row has a non-NULL `user_handle` equal to the one their authenticator reports.

## Actual behavior

The handle isn't stored anywhere.

## Notes

- The dev store (`internal/devstore`) needs the matching field only if it models credentials. Check.
- Tests: a login test asserting the handle is stored on first login and left unchanged on the next, and a registration test asserting it's stored at insert. `descope/virtualwebauthn` is already a test dependency.

## Root cause

The handle was never persisted anywhere. Worse, registration and recovery called `NewRegistrationUser` twice: once at begin (whose random handle the browser received and the authenticator stored) and again at finish (a different random handle). So storing "the handle they generated", as this issue first suggested, would have recorded a value no authenticator ever reports.

## Fix

The begin-time handle is saved with the challenge (`webauthn_challenges.user_handle`) and replayed at finish via `registrationUserFromHandle`. The new credential stores it in `passkey_credentials.user_handle`. A challenge row written by the previous binary (NULL handle) falls back to a fresh handle and stores NULL. `FinishLogin` fills the column from the assertion's `userHandle` inside the ceremony transaction, but only while it is still NULL. An empty assertion handle is skipped. A stored handle that disagrees is kept and logged as a warning with `user_id` and the credential row id (no handle bytes). Migration 000017 adds both nullable columns (`SET lock_timeout = '5s'`); the down migration warns that captured handles cannot be regenerated. `docs/passkeys.md` has the readiness queries for #0131.

## Gotchas

- Deploy order is safe in both directions: the old binary ignores the new columns, and the new binary handles NULL-handle challenges from the old one.
- Rolling back 000017 loses every captured handle. Back up `credential_id, user_handle` first.
- Ship this to all three instances early: handles are only learned when people sign in.
- Portiko's login uses each credential's own handle, so one account having passkeys with different handles (ShortLinks made a new handle per registration/recovery) should import cleanly. The allowCredentials path in Portiko's `internal/accounts/login.go` uses `creds[0].UserHandle`; check that in #0131.
