## Description

Automate the Admin ▸ Settings surface, in particular the **registrations-enabled
gate** (`registrations_enabled`) that controls whether new signups are allowed.
Depends on [#0080](0080.md); part of [#0079](0079.md).

## Scope / scenarios to automate

- **Settings view renders** for the admin (`GET /admin/settings`), showing the
  registration gate control and any other settings.
- **Toggle the registration gate.** Flip `registrations_enabled` off → on (or
  vice versa) via `PATCH /admin/settings` → assert the UI reflects the new value
  and it persists on reload.
- **Effect of the gate (if observable in dev).** With registrations disabled,
  assert the observable downstream signal (e.g. the register flow / API reports
  registrations closed). If the effect isn't reachable in the dev stub, assert the
  setting value round-trips and note the downstream is covered by handler tests.

## Preconditions

- Fresh-seed dev server (admin auto-logged-in). `AdminPage` / `SettingsPanel`
  page object. Note: dev audit logging is disabled (`nil`), so don't assert audit
  entries here — that's #0089.

## Acceptance criteria

- [ ] Settings view renders with the registration-gate control.
- [ ] Toggling the gate persists and re-reads correctly.
- [ ] Downstream effect asserted, or explicitly deferred with reason.

## Out of scope

- User activate/deactivate — #0088.
- Audit-log entries produced by settings changes — #0089 (and disabled in dev).

## Notes

- `db-status.sh` treats `registrations_enabled` as the canonical gate
  ("must be 'true' to allow new signups") — mirror that semantics in assertions.
