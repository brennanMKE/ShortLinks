# 0132 — Sign ShortLinks in through Portiko's `rp` library instead of its own passkey flows

| | |
|---|---|
| **Status** | in-progress |
| **Module** | auth / middleware / handlers |
| **Platform** | All |
| **Phase** | 14 — Sign in through Portiko |
| **First seen** | 2026-11-12 |

## Description

Make ShortLinks a relying party of its own embedded provider, using `rp.New`. It gets a Postgres `session.Store` and an `OnSignIn` hook that maps the Portiko subject onto the ShortLinks `users` row. The session middleware (`requireSession`, `requireCookie`, `requireAdmin`, `requireAPI`, about 29 routes in `main.go`) moves onto it. This sits behind the #0130 switch, so an instance runs one sign-in system or the other.

## Long Description

**Routes:**
- `GET /auth/portiko/login` → `client.LoginHandler()`
- `GET /auth/portiko/callback` → `CallbackHandler()`
- `POST /auth/logout` → `LogoutHandler()`, which signs out at the provider and returns to `/`
- `POST /auth/portiko/backchannel` → `BackchannelLogoutHandler()`
- `POST /auth/portiko/events` → `EventsHandler()`, for profile changes
- While Portiko is on, the old `/auth/register/*`, `/auth/login/*` and `/auth/recover*` routes aren't mounted.

**Sessions:** implement `session.Store`, `LogoutStore` and `ProfileStore` in Postgres. That's a migration for a new `rp_sessions` table that keeps the access and refresh tokens: encrypt them at rest, or explain in the plan why that isn't needed. This replaces the `sessions` table for Portiko sign-ins. `CookieKey` comes from config and is the same on every restart.

**`OnSignIn`**, inside one transaction:
1. Look up `users` by `subject`.
2. If there's no match, look up by the verified email in the ID token and record the `subject` on that user. This catches accounts the #0131 import missed.
3. If there's still no match, it's a new user. Create the row and apply the admin rule: the first user, or a match on `ADMIN_EMAIL`, becomes admin. This is the logic moved from `RegistrationService`. With the #0129 policy in place, a new subject only arrives here when registration was allowed.
4. Refuse `active=false` with the same "account deactivated" result as today.
5. Update `last_login_at`.
6. Write the `account.login` audit row (`account.registered` for new users).

**Middleware:** `RequireUser`/`RequireUserAPI` authenticate, and a thin ShortLinks wrapper loads the `users` row by subject into the request context in the existing shape, so handlers don't change. Every request still checks `active` and `is_admin` from ShortLinks' table. The API-token path (`requireAPI` accepting `Authorization: Bearer slk_…`) is unchanged.

**Sign out everywhere:** `POST /auth/logout/all` becomes "sign out of every browser". It calls Portiko's logout-all, and the back-channel logout clears the `rp_sessions` rows. The `SendSessionsRevoked` email goes away unless Portiko sends an equivalent.

**`/api/me`** keeps its response shape.

## Expected behavior

With Portiko on, an imported user goes from `/auth/portiko/login` to Portiko's sign-in at `/id/…`, uses their passkey, lands back signed in with their links, admin rights and API tokens intact, and is signed out by `POST /auth/logout`.

## Notes

- Integration test with `virtualwebauthn` covering the whole loop: import, sign in, `/api/me`, deactivate the user, then the next request gets 401 or 403.
- Rate limiting for sign-in moves to Portiko (`docs/rate-limits.md` in Portiko). Remove ShortLinks' login/register/recover limiters from the Portiko path.
- **Detecting a new account (from the #0129 work, agreed with the Portiko session):** Portiko sends the RP no signal that a sign-in created an account, and OIDC has no standard claim for it. `OnSignIn` treats "no `users` row for this `sub`, and none by verified email" as new. Make that step an atomic insert-if-absent (`INSERT … ON CONFLICT (subject) DO NOTHING RETURNING`, then re-select), or two concurrent first sign-ins race on the admin rule. "New" means new to ShortLinks, not new to Portiko; they differ only if one database is restored without the other. If that ever matters, the cleaner fix is an in-process `provider.Options.OnAccountCreated(ctx, sub, email)` hook beside `RegistrationPolicy` (not built).
- **Registration closed mid-flight:** Portiko re-asks `RegistrationPolicy` when the emailed code is verified, but not at the final passkey step, so one ceremony can still finish within the challenge TTL after an admin closes registration. Refuse unknown subjects in `OnSignIn` while `registrations_enabled` is false to close that gap.
- **Mounting (from #0128):** `mux.Handle("/id/", p.Handler())`, never `http.StripPrefix`. `rp.Config.Issuer` is `BASE_URL + "/id"`. The provider's SSO cookie is `accounts_sso` with `Path=/id`. The rp's own cookies stay at `Path=/`.

## Root cause

ShortLinks signed people in only through its own passkey ceremonies and its own `sessions` table. The embedded provider (#0130) and the `users.subject` mapping (#0131) existed, but nothing authenticated a request through them, and #0131 never checked that a provider sign-in lands on the right ShortLinks user.

## Fix

Everything is behind `PORTIKO_ENABLED`. With it off, `cmd/shortlinks` builds the same guards and routes as before, and `MountPortal` returns the handler untouched. The existing auth tests are unmodified and pass.

- **`internal/idp/portal.go` (`Portal`):** ShortLinks as a relying party of its own provider, via `rp.New`.
  - Issuer `BASE_URL/id`, client `shortlinks`, scopes `email` and `profile` added.
  - The provider now registers the `email` scope and the events URI for the client. Without `email`, `sub` arrived but no address.
  - The rp's discovery, key and token calls go to the provider's handler in-process (`inProcess` transport), so there is no hairpin through Apache and no startup ordering problem.
  - The session key and the flow-cookie key are derived from `PORTIKO_CRYPTO_KEY` with domain separation, so they are stable across restarts and no new setting is needed.
- **Sessions:** Portiko's own `rp/session/pgstore` (it already implements `Store`, `LogoutStore` and `ProfileStore`) on a new `rp_sessions` table (**migration 000028**). The session id is stored only as a SHA-256, and the tokens, email and name are sealed with AES-256-GCM, so the "encrypt at rest" requirement is met. The migration's DDL is the table `pgstore.Migrate` would create. A pruner runs hourly.
- **`OnSignIn`** (one transaction):
  1. Look up by `users.subject`.
  2. Otherwise by email, recording the subject (never re-pointing a user already linked to a different subject).
  3. Otherwise a new user: refused while `registrations_enabled` is false, else inserted with the admin rule (first user or `ADMIN_EMAIL`). The step runs under an advisory lock as an insert-if-absent (`ON CONFLICT (subject) DO NOTHING RETURNING`, then a re-select).
  4. Refuse `active=false`.
  5. Set `last_login_at`.
  6. Write `account.login` (or `account.registered`).
- **Middleware:** `middleware.RequirePortikoSession` wraps `client.RequireUserAPI`, then loads the users row by subject (`auth.Store.ResolveSubject`) into the usual `AuthUser`, so handlers don't change. `active` and `is_admin` are read on every request. `slk_` bearers on session routes still answer 403 `api_token_not_permitted`. `RequireSessionOrAPIToken` and `RequireCookieSession` were split into `RequireGuardOrAPIToken` and `RequireCookieGuard` (the originals delegate), so the API-token path is the same code.
- **Routes (`Portal.Wrap`, in front of the mux, so the `buildMux` pattern list and OpenAPI tests are untouched):** `GET /auth/portiko/login`, `GET /auth/portiko/callback`, `POST /auth/portiko/backchannel`, `POST /auth/portiko/events`. `POST /auth/logout` writes `account.logout`, then runs the rp's `EndSessionHandler("/")`, which ends the session at the provider too. `POST /auth/logout/all` is guarded, ends the current session at the provider, deletes every `rp_sessions` row for the subject, writes `session.revoked_all` and keeps the JSON shape. `/auth/register/*`, `/auth/login/*` and `/auth/recover*` answer 404. `/api/me` is unchanged.
- **Docs:** `docs/configuration.md` ("Signing in through Portiko") and `DEPLOYMENT.md`.

### Differences from the issue text, and limits

- **Logout everywhere:** `rp` has no logout-all call. Portiko's `POST /id/accounts/v1/logout/all` needs the browser's SSO cookie (`Path=/id`), which a server call can't send. So ShortLinks ends this browser's provider session, notifies other sites through back-channel logout, and deletes every ShortLinks session of the subject. The provider sessions in other browsers stay until the user uses the provider's own sign-out everywhere. #0133 can link to it.
- **Refused sign-ins:** `rp` turns any `OnSignIn` error into a bare `500 sign-in failed`, so a deactivated account no longer gets the old "account deactivated" body. The reason is logged (`portiko sign-in refused`). Upstream change that would fix it: let `OnSignIn` return a typed error that the callback maps to a status and a `return_to` error page. Not done.
- **`email_verified`** isn't in `verify.Claims` for the session, and `OnSignIn` trusts that Portiko only issues verified addresses (it only creates identifiers through a verified code).
- **IP** isn't on the audit rows for sign-in: `OnSignIn` has no request.
- **Logout** now answers a 302 to `/` rather than JSON `{"message":"Signed out"}`. #0133 must handle it, or `fetch` will follow the redirect.
- `/account/credentials*` still exists and shows the old, now unused ShortLinks credentials. The SPA stops using it in #0133, and #0136 removes it.
- No `SendSessionsRevoked` email on logout-all while Portiko is on.
- The `inProcess` rp calls reach the provider as 127.0.0.1, so they share one rate-limit bucket on the token endpoint, which Portiko documents as loose.

## Review round 1

Review asked for changes; all done in new commits. Migration 000028 kept; main not merged (#0180 and #0183 land first).

- **Refused sign-ins are 403.** `OnSignIn` records a typed refusal in a context-held slot, and a `callback` wrapper turns rp's bare 500 into `403 {"error": "<message>"}`: "account deactivated", "Registration is currently closed.", or "this account cannot be signed in; contact an administrator" (subject conflict, ambiguous email). A real failure stays a 500. `TestCallbackRefusals` covers each case, and the round-trip test asserts the deactivated one end to end.
- **Ambiguous email:** a `lower(email)` match on more than one user refuses the sign-in and records no subject.
- **Adoption by email** now does `SELECT ... FOR UPDATE`, then `UPDATE ... WHERE subject IS NULL`, and refuses if no row was affected (the subject was set concurrently).
- **401 body** from the Portiko guard is now `{"error":"unauthenticated"}` (rp's `not signed in` is rewritten); tested for no cookie and a stale cookie.
- **logout/all `revoked_count`** counts the current session only if it was still stored before it was ended.
- **#0135** has a "Cutover risk" section: the iPhone app's bearer session tokens (#0077) stop working with the switch on.
- **Verification:** fresh DB (migrated to 28, dropped afterwards), `go build`, `go vet` and `go test -count=1 -p 1 ./...` pass. One run had a timing failure in `internal/clicks` (`TestCampaignRollup_TimeseriesConsistentWithClickCountUnderConcurrentWrites`, "only completed 9 iterations in 1s", code this issue doesn't touch); it passed on re-run. The `internal/idp` portal tests pass.
