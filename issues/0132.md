# 0132 — Sign ShortLinks in through Portiko's `rp` library instead of its own passkey flows

| | |
|---|---|

| **First seen** | 2026-11-12 |

## Description

Make ShortLinks a relying party of its own embedded provider, using `rp.New`. It gets a Postgres `session.Store` and an `OnSignIn` hook that maps the Portiko subject onto the ShortLinks `users` row. The session middleware (`requireSession`, `requireCookie`, `requireAdmin`, `requireAPI`, about 29 routes in `main.go`) moves onto it. This sits behind the #0130 switch, so an instance runs one sign-in system or the other.

## Long Description

**Routes:**
- `GET /auth/portiko/login` → `client.LoginHandler()`
- `GET /auth/portiko/callback` → `CallbackHandler()`
- `POST /auth/logout` → `LogoutHandler()`, which signs out at the provider and returns to `/`
- `POST /auth/portiko/backchannel` → `BackchannelLogoutHandler()`
- `POST /auth/portiko/events` → `EventsHandler()`, for profile changes
- While Portiko is on, the old `/auth/register/*`, `/auth/login/*` and `/auth/recover*` routes aren't mounted.

**Sessions:** implement `session.Store`, `LogoutStore` and `ProfileStore` in Postgres. That's a migration for a new `rp_sessions` table that keeps the access and refresh tokens: encrypt them at rest, or explain in the plan why that isn't needed. This replaces the `sessions` table for Portiko sign-ins. `CookieKey` comes from config and is the same on every restart.

**`OnSignIn`**, inside one transaction:
1. Look up `users` by `subject`.
2. If there's no match, look up by the verified email in the ID token and record the `subject` on that user. This catches accounts the #0131 import missed.
3. If there's still no match, it's a new user. Create the row and apply the admin rule: the first user, or a match on `ADMIN_EMAIL`, becomes admin. This is the logic moved from `RegistrationService`. With the #0129 policy in place, a new subject only arrives here when registration was allowed.
4. Refuse `active=false` with the same "account deactivated" result as today.
5. Update `last_login_at`.
6. Write the `account.login` audit row (`account.registered` for new users).

**Middleware:** `RequireUser`/`RequireUserAPI` authenticate, and a thin ShortLinks wrapper loads the `users` row by subject into the request context in the existing shape, so handlers don't change. Every request still checks `active` and `is_admin` from ShortLinks' table. The API-token path (`requireAPI` accepting `Authorization: Bearer slk_…`) is unchanged.

**Sign out everywhere:** `POST /auth/logout/all` becomes "sign out of every browser". It calls Portiko's logout-all, and the back-channel logout clears the `rp_sessions` rows. The `SendSessionsRevoked` email goes away unless Portiko sends an equivalent.

**`/api/me`** keeps its response shape.

## Expected behavior

With Portiko on, an imported user goes from `/auth/portiko/login` to Portiko's sign-in at `/id/…`, uses their passkey, lands back signed in with their links, admin rights and API tokens intact, and is signed out by `POST /auth/logout`.

## Notes

- Integration test with `virtualwebauthn` covering the whole loop: import, sign in, `/api/me`, deactivate the user, then the next request gets 401 or 403.
- Rate limiting for sign-in moves to Portiko (`docs/rate-limits.md` in Portiko). Remove ShortLinks' login/register/recover limiters from the Portiko path.
- **Detecting a new account (from the #0129 work, agreed with the Portiko session):** Portiko sends the RP no signal that a sign-in created an account, and OIDC has no standard claim for it. `OnSignIn` treats "no `users` row for this `sub`, and none by verified email" as new. Make that step an atomic insert-if-absent (`INSERT … ON CONFLICT (subject) DO NOTHING RETURNING`, then re-select), or two concurrent first sign-ins race on the admin rule. "New" means new to ShortLinks, not new to Portiko; they differ only if one database is restored without the other. If that ever matters, the cleaner fix is an in-process `provider.Options.OnAccountCreated(ctx, sub, email)` hook beside `RegistrationPolicy` (not built).
- **Registration closed mid-flight:** Portiko re-asks `RegistrationPolicy` when the emailed code is verified, but not at the final passkey step, so one ceremony can still finish within the challenge TTL after an admin closes registration. Refuse unknown subjects in `OnSignIn` while `registrations_enabled` is false to close that gap.
- **Mounting (from #0128):** `mux.Handle("/id/", p.Handler())`, never `http.StripPrefix`. `rp.Config.Issuer` is `BASE_URL + "/id"`. The provider's SSO cookie is `accounts_sso` with `Path=/id`. The rp's own cookies stay at `Path=/`.
