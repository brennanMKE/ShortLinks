## Description

`AuthHandler` has no logger. All **seven** of its `http.StatusInternalServerError` branches (`internal/handlers/auth.go:106, 128, 195, 226, 250, 285, 309`) follow the same shape: take an `error` from the service layer, throw it away, and return a fixed `"internal server error"` string to the client.

```go
revoked, err := h.login.LogoutAll(r.Context(), u.ID, u.Email, clientIP(r))
if err != nil {
    writeError(w, http.StatusInternalServerError, "internal server error")
    return
}
```

The generic client response is correct — leaking internals to an unauthenticated caller would be worse. The problem is that the error is not written *anywhere else* either.

**The service layer does not cover this.** `LoginService.LogoutAll` (`internal/auth/login.go:340-385`) wraps and returns its failures — `begin logout-all tx`, `DeleteSessionsForUser`, the audit `WriteTx`, `commit logout-all tx` — without logging any of them. It logs exactly one thing, the fire-and-forget mailer failure (`login.go:381`), precisely because that path *cannot* propagate. So for a genuine database or transaction failure the error is constructed, wrapped with useful context, returned up one frame, and dropped. The operator sees a 500 in the access log and has nothing else: no failing query, no user id, no transaction stage.

This is the observability equivalent of the bug fixed in #0093, where `protocol.Error` `DevInfo` was discarded and made a login failure expensive to diagnose. Same shape: the information needed to explain the failure existed in the process and was thrown away.

## Why it is worth fixing now rather than at the next outage

These are the highest-value 500s in the codebase to have logged. The seven sites cover login, registration, recovery, logout, and sign-out-everywhere — the paths a user hits when they are already locked out and least able to describe what happened. A failed `LogoutAll` in particular is a security action: the user believes their sessions are gone, the transaction rolled back, and there is no server-side record of *why*.

`Logout` (`auth.go:226`) has the same gap and predates #0094, so this is a long-standing pattern rather than a regression from that issue — which is also why it will not fix itself.

## Scope / deliverables

- Add an `*slog.Logger` to `AuthHandler` and populate it in `NewAuthHandler` (`internal/handlers/auth.go:65-77`). **No handler in `internal/handlers` currently holds a logger**, so this establishes the pattern — pick the shape deliberately.
- **Decide where logging belongs before writing code.** Two defensible options; pick one and apply it consistently rather than doing both and double-logging:
  1. **Log in the handler.** One place per 500 branch, keeps services pure, and matches the fact that the handler is what decides the request failed. Costs a logger on every handler struct.
  2. **Log in the service.** `LoginService` already has `s.log` and already logs the mailer failure, so the plumbing exists; failures get logged with more local context (which stage of the transaction) closer to where they arose. Costs consistency with handlers that have no service behind them.

  The service-side option is the smaller diff and reuses an existing field; the handler-side option is uniform across all seven sites including ones whose services may not have a logger. State the choice in the resolution.
- Log at `Error` (these are genuine infrastructure failures, unlike the `Warn`-level mailer miss) with at minimum the wrapped `err` and the authenticated `user_id` where one is in scope.
- **Do not change any client-facing response.** The status codes and the `"internal server error"` body stay exactly as they are; this issue adds a server-side record only.
- Handle `NewAuthHandler`'s existing nil-dependency tolerance (its doc comment notes tests pass nil for unused services) — a nil logger must not panic. Default to `slog.Default()` or guard the call sites.

## Acceptance criteria

- [ ] Each of the seven 500 branches in `internal/handlers/auth.go` produces exactly one `Error`-level log line carrying the underlying error, with no duplicate emitted from the other layer.
- [ ] Log lines include the authenticated `user_id` on the routes where one is available (`Logout`, `LogoutAll`).
- [ ] A test asserts the log line for at least the `LogoutAll` failure path, captured through an `slog` buffer handler — `internal/auth/logout_all_test.go` already does this for the mailer warning (`TestLogoutAll_MailerErrorDoesNotFailOperation`), so reuse that harness.

- [ ] No secrets, tokens, session values, or full email addresses in the log output.
- [ ] `go build ./...`, `go vet ./...`, `gofmt -l` clean on touched files; `go test ./...` passes with the new test observed by name.

## Out of scope

- Adding loggers to the other handler types (`LinkHandler`, settings, admin, redirect). If the chosen pattern generalizes, file a separate issue to roll it out — doing it all here would make the diff unreviewable and mix a design decision with a mechanical sweep.
- Structured request IDs / correlation IDs linking the log line to the access-log entry. Genuinely useful and the natural next step, but it is a middleware concern and a larger design.
- Changing what the client receives on a 500, including any "reference id" surfaced to the user.
- Any change to the `Warn`-level mailer logging at `login.go:381`, which is already correct.

## Root cause

`AuthHandler` had no logger, so all seven of its `StatusInternalServerError` branches took an `error` from the service layer and dropped it. The service layer did not compensate: `RegistrationService` and `RecoveryService` have no logger at all, and `LoginService` returns every error on these paths without logging — its only log calls are `Warn`s in `FinishLogin` (which map to 401/403, not a 500) and the post-commit mailer `Warn`, reachable only on the success path. So a genuine database or transaction failure produced a 500 in the access log and no other record anywhere.

## Fix

**Decision: handler-side logging**, and the survey that drove it inverted the issue's own guess. The issue assumed service-side would be the smaller diff because `LoginService` already has `s.log`. It isn't: `RegistrationService` (`registration.go:37-52`) and `RecoveryService` (`recovery.go:30-40`) have no logger field and their constructors take none, and the dev counterparts (`devstore.DevRegistrar`, `DevRecoverer`, `devLoginService`) match. Service-side would have meant adding a field *and* a constructor parameter to two services plus their dev wiring just to cover 4 of the 7 sites. Handler-side is uniform and required no service changes. The reviewer re-ran the survey independently and confirmed every particular.

`AuthHandler` gained a `*slog.Logger`; `NewAuthHandler` takes it as a 4th parameter and nil-defaults to `slog.Default()`, honoring the constructor's documented nil-dependency tolerance. Seven `h.log.Error` calls, 1:1 with the seven `writeError` sites and each immediately preceding it. `LogoutAll` carries `user_id`; `Logout` carries `ip`. Responses are byte-identical — this adds a server-side record only.

**`Logout` deliberately does not log `user_id`.** The route is mounted bare at `main.go:297` (unauthenticated by design, so a stale cookie still clears cleanly), so no `AuthUser` is ever in context; and `Store.DeleteSession` returns `0` on its error path (`store.go:607-620` — the `RETURNING user_id` value is never scanned on failure), so widening the interface would surface nothing. The acceptance criterion's governing clause is "on the routes where one is available"; its parenthetical naming `Logout` was factually wrong. `clientIP(r)` is logged instead, since it is already passed into every service call on these routes and already persisted as `audit.Entry.IP`.

**The first implementation introduced a PII leak, caught in review.** `SESMailer` wrapped its errors as `fmt.Errorf("auth: sending email to %s: %w", toEmail, err)`, and `registration.go:111` / `recovery.go:106` return that error bare — so the new `Error` lines would have written full recipient addresses into the journal on an SMTP outage, from two unauthenticated endpoints, i.e. the most likely 500 those routes have. The old code avoided this only by accident, by discarding the error entirely. Fixed at the source: the recipient was dropped from the format string.

## Gotchas

- **Adding logging is a PII surface change.** Discarding an error hides whatever it embeds; logging it publishes that. Before wiring an error into a log line, read what the *deepest* frame interpolates — here, a mailer four frames down had put the recipient in the message, and two intermediate frames returned it bare. The routes that made this serious were the unauthenticated ones, where the leaked value is attacker-supplied.
- **pgx is safe here, and it is worth knowing why.** `PgError.Error()` deliberately excludes `Detail`, which is where Postgres puts `Key (email)=(alice@example.com) already exists.` on a unique violation — so a duplicate-email insert reaching `RegisterStart`'s 500 does not leak. `ConnectError` prints no password and `ParseConfigError` runs the conn string through `redactPW`. Do not assume this holds for other drivers.
- **A forbidden-substring assertion is worthless until a test case can trip it.** The first version listed two session tokens no fixture could produce in a log line. The guard only became real when a subtest injected an error genuinely carrying an address — the same lesson [#0096](0096.md) reached about its 401 assertions.
- **Counting log lines catches over-logging, which reading code does not.** The per-branch counter asserts exactly 1, so a future service that starts logging the same failure fails the test instead of silently double-writing. `slog.TextHandler` escapes newlines inside quoted values, so one record is always one line, and a hypothetical multi-line record would count >1 and fail — the counter errs safe.
- **The registration audit row carries no email.** `account.registration_started` is written pre-auth with only `Action` and `IP` — no `actor_id`, `user_id`, or `target_id`, and `audit.Entry` has no email field. The address lives in `pending_registrations` (written immediately before the send), so post-redaction recovery is a timestamp+IP correlation, not a join. The first version of the redaction comment claimed otherwise; corrected in `cfc4c0b`.

## Follow-ups

- **The repo has no request-logging middleware at all.** `internal/middleware/doc.go` claims the package "provides logging," but there is no access log — no method/path/status/duration line anywhere. These seven `Error` lines therefore have no request context to correlate against beyond the `ip` on one of them. Worth filing: an access log plus a request ID threaded into these lines would make them substantially more useful, and the issue's Notes above were written on the false assumption that one already existed.
