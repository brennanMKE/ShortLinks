# 0090 — E2E: admin URL filter rules

## Description

Automate the Admin ▸ URL filters surface: listing rules, creating a rule, the
"test a URL against the rules" tool, and editing a rule. Depends on
[#0080](0080.md); part of [#0079](0079.md).

## Scope / scenarios to automate

- **Filter list renders** (`GET /admin/url-filters`) — shows existing rules (or
  the empty state) with their pattern, action, and denial reason.
- **Create a rule** (`POST /admin/url-filters`) — add a rule (e.g. deny a host
  substring) → assert it appears in the list.
- **Test a URL** (`POST /admin/url-filters/test`) — enter a URL that matches the
  new rule → assert the tool reports a match/deny with the reason; enter a
  non-matching URL → assert allow.
- **Edit a rule** (`PATCH /admin/url-filters/{id}`) — toggle enabled/disabled or
  change the reason → assert it persists.
- **End-to-end deny on create (cross-check).** With a deny rule active, attempting
  to create a link whose destination matches it is blocked with the reason shown
  (ties to #0082). Assert the deny surfaces in the create form.

## Preconditions

- Fresh-seed dev server; `URLFiltersPage` page object. Note whether the dev store
  seeds any rules; if not, tests create their own.

## Acceptance criteria

- [ ] Filter list renders (rules or empty state).
- [ ] Creating a rule adds it to the list.
- [ ] The test-URL tool reports match/deny vs. allow correctly.
- [ ] Editing a rule persists.
- [ ] A link creation matching a deny rule is blocked with the reason (cross-check
      with #0082).

## Out of scope

- The redirect-time enforcement internals — assert the user-visible deny, not the
  cache/rule-engine internals (those have their own tests).

## Notes

- Filter rules + denial reasons live in the `filters` module with a Ristretto
  rule cache; the dev store uses a no-op evictor. Assert through the UI, not the
  cache.
