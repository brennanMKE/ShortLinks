## Description

Dev mode (`STORAGE=json`, `internal/devstore`) stubs out registration, login and recovery (`DevRegistrar`, `devLoginService`) and signs every request in through `DevAutoLogin`. That doesn't carry over once sign-in goes through Portiko. `scripts/dev.sh` and the planned E2E harness (#0080) need dev mode to keep working without Postgres or a real passkey.

## Long Description

**Options for the plan to choose between:**
1. Keep `DevAutoLogin` as the dev-mode sign-in and skip Portiko entirely in dev mode. This is the simplest, but the Portiko path never gets exercised locally.
2. Run the embedded provider in dev mode with Portiko's `DEV_INSECURE` setting, the stdout mailer and a local Postgres. This is realistic, but dev mode then needs a database.
3. Both: `DevAutoLogin` by default, and a `scripts/dev.sh --portiko` mode for testing the real flow.

Whatever is chosen, document it in `docs/dev.md`. The `devstore` stubs for the old ceremonies are deleted in #0136.

## Root cause

Dev mode (`STORAGE=json`) signs every request in through `DevAutoLogin`, and the real Portiko flow (#0132) is refused there (`PORTIKO_ENABLED` needs Postgres), so the redirect-based sign-in of #0133 could never be exercised locally.

## Fix

Option 3, without a database. `DevAutoLogin` stays the default. `DEV_PORTIKO=true` (`scripts/dev.sh --portiko`) replaces it with `devPortikoLogin`, which signs nobody in until the browser visits `GET /auth/portiko/login?return_to=<local path>`. That mints a dev session for the mock admin and redirects to a same-origin `return_to`, keeping a `#fragment`. `POST /auth/logout` is unchanged. `DEV_PORTIKO=true` without `STORAGE=json` stops startup, and `devPortikoLogin` panics outside dev mode, so it can't reach production. No migration, and no SPA change was needed. #0133 can use the same `/auth/portiko/login?return_to=` URL as it does with real Portiko. Documented in `docs/dev.md`.
