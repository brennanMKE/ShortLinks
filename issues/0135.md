## Description

Write and then carry out the cutover runbook for the three instances that share the binary. For each one: set the Portiko config, deploy, run `shortlinks portiko-import`, turn on `PORTIKO_ENABLED`, and confirm an existing user signs in with their existing passkey. Each instance keeps a rollback path (switch off, restart) until #0136 removes the old code. **Deploying happens only when Brennan explicitly asks.**

## Long Description

**Runbook (goes in `DEPLOYMENT.md`):**
1. **Pre-checks:**
   - #0127 has been in production long enough.
   - Per instance, count the credentials still missing a `user_handle`. Contact or plan for those users.
   - Take a database backup (`docs/backups.md`).
2. **Config:** set `PORTIKO_CRYPTO_KEY`, the client secret and the `rp` cookie key in each instance's `.env`, using `vim` on the server.
3. **Migrate:** run the ShortLinks migrations and start with the switch off. That creates the `portiko` schema.
4. **Import:** `shortlinks portiko-import --dry-run`, review the counts, then run it for real.
5. **Turn it on:** set `PORTIKO_ENABLED=true` and restart the service.
6. **Verify:**
   - Sign in with an existing passkey, the admin pages, an API token call, a `/u/{key}` redirect, the #0125 home page, sign out, and back-channel sign-out.
   - `/id/.well-known/openid-configuration` shows the right issuer.
7. **Rollback:** `PORTIKO_ENABLED=false` and restart. Old sessions in `sessions` still work, because #0136 hasn't dropped them yet.

Cut over one instance first (the lowest-traffic one), then the other two.

## Notes

- Users whose passkeys weren't imported see Portiko's sign-in. They recover with their email: a one-time code, then a new passkey attached to the same subject. Decide whether to email them beforehand.
- Deployment target and OS details are in `DEPLOYMENT.md`. The build is done on the Mac.
