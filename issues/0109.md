# 0109 — PATCH /api/links does not re-run the URL filter on a changed destination

| | |
|---|---|
| **Status** | open |
| **Module** | handlers / filters |
| **Platform** | All |
| **First seen** | 2026-08-07 |

## Description

`POST /api/links` runs the [#0024](0024.md) URL filter check at the top of `Create`, so a destination matching an active deny rule is rejected. **`PATCH /api/links/{key}` does not.** A link can therefore be created with a permitted destination and then edited to point at a denied one, and the filter never sees it.

The gap is pre-existing at the API layer — it predates the campaigns work — but [#0099](0099.md) shipped the first UI button that reaches it. Before #0099 the edit form did not exist, so the only way to hit this was a hand-crafted API call. Now it is two clicks.

## Why it matters

The filter's purpose is to stop the instance being used to shorten links to content the operator has ruled out. A control that only applies at creation is not a control — it is a speed bump for anyone who reads the API surface, and now not even that.

The rule cache (`cache.NewRuleCache`, 60s TTL, invalidated on admin mutation) is already wired into the handler for `Create`, so the check itself is available at the patch site; this is a missing call, not missing infrastructure.

## Scope / deliverables

- Run the same filter check in `Patch` whenever `destination_url` is present in the request body, using the same rule cache and the same denial-reason plumbing as `Create`.
- Match `Create`'s response shape and status code exactly on denial — a caller should not be able to tell which endpoint rejected it.
- Write the same audit entry `Create` writes on a filter denial, if it writes one. Check rather than assume; if it does not, decide deliberately whether a denied patch is worth recording and say which.
- **Decide and state what happens to links that already point at a now-denied destination.** Adding a rule does not retroactively check existing links. That is out of scope to *fix*, but the behavior should be written down rather than discovered.

## Acceptance criteria

- [ ] `PATCH` with a destination matching an active deny rule is rejected with the same status and body as `POST` would produce for that destination.
- [ ] `PATCH` that does **not** include `destination_url` skips the check entirely — patching only a title must not fail because the link's existing destination matches a rule added since creation.
- [ ] The check reads through the existing rule cache, not a fresh DB load per request.
- [ ] A rule added and then invalidated takes effect on the next patch without a restart.
- [ ] Ownership and existing patch behavior are unchanged for permitted destinations.
- [ ] A test asserts the create/patch parity directly — same destination, same rule, same outcome from both endpoints.
- [ ] `go build ./...`, `go vet ./...`, `gofmt -l` clean; `go test ./...` passes with new tests observed **by name**.

## Out of scope

- Retroactively scanning existing links when a rule is added.
- Any change to the rule format, the admin CRUD, or the cache TTL.
- The redirect-time check (if one exists) — this issue is about the write path.

## Notes

- `internal/handlers/links.go` — `Create` has the check; `Patch` does not. The rule cache is already a field on the handler.
- Worth checking whether `CreateOrReactivateLink`'s reactivate branch re-checks the filter. A link deactivated while permitted, then reactivated after a rule change, is the same class of gap.
