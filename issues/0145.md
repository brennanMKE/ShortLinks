## Description

`DELETE /api/links/{key}` deactivates a link, but `patchLinkRequest` (`internal/handlers/links.go:809-824`) has no `active` field and nothing else turns it back on. Accept `"active": true|false` on `PATCH /api/links/{key}`.

## Long Description

- `active: false` behaves exactly like `DELETE` (same audit action, same redirect-cache eviction).
- `active: true` reactivates the link. It re-runs the URL filter against the current destination, because rules may have changed since the link was made (see [#0109](0109.md)), and refuses with 422 `destination_denied` if it now fails. It evicts the cached redirect entry and writes a `link.reactivated` audit entry.
- Reactivating an already-active link is a no-op 200.
- Read-only tokens get 403 as with any write.

## Acceptance criteria

- Handler tests cover deactivate via PATCH, reactivate, the no-op, denial by a filter rule added after deactivation, cache eviction (a redirect works again immediately), audit entries, and read-only tokens.
- [docs/links.md](../docs/links.md) documents the field.
- `go test ./...` passes.

## Root cause

`DELETE /api/links/{key}` set `active = false`, and nothing could set it back. `patchLinkRequest` had no `active` field, and the only reactivation path was the dedup flow when creating a link with the same destination. That left no undo in the UI and no way for an agent to restore a link.

## Fix

`patchLinkRequest` gains `Active *bool`.

**Deactivate.** `active: false` and DELETE now share one `deactivate` helper, so the `link.deactivated` audit entry and the redirect-cache eviction are identical.

**Reactivate.** For `active: true` on an inactive link, the handler does these steps in order:

1. Reads the link.
2. Refuses links denied at creation (`denied_reason != 0`). The user makes a new link instead.
3. Runs the URL filter against the effective destination: the `destination_url` being sent, otherwise the current one. This happens **before** any field edit is written, so a refused request saves nothing and returns 422 `{"error":"destination_denied","reason","label"}`.
4. Applies the field edits.
5. Calls the new `links.Store.ReactivateLink`. Its `UPDATE` is scoped to the user and also requires `denied_reason = 0` and `destination_url` = the filtered destination. If the destination changed in between, it returns `ErrLinkChanged`, which maps to 409 `conflict`.
6. Evicts the cached redirect.
7. Writes `link.reactivated`.

**Other behaviour.**
- Reactivating an already-active link is a 200 no-op with no audit entry.
- `expires_at` is never changed.
- Read-only tokens get 403 from the existing middleware.
- `devstore` mirrors all of this.

The review fixes went into `fd6d359` on `issue/0145`: validate before writing, a real eviction round trip, the race guard and 409, a Postgres store test, and docs.

## Gotchas

- **#0109 is still open.** A plain PATCH that changes the destination of an *active* link still skips the URL filter. Only reactivation runs it.
- **Reactivation can create duplicates.** It doesn't check for them, so a user can end up with two active links to one URL. Custom aliases and batch creates could already cause that.
- **Repeated calls aren't symmetric in the audit log.** Repeating `active: false` writes another `link.deactivated` entry, as DELETE does. Repeating `active: true` writes nothing.
- **A narrow race can return 200 with `active: false`.** If the link was active at the pre-check but deactivated before the write, `{"active": true}` returns 200 with `active: false`. The response shows the real state.
- **No handler test for the 409.** It is only covered at the store level.
