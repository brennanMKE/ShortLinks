## Description

Expose every report from `internal/reports` as a typed MCP tool, plus `list_reports`, and add three MCP prompts for the questions Brennan asks most.

## Long Description

**Tools:** `list_reports`, `get_overview`, `get_top_content`, `get_top_links`, `get_breakdown`, `get_timeseries`, `get_movers`, `get_idle_links`, `compare_campaigns`, `get_campaign_performance`, `get_link_performance`. Each takes the shared parameters from #0139 as typed, described fields (an enum for `range`, an array of strings for each UTM filter, a `tz` string defaulting to the instance's `DEFAULT_TIMEZONE`) plus its report-specific ones. Each calls `internal/reports` directly; reports are read-only, so in-process HTTP dispatch isn't needed.

Results return `highlights` as the text content and the full envelope as structured content, so a model can answer from the text and read the data when it needs detail. Keep each tool description to one or two sentences that say **when** to use it ("Use for 'what content is getting the most clicks'…").

**Prompts:**

| Prompt | Arguments | What it asks the model to do |
|---|---|---|
| `weekly_summary` | `tz?` | Call `get_overview` and `get_movers` for the last 7 days and write a short summary: totals versus the previous week, the top three pieces of content, what's rising and what's gone quiet. |
| `campaign_report` | `slug` | Call `get_campaign_performance` and summarise which content won on which channel, with idle links. |
| `whats_working` | `range?` | Call `get_top_content` and `get_breakdown` by source and recommend where to post next. |

**Performance budget:** every report tool responds in under 300 ms for a user with 1,000 links and 100,000 clicks in the window, measured with a seeded test DB benchmark (`go test -bench`). If one doesn't, add the index it needs (for example `clicks (link_id, clicked_at)`) in a migration.

## Acceptance criteria

- Every registered report has a tool. A test fails if a report is added to the registry without a tool.
- MCP client round-trip tests call each tool and each prompt.
- The benchmark exists, and its result is recorded in the resolution notes.
- `go test ./...` passes.

## Root cause

The MCP server (#0149) exposed links and campaigns but none of the reports. Answering "what content is getting attention?" meant paging through links, and the overview report scanned the click window about 15 times.

## Fix

**Report tools.** The MCP server gains `list_reports` and one read-only tool per report:
- `get_overview`
- `get_top_content`, `get_top_links`
- `get_breakdown`, `get_timeseries`
- `get_movers`, `get_idle_links`, `compare_campaigns`
- `get_campaign_performance`, `get_link_performance`

How the tools behave:
- They call `reports.Service.Run` directly through `Options.Reports`.
- A `Spec.Refine` hook adds enums from the catalogue (`range`, `compare`, and each report's own params), date formats, and the `tz` default from `DEFAULT_TIMEZONE`.
- Refined schemas are cached per tool.
- Results contain the highlights, then a JSON mirror, then the full envelope as structured content.
- `ParamError` and `NotFoundError` map to tool errors that carry their code and field.
- In dev mode there is no reports service, so the tools return an error.

**Prompts.** `weekly_summary`, `campaign_report` and `whats_working`. They work for read-only tokens.

**Drift checks.** `TestEveryReportHasATool` checks both directions. Parity now maps `GET /api/reports*` to the tools. The MCP server has 28 tools and 3 prompts.

**Performance.**
- Overview runs as one scan of both windows. Per-row filter flags sit in a CTE, and `GROUPING SETS` produce totals, both day series, six facets (each ignoring only its own filter) and the campaign counts.
- Visitor-days is a hashed `SELECT DISTINCT`. Links-clicked is an `EXISTS` probe.
- `SET LOCAL work_mem = '32MB'`, inside the read-only report transaction.
- The referer breakdown counts per raw referer before applying the host regexp.
- Migration `000019` adds `idx_clicks_link_time ON clicks (link_id, clicked_at)`, built `CONCURRENTLY`. The down migration drops it concurrently.

**Benchmark.** It lives in `internal/reports/bench_test.go` and is gated by `SHORTLINKS_BENCH=1`. It seeds 1 user, 1,000 links, 100k clicks in the window and 50k before it, all in a throwaway schema `bench_0150` that is dropped afterwards.

| Report | ms |
|---|---|
| overview | 285–307 |
| overview with filters | 267–270 |
| overview, range=all (150k clicks) | 316–331 |
| breakdown by referer | 36–50 |
| timeseries | 66–125 |
| campaign-comparison | 67–79 |
| idle-links | 4.5–8.9 (was 1,357 before the index) |
| every other report | under 81 |

**Acceptance criterion waived (orchestrator, 2026-11-18).** Overview sits right at the 300 ms budget on a noisy dev Mac at the benchmark's volume. That is orders of magnitude more than production sees, so the budget is waived for overview. If it is ever needed, the next step is daily rollups or caching.

The review fixes went into `04f88bb` on `issue/0150`: `work_mem` 32MB, the forced parallel costs removed, the concurrent index, the schema cache, an equivalence test, and a dev-mode test.

## Gotchas

- **Deploy.** Migration `000019` must run on all five instances. It uses `CONCURRENTLY`, so each file holds exactly one statement and must not be wrapped in a transaction. The golang-migrate CLI runs it fine.
- **Follow-up.** `idx_clicks_link_id` is now a redundant prefix of `idx_clicks_link_time` and could be dropped.
- **Benchmark noise.** Timings vary a lot from run to run on a busy Mac, so compare runs on a quiet machine.
