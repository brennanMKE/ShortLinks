# 0178 — `/u/{key}` has no rate limit, so anyone can scan for live keys

| | |
|---|---|
| **Status** | in-progress |

| **First seen** | 2026-11-18 |

## Description

`GET /u/{key}` (`cmd/shortlinks/main.go:382`) is the only public route without a limiter. Register, login and recover all have one (`main.go:373-375`). Generated keys are 6 base-62 characters (`internal/links/keygen.go:14`), so a scanner can enumerate live short links. For a CoupleDozen invitation, a live link is a way into a family group.

## Long Description

Requested by the CommunityPlatform session on 2026-11-18, for CoupleDozen invitation links on the new go.coupledozen.com instance. Their plan is in CommunityPlatform `docs/Plans/2026-11-ShortInviteLinks.md`, with issues GroupsWeb #0274/#0275 and CommunityBackend #0108. Each invitation link carries a secret token that grants entry to a family group, so these links need more protection than marketing links.

**Wanted:**
- **Limiter split.** Add a per-IP limiter on `/u/{key}`, with **misses limited much more strictly than hits.** A poster scanned by 50 people behind one venue NAT must keep working, while a scanner that mostly hits unknown keys gets throttled. Use two buckets per IP:
  - all requests: generous, for example 120/minute;
  - 404 and 410 responses: strict, for example 20/minute with a burst of 10.
  
  When the miss bucket is empty, every `/u/*` request from that IP gets 429 with `Retry-After` until it refills, including keys that would have resolved.
- **Limits are configurable** through settings (`REDIRECT_RATE_PER_MIN`, `REDIRECT_MISS_RATE_PER_MIN`) with the defaults above. Document them in [docs/configuration.md](../docs/configuration.md).
- **Client IP behind Apache.** Use the same `clientIP` logic as the existing limiters (`internal/middleware/ratelimit.go:102`), and check that it reads the forwarded address behind Apache, not `127.0.0.1`. If it doesn't, fix it for every limiter and say so in the resolution notes.
- **429 clicks:** not recorded.
- **Memory:** limiter state per IP must be bounded, evicting idle entries, so a scan can't grow memory without limit.

## Acceptance criteria

- Handler tests cover: hits under the limit pass; many hits from one IP pass; misses exhaust the strict bucket and then all `/u/*` from that IP get 429 with `Retry-After`; other IPs are unaffected; idle entries are evicted.
- A test proves the forwarded client IP is used behind a loopback proxy.
- `go test ./...` passes.

## Root cause

`GET /u/{key}` was registered with no limiter, so a scanner could probe 6-character keys without limit. Separately, `clientIP` (middleware and redirect handler) used the **leftmost** `X-Forwarded-For` entry. Apache's mod_proxy appends the address it saw to whatever the client sent, so the leftmost entry is client-controlled: any per-IP limiter (including the existing register/login/recover ones) could be bypassed by sending a rotating fake `X-Forwarded-For`, and it also let a visitor pick the IP stored in click hashes.

## Fix

- `internal/middleware/redirectlimit.go`: `RedirectLimiter`, two in-memory token buckets per IP. All requests: 120/min (burst 120). Responses 404/410 charge a strict bucket: 20/min with burst 10. When the miss bucket is empty, every `/u/*` request from that IP gets 429 with `Retry-After` (even live keys) until it refills. 429s consume nothing and never reach the redirect handler, so no click is recorded. No DB work. Idle entries (2 min) are swept lazily, so memory is bounded by recently active IPs; an evicted entry equals a fresh one, so eviction grants no extra quota.
- `REDIRECT_RATE_PER_MIN` / `REDIRECT_MISS_RATE_PER_MIN` in `internal/config` (defaults 120/20, must be >= 1) and documented in `docs/configuration.md`. The `/u/{key}` route is wrapped in `buildMux` (3 lines in main.go).
- **Client IP fix (all limiters):** `clientIP` now uses the **last** `X-Forwarded-For` entry (the one Apache appended), only if it parses as an IP, else `RemoteAddr`. Applied to `internal/middleware/ratelimit.go` and `internal/handlers/redirect.go`; existing tests updated accordingly. Behind Apache the old code did read the forwarded address (not 127.0.0.1) but trusted the spoofable leftmost entry.

## Review round 1

- **Concurrent bypass fixed:** `admit` now reserves the miss token up front (and the general token); a response other than 404/410 refunds it. 100 parallel misses admit at most the burst (10); test `ConcurrentMissesBoundedByBurst`, run with `-race`.
- **IPv6** clients are keyed on their /64.
- **Hard cap** of 100,000 tracked IPs: at the cap, a forced sweep runs, then new IPs fail closed (429, `Retry-After: 60`) with one warning logged per episode; known IPs keep working. Test `EntryCapFailsClosed`.
- `X-Forwarded-For` is honoured only when `RemoteAddr` is loopback (middleware and redirect handler); test `IgnoresXFFFromNonLoopback`. Existing tests now use a loopback peer.
- Fixed the stale "first hop" comment in `redirect.go`.
- `docs/configuration.md` documents the CDN caveat and the shared-NAT lockout trade-off.
- Config rejects `REDIRECT_MISS_RATE_PER_MIN` > `REDIRECT_RATE_PER_MIN`.
- `issues/0178/curl.txt` regenerated without the session cookie.
- Merged `main` (#0184); the only conflict was in `internal/handlers/static_test.go` (kept main's additions).
- `go test -race ./internal/middleware ./internal/handlers ./internal/config` and `go test ./cmd/...` pass; no DB used.

## Review round 2

- **Cap evicts instead of refusing:** at 100,000 entries a new IP evicts one arbitrary entry (O(1) map iteration) and is admitted, so an address flood cannot lock out new visitors; one warning is logged per episode. The forced O(n) sweep is gone from the request path: idle entries are now swept by `RedirectLimiter.Run` (30s ticker, started from `buildMux`). Test `EntryCapEvicts`: 20 new IPs at a cap of 5 are all admitted and the entry count stays <= 5.
- `clientIP` returns the normalised `ip.String()` (also for `RemoteAddr`), so `::ffff:a.b.c.d` and `a.b.c.d` share a key.
- `docs/configuration.md` notes that more than about 10 requests in flight at once from one IP can get a 429, because a request holds its miss token until the response is known.
- `go test -race` on middleware, handlers, config and cmd passes.
