## Description

During #0132 verification, `go test -count=1 -p 1 ./...` on a fresh DB failed this timing assertion in `internal/clicks` once. The package passed on re-run. A flaky test erodes trust in the green baseline that every review relies on.

## Acceptance criteria

- Find the race. Either it's in the test (for example, timing-based expectations, or a snapshot taken outside the rollup's transaction) or it's a real inconsistency in `CampaignRollup` under concurrent writes. If it's a product bug, fix it in the code. Otherwise make the test deterministic.
- `go test -count=50 -run TestCampaignRollup_TimeseriesConsistentWithClickCountUnderConcurrentWrites ./internal/clicks/` passes on a fresh DB.

## Relation

- Found while verifying [#0132](0132.md).

## Root cause

`CampaignRollup` is not inconsistent: it reads the totals and timeseries inside one REPEATABLE READ read-only transaction (`beginCampaignReadTx`), and 50 runs never produced a mismatch. The flake was in the test:

1. The `iterations < 10` floor was a pacing assertion tied to a fixed wall-clock window, so CPU contention under `go test ./...` could trip it with no inconsistency.
2. The `truncate` helper had a 5s timeout. The post-burst cleanup truncate needs ACCESS EXCLUSIVE on `clicks`, and it can queue behind autovacuum or analyze of the table the burst just bloated. One of the 50 runs failed with `truncate: context deadline exceeded`. This is the likely cause, but the lock queue was not directly observed.

## Fix

- The read loop now runs until the window has elapsed and at least 10 iterations are done, with a 60s hard cap.
- The `truncate` timeout goes from 5s to 60s.
- No production code changed.

## Verification

- On a fresh private DB, `go test -count=50 -run TestCampaignRollup_TimeseriesConsistentWithClickCountUnderConcurrentWrites ./internal/clicks/` passed twice in a row after the fix.
- Before the fix, one run in 50 failed (truncate timeout).
- `go test -p 1 ./internal/clicks/ ./internal/handlers/` passes.
