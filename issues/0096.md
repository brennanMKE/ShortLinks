## Description

#0094's headline behavioral claim is that "sign out everywhere" also signs out the iPhone app. Nothing asserts it. The 13 tests added in #0094 drive `POST /auth/logout/all` exclusively through the `shortlinks_session` **cookie**; not one sets an `Authorization: Bearer <token>` header, so the native-client transport that motivated half the issue's copy is entirely uncovered.

The claim is correct today by construction, which is exactly why the gap is easy to leave open:

- `middleware.sessionToken` (`internal/middleware/auth.go:23-33`) prefers a well-formed `Authorization: Bearer <token>` header and falls back to the cookie. Both transports carry the **same** opaque token.
- `Store.DeleteSessionsForUser` issues `DELETE FROM sessions WHERE user_id = $1`, which is transport-agnostic — it cannot distinguish a row created for a browser from one a native client is using.

So the behavior follows from two facts in two different packages, neither of which is pinned by a test that says "a Bearer-authenticated session is revoked too." A change to either — a `device_type` column with a filtered delete, a separate native-token table, a `sessionToken` rewrite — would silently break the promise the Account UI makes to users, and the whole existing suite would stay green.

## Why this matters more than a typical coverage gap

The copy in `Account.svelte` tells the user their iPhone will be signed out. A user reaching for this button has usually lost a device. If the guarantee quietly stops holding, they believe a device is locked out when it is not — the same class of failure as the bug the #0094 review caught in the frontend (a failed revoke that rendered as success), just with a longer fuse.

## Scope / deliverables

- Add a Bearer-transport variant of `TestLogoutAll_HTTP_RevokesAllSessionsAndClearsCookie` in `internal/handlers/logout_all_test.go`. Seed a user with **two** sessions, authenticate the revoke request with `Authorization: Bearer <token>` and **no** cookie, and assert the account ends with zero sessions.
- Assert the reverse pairing too: a session created and used via Bearer is revoked when the request is authenticated by **cookie**. This is the direction that actually encodes "everywhere" — one transport killing the other's session.
- Assert a follow-up request carrying the old Bearer token is rejected (401), mirroring the existing cookie-token assertion.
- Consider a table test over `{cookie, bearer}` × `{cookie, bearer}` rather than four near-duplicate functions; the existing test's setup helpers should carry over.

## Acceptance criteria

- [ ] A revoke authenticated **only** by `Authorization: Bearer` succeeds and leaves the account with zero sessions.
- [ ] A session established via Bearer is revoked by a cookie-authenticated revoke, and vice versa.
- [ ] The old Bearer token is rejected on the next request.
- [ ] Another user's sessions remain untouched in the Bearer case (the existing cookie test already asserts this; do not lose it in a refactor).
- [ ] New tests are observed **by name** in the `go test ./...` output against the live `shortlinks_test` database — not merely compiled.
- [ ] `go build ./...`, `go vet ./...` clean.

## Out of scope

- Distinguishing native from browser sessions in the schema or the UI. The `sessions` table has no `user_agent`, IP, or device column (#0094's out-of-scope list), and adding one is a separate design decision.
- Selective revocation ("sign out my phone but not my Mac"). That needs the labelled session list #0094 explicitly deferred.
- Any change to `middleware.sessionToken` itself. This issue pins existing behavior; it does not modify it.

## Notes

- `internal/handlers/logout_all_test.go` already builds authenticated requests through the real `RequireSession` guard, so the Bearer variant should be a header swap in the request construction rather than new scaffolding.
- `sessionToken` deliberately falls through to the cookie on a *malformed* Authorization header (wrong scheme, empty token). A test for that fallback would be a reasonable bonus but belongs to #0077's surface, not this one.
- The reviewer on #0094 flagged this as non-blocking and noted the behavior is correct by construction — this issue is about pinning it, not fixing a defect.

## Root cause

Not a defect — a coverage gap. #0094 shipped the endpoint and the UI copy promising that "sign out everywhere" also signs out the iPhone app, but every one of its 13 tests authenticated through the `shortlinks_session` cookie. The promise held only by construction, across two packages, with nothing asserting it.

## Fix

Test-only; **no production file was touched**. Added `TestLogoutAll_HTTP_Transports` to `internal/handlers/logout_all_test.go`: a table test over `{cookie, bearer}` × `{cookie, bearer}` (revoke transport × check transport). Each of the four subtests seeds Alice with two live sessions plus a second account (Bob), authenticates the revoke with session 1's token over `revokeTransport`, then replays session 2's token over `checkTransport` on the very next request and requires a 401. Each subtest also re-asserts the full set from the original cookie test: 200 with `revoked_count=2`, the clearing cookie, zero remaining sessions for Alice, Bob's session untouched, the notification email, and the `session.revoked_all` audit row.

The only new scaffolding is a `transport` enum and `authenticateVia(req, transport, token)`, which either delegates to the existing `withCookie` helper or sets `Authorization: Bearer <token>` — a header swap, as the issue specified. The original `TestLogoutAll_HTTP_RevokesAllSessionsAndClearsCookie` was left byte-identical (the diff is 160 insertions, **0 deletions**), so the `cookie/cookie` row is deliberate redundancy rather than a refactor that could silently drop an assertion.

## Verification

`go build ./...`, `go vet ./...` clean; `gofmt -l` clean on the touched file. All four subtests observed by name and passing under `-race` against the live `shortlinks_test` database: `TestLogoutAll_HTTP_Transports/revoke=cookie/check=cookie`, `.../revoke=cookie/check=bearer`, `.../revoke=bearer/check=cookie`, `.../revoke=bearer/check=bearer`. Full `go test ./... -race -count=1` green apart from the pre-existing `internal/config` `TestLoad_DefaultsApplied` failure, confirmed identical on `main` via a throwaway worktree.

**Both sides ran mutation checks, and the reviewer's was the one that settled it.** The implementer disabled the Bearer branch in `sessionToken` and saw the two `revoke=bearer` subtests fail, but reported honestly that `revoke=cookie/check=bearer` still passed. The reviewer designed a sharper break — rewriting `DeleteSessionsForUser` to delete only the *oldest* session while still returning the full count, so `revoked_count` stayed green and only genuine revocation assertions could fire. **All four subtests failed**, each at the 401 replay assertion. Critically, that break also produced the missing positive control: with the session still live, the Bearer replay returned **200**, proving the baseline 401 means "revoked" rather than "Bearer never authenticated." ## Gotchas

- **A 401 is a weak assertion without a positive control.** `revoke=cookie/check=bearer` asserts that replaying a revoked token over Bearer yields 401 — but a 401 also arrives when the header is malformed, when the token was never valid, or when a guard rejects before session lookup. Only by breaking revocation *while leaving the session live* and observing a **200** does the 401 become evidence of anything. The lesson generalizes: any test whose success condition is an error response needs a demonstrated path to the success response, or it can pass for the wrong reason forever.
- **Mutation testing has to isolate the dimension under test.** Disabling the whole Bearer branch makes every Bearer request 401 regardless of revocation, so it cannot distinguish the two failure modes. The break that worked kept the transport intact and broke only the delete — and it deliberately preserved the returned count so a `revoked_count` assertion could not mask the result.
- **The subtests share a truncation.** `credsTestPool(t)` is called once at the parent level, so rows accumulate across table iterations. It is safe today only because each seed is indexed by `i` and each assertion is scoped to a specific user id — the isolation is incidental, not enforced.
- **`lastAuditFor` selects `ORDER BY id DESC LIMIT 1` globally for the action.** The audit assertion is correct only because subtests run sequentially and each writes exactly one `session.revoked_all` row. Adding `t.Parallel()` later would silently assert against another subtest's row.
