# 0091 — E2E: real-time updates (SSE)

|---|---|

## Description

Automate the real-time update path: the SPA subscribes to `GET /api/events` (SSE)
and live-updates the dashboard when links change. Depends on [#0080](0080.md);
part of [#0079](0079.md).

## Scope / scenarios to automate

- **SSE connection established.** On loading the Dashboard, the SPA opens the
  events stream (`GET /api/events`) and stays connected. Assert the connection is
  live (e.g. an observable "connected" state, or that a subsequent broadcast
  arrives).
- **Live create reflects without reload.** Create a link **out of band** (a second
  API call / second Safari context / direct `POST /api/links`) → assert the first
  Dashboard's link list updates **without a manual reload**, driven by the SSE
  broadcast.
- **Live delete reflects without reload.** Deleting a link out of band removes its
  row live.
- **Reconnect (best-effort).** If the stream drops, the SPA reconnects and resumes
  receiving events. Assert if feasible; otherwise document as manual.

## Preconditions

- Fresh-seed dev server. A way to mutate links **out of band** relative to the
  observed tab — e.g. a direct authenticated `POST /api/links` from the harness
  (reusing the dev auto-login), or a second driver context. Because only one
  safaridriver session runs at a time, prefer the **out-of-band API call** over a
  second browser to trigger the broadcast.

## Acceptance criteria

- [ ] SSE stream connects on Dashboard load (asserted).
- [ ] An out-of-band create appears in the list live (no reload).
- [ ] An out-of-band delete removes the row live (no reload).
- [ ] Reconnect behavior asserted or documented.

## Out of scope

- SSE broker internals / fan-out correctness — `events` package + `events.test.ts`
  own that; this issue asserts the user-visible live update.

## Notes

- The broker is shared across dev and prod wiring (`NewEventsHandler(broker)`),
  and links mutations publish to it (`linksH … broker …`). Triggering a mutation
  via the API from the harness is the cleanest way to produce a broadcast for the
  single observed Safari session.
- Single-session constraint (see #0080) is why the trigger should be an API call,
  not a second browser tab under a separate driver.
