## Description

Automate the Admin ▸ Users surface: listing users, viewing a user, and the
deactivate / reactivate actions. Depends on [#0080](0080.md); part of
[#0079](0079.md).

## Scope / scenarios to automate

- **User list renders** (`GET /admin/users`) — at minimum the seed mock admin
  appears with its email, admin flag, and active status.
- **User detail** (`GET /admin/users/{id}`) — opening a user shows their details
  (link count, passkey count, timestamps). Passkey count is 0 in dev (stub) —
  assert accordingly.
- **Deactivate** (`POST /admin/users/{id}/deactivate`) — deactivating a user
  flips their status to inactive in the UI and persists.
- **Reactivate** (`POST /admin/users/{id}/reactivate`) — reactivating restores
  active status.
- **Self-deactivation guard (if present).** If the app prevents an admin from
  deactivating their own only-admin account, assert that guard; otherwise note it
  isn't enforced and cover via handler tests.

## Preconditions

- Fresh-seed dev server. Ideally more than one user so deactivate/reactivate can
  target a non-admin. If the dev store seeds only the mock admin, either seed an
  extra user via a harness hook or operate on the admin and restore state, and
  document the choice.

## Acceptance criteria

- [ ] User list renders with the seed admin.
- [ ] User detail renders (passkey count 0 in dev).
- [ ] Deactivate flips status and persists.
- [ ] Reactivate restores status.

## Out of scope

- Settings / registration gate — #0087.
- Audit entries for user actions — #0089 (disabled in dev).

## Notes

- If only the admin exists in the seed, deactivating it could lock the session —
  prefer seeding a throwaway user for the deactivate/reactivate assertions, or run
  them last with a server restart to reset.
