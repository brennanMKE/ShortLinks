## Description

The production PostgreSQL database (AWS EC2, Amazon Linux 2023) has **no backup
system**. A single EBS failure, an accidental `DROP`, a bad migration, or
instance termination would lose all data — links, click analytics, the audit
log, WebAuthn credentials, and sessions — with no recovery path.

Add an automated **nightly logical backup** on the EC2 host, scheduled via
`crontab`, writing a compressed, transactionally-consistent dump to local disk
with daily rotation. A home **Mac mini pulls** the backups over `rsync`-over-SSH
on its own schedule, giving an offsite copy that survives loss of the EC2
instance.

This is the smallest reliable first step toward a real backup/restore story; S3
offsite and point-in-time recovery (WAL archiving) are noted as out of scope
below.

## Motivation

The site is live and accumulating data that cannot be regenerated (click
history, audit trail, user passkey registrations). Right now the recovery time
objective and recovery point objective are both effectively infinite — any loss
is total. A nightly dump caps data loss at ≤24h and makes restore a routine
operation.

## Proposed approach

The user's proposed shape — nightly cron on AL2023, compressed files on disk,
Mac mini downloads via `rsync` — is sound and adopted. One correction and a few
hardening details:

### Use `pg_dump`, not `tar` of the data directory

A `tar` (or `tar.gz`) of the live `PGDATA` directory is **not crash-consistent**
— it captures the cluster mid-write and a restore from it can fail. Use a
logical dump instead, which is transactionally consistent by design:

```bash
# Custom format (-Fc): already compressed, supports selective/parallel restore
pg_dump -Fc shortlinks > shortlinks-YYYYMMDD.dump

# OR plain SQL piped through gzip, if a human-readable .sql.gz is preferred
pg_dump shortlinks | gzip > shortlinks-YYYYMMDD.sql.gz
```

Recommend the custom format (`-Fc`) restored with `pg_restore`; it's compact and
flexible. (`.sql.gz` is the closest match to the originally-imagined "`.tar.gz`"
and is fine too — just less flexible to restore.)

### Backup script (`/usr/local/bin/pg-backup.sh`)

- `set -euo pipefail`; run as the `postgres` OS user (or a role with a `.pgpass`)
  so no password lands in cron.
- **Atomic write:** dump to a `*.tmp` file and `mv` to the final name only on
  success, so the Mac mini's rsync never grabs a half-written file.
- **Rotation:** after a successful dump, prune dumps older than N days
  (e.g. keep 14): `find "$DEST" -name 'shortlinks-*.dump' -mtime +14 -delete`.
- Write to a dedicated dir, e.g. `/var/backups/postgres/`, owned by `postgres`.
- Log to `/var/log/pg-backup.log` (or journal) and exit non-zero on failure.

### Scheduling (cron)

`crontab -u postgres -e` — nightly at a low-traffic hour, e.g.:

```cron
30 7 * * *  /usr/local/bin/pg-backup.sh   # 07:30 UTC nightly
```

(Pick the UTC time that maps to local off-peak.)

### Offsite pull from the Mac mini

Mac mini pulls over SSH (no Mac credentials ever stored on EC2 — an instance
compromise can't reach the offsite copy):

```bash
# On the Mac mini, via launchd or cron, after the EC2 backup window:
rsync -avz --delete-after \
  ec2-user@<host>:/var/backups/postgres/ \
  ~/Backups/shortlinks-pg/
```

Use a dedicated SSH key restricted to the backup path. The pull schedule should
run a bit after the EC2 dump completes.

### Hardening / verification

- **Encryption-at-rest decision:** dumps contain session tokens, WebAuthn
  credentials, and the full audit log. Transport is already protected by SSH;
  decide whether the files themselves should be encrypted (e.g. `age` or `gpg`)
  on disk and at rest on the Mac mini. At minimum, lock down directory perms
  (`0700`, owner `postgres`).
- **Restore drill:** periodically `pg_restore` a dump into a scratch database to
  prove the backups are actually restorable — an unverified backup is a guess.
- **Failure alerting:** a silently-failing cron job is worse than none. Alert
  (email / healthcheck ping) if a night's dump is missing or the script exits
  non-zero.

## Acceptance criteria

- [ ] A backup script exists on the EC2 host that produces a consistent,
      compressed `pg_dump` of the `shortlinks` database to local disk.
- [ ] The script writes atomically (temp file + rename) and prunes dumps older
      than the chosen retention window.
- [ ] A `crontab` entry runs the script nightly at an off-peak time.
- [ ] The Mac mini pulls the backup directory via `rsync`-over-SSH on a schedule,
      producing an offsite copy.
- [ ] A documented restore procedure (`pg_restore` / `gunzip | psql`) exists and
      has been exercised at least once against a scratch database.
- [ ] Backup failures surface somewhere the operator will notice (log + alert).

## Out of scope

- **Point-in-time recovery / WAL archiving** (`archive_command`, base backups,
  `pg_basebackup`) — a heavier setup for ≤seconds RPO; revisit if nightly
  granularity proves insufficient.
- **S3 (or other cloud) offsite** as a second destination — easy to add later
  alongside the Mac mini pull; the Mac mini copy satisfies the immediate offsite
  need.
- **Managed database migration** (e.g. RDS with automated snapshots) — a larger
  architectural change, not this issue.

## Notes

- Verify `pg_dump` / `pg_restore` are installed on AL2023 (they ship with the
  `postgresqlNN` packages; confirm the client version matches the server).
- Confirm the DB connection details the script should use (local socket vs.
  TCP, role, `.pgpass`) against the production `.env` / config.
- The Mac mini side can use `launchd` (preferred on macOS) or `cron`; either is
  fine for the pull.

## Root cause

Not a bug — a missing capability. Production had no backup system at all: a
single EBS failure, accidental `DROP`, bad migration, or instance termination
would lose all data with no recovery path (RPO/RTO effectively infinite).

## Fix

Added three shell scripts under `scripts/db/` plus documentation, following the
project's existing conventions (`set -euo pipefail`, `sudo -u postgres` peer
auth as in `db-status.sh`, `.env` parsed not sourced):

- **`backup.sh`** — nightly logical backup. Dumps one or more databases with
  `pg_dump` into a **common backup root** (`$BACKUP_ROOT/<db>/`, default
  `/var/backups/postgres/`), so a single rsync mirrors every database and new
  databases appear as new subfolders with no script change (the multi-DB design
  the user asked for). Default format is custom (`-Fc` → `.dump`); `plain` yields
  `.sql.gz`. Writes to a `*.tmp` file and atomically renames on success (rsync
  never sees a partial file), maintains a `<db>-latest.<ext>` relative symlink,
  prunes dumps older than `BACKUP_RETENTION_DAYS` (default 14) **only after a
  successful fresh dump** (so the only copy can't be pruned), sets `0700` dirs /
  `0600` files, and exits non-zero if any database fails so cron/monitoring can
  alert. Databases resolve from positional args → `BACKUP_DATABASES` → the `.env`
  `DATABASE_URL`. Runs `pg_dump` as `postgres` via sudo on the server;
  `BACKUP_RUN_AS` disables sudo for local dev.
- **`pull-backups.sh`** — runs on the Mac mini, `rsync`-over-SSH mirroring the
  whole root offsite (`--delete-after`, `--partial`). Pull model: the server
  holds no Mac credentials, so an instance compromise can't reach the offsite
  copy.
- **`restore.sh`** — restores `.dump` (via `pg_restore --clean --if-exists`) or
  `.sql.gz` (via `gunzip | psql`) into a target database; used for restore
  drills and real recovery.
- **`docs/backups.md`** — full operator guide (server setup, cron entry, Mac
  mini launchd/cron pull, restore drill + real recovery, failure alerting,
  encryption-at-rest note), wired into `docs/README.md` and `scripts/db/README.md`.

Used `pg_dump` (transactionally consistent) rather than a `tar` of `PGDATA`,
which is not crash-consistent — as flagged in the proposed approach.

## Verification

All run end-to-end against local PostgreSQL 16.14 (not just compiled):

- `shellcheck` clean on all three scripts (installed via Homebrew for this).
- **Backup:** dumped `shortlinks` and `shortlinks_test` into the common root;
  confirmed `0600` dumps in `0700` per-db dirs and a working relative
  `*-latest.dump` symlink (`readlink`).
- **Restore drill:** `restore.sh` with `RESTORE_CREATE=1` restored the latest
  dump into a scratch DB — all 11 tables present, row counts matched source
  (`users` 1=1, `links` 1=1, `passkey_credentials`/`audit_log` 0=0). Scratch DB
  dropped after.
- **Rotation:** a planted 20-day-old dump was pruned while the fresh dump
  survived (`BACKUP_RETENTION_DAYS=14`).
- **Failure path:** backing up a non-existent database exits `1`, removes the
  empty `*.tmp`, and leaves prior backups untouched (no prune).
- **Plain format:** `BACKUP_FORMAT=plain` produced a valid `.sql.gz`
  (`gunzip -t` OK) that restored 11 tables.

## Gotchas

- `"${arr[@]}"` on an **empty** array trips `set -u` on macOS's bash 3.2
  (`unbound variable`) — end-to-end testing caught this on the first run. EC2's
  bash 5.x is unaffected, but the portable fix `${arr[@]+"${arr[@]}"}` is used so
  the same script is safe on both. This is exactly the class of bug a
  compile-only check would miss.
- Pruning must run **after** the fresh dump lands (age 0), never before — that's
  what guarantees rotation can't delete the last remaining copy if a night's dump
  fails.

## Deployment note (not code — for when this is put into service on EC2)

The scripts are committed but not yet installed on the server. To activate:
create `/var/backups/postgres` owned by `postgres`, add the postgres-user crontab
entry (see `docs/backups.md`), and set up the Mac mini launchd/cron pull with a
dedicated SSH key. A restore drill on the server is worth doing once after setup.
