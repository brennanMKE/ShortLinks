# 0095 — UTM builder fields give no usable guidance on what typical values look like

| | |
|---|---|
| **Status** | open |
| **Module** | web |
| **Platform** | All |
| **First seen** | 2026-08-06 |

## Description

The five UTM fields in the "Campaign / UTM parameters" section of the create form (`web/src/views/Dashboard.svelte:419-470`) do not tell the user what to put in them. Someone who has not memorized the Google Analytics conventions cannot tell what distinguishes `utm_source` from `utm_medium`, whether values should be lowercase, hyphenated or underscored, or when `utm_term` and `utm_content` are worth filling in at all. The result is inconsistent tagging, which fragments the #0049/#0030 UTM breakdown on `LinkDetail` — `Newsletter`, `newsletter`, and `news-letter` become three separate bars for one channel.

Placeholders *are* present today, but they are doing very little work:

| Field | Current placeholder |
|---|---|
| Source | `e.g. newsletter, google, twitter` |
| Medium | `e.g. email, cpc, social` |
| Campaign | `e.g. spring-launch, black-friday` |
| Term | `e.g. running+shoes` |
| Content | `e.g. hero-cta, sidebar-link` |

Three problems with relying on these alone:

1. **They vanish the moment the user types.** The guidance is gone exactly when the user is second-guessing the value they just entered.
2. **They truncate.** Three comma-separated examples plus an `e.g. ` prefix does not fit an input at mobile widths; the user sees `e.g. newsletter, goo…`.
3. **They show values but not meaning.** Knowing that `cpc` is a valid medium does not tell you that medium answers "what *kind* of traffic is this", nor that source and medium are the pair analytics tools actually group on. `e.g. running+shoes` for Term is the least helpful of the five — it never explains that the field is for paid-search keywords and is normally left blank.

## What the typical values actually are

The five parameters split into three tiers of usage, which the UI should reflect rather than presenting all five as peers.

**`utm_source` — *where* the traffic comes from.** The specific named property or product. Almost always a proper noun lowercased.

> `newsletter`, `google`, `bing`, `twitter`, `x`, `linkedin`, `facebook`, `instagram`, `youtube`, `reddit`, `github`, `hackernews`, `producthunt`, `mastodon`, `podcast`, `partner-blog`, `qr-code`, `docs`

**`utm_medium` — *how* the traffic arrives.** The channel category. This is a small, closed vocabulary in practice, and keeping it small is the whole point — it is the field that makes cross-source comparison possible.

> `email`, `social`, `cpc` (paid search), `paid-social`, `organic`, `referral`, `display` (banners), `affiliate`, `sms`, `push`, `qr`, `print`

**`utm_campaign` — *why*, i.e. which initiative.** A slug naming the campaign, ideally with a date or version so a repeat of the same campaign next quarter stays distinguishable.

> `spring-launch`, `black-friday-2026`, `q3-webinar`, `product-hunt-launch`, `v2-announcement`, `onboarding-drip-3`

**`utm_term` — paid-search keyword. Usually blank.** Only meaningful for paid search ads where the keyword bid on is worth recording, and even then most ad platforms auto-populate it. Values are the keyword itself: `running+shoes`, `url+shortener`, `self+hosted+analytics`.

**`utm_content` — which *specific* creative or placement within one campaign.** The A/B and placement discriminator; the only field where two links in the same campaign are expected to differ.

> `hero-cta`, `footer-link`, `sidebar-banner`, `variant-a` / `variant-b`, `text-link`, `image-link`, `week1-email`

**Formatting conventions worth stating in the UI**, because they are the source of the fragmentation problem:

- Values are **case-sensitive** to most analytics tools — `Email` and `email` are different buckets. Lowercase everything.
- Use hyphens, not spaces or underscores (`black-friday`, not `Black Friday`).
- No PII, no internal identifiers. These are visible in the browser address bar and in referrer headers.
- Source + medium is the pair that gets grouped on. Keep medium to a short reusable list; let source be specific.

## Scope / deliverables

> **Scope grew: [#0099](0099.md) shipped a second UTM builder.** The edit form in `LinkDetail.svelte` now has its own copy of the five fields, and a campaign `<select>` sits above the builder in `Dashboard.svelte`. So this issue covers **three surfaces**, not one: the create builder, the edit builder, and the campaign selector's copy. The edit builder currently ships with bare labels and no guidance at all. Whatever form the guidance takes, it must not be written twice — extract it so the two builders share it, or the next change to a field's hint text will update one and miss the other.

- **Rewrite the five placeholders** to be single, canonical, non-truncating examples rather than comma-separated lists — the placeholder shows *shape*, not the full menu (e.g. Source → `newsletter`, Medium → `email`, Campaign → `spring-launch-2026`, Content → `hero-cta`). Drop the `e.g. ` prefix; it costs six characters of a field that is already too narrow.
- **Add persistent hint text under each field** carrying the one-line meaning plus 3–4 typical values. This is the part that survives the user typing, and is where the source-vs-medium distinction gets explained. Style it with the #0052 design-system faint-text token — `.text-faint` is already used for the `(utm_source)` key annotations at `Dashboard.svelte:422`.
- **Mark Term and Content as optional in a way that says why**, not just `(optional)` as today (`Dashboard.svelte:452`, `:462`). Term in particular should say "paid search keyword — usually blank" so users stop guessing at it.
- **Consider a "conventions" line** at the top of the expanded section covering lowercase + hyphens + no PII, once rather than five times.
- Verify the expanded section still lays out correctly at 375px with the added hint text, and that the added text does not push the live destination preview (`Dashboard.svelte:472-477`) below the fold on a phone.

## Acceptance criteria

- [ ] Each of the five inputs has a placeholder that fits without truncation at 375px viewport width.
- [ ] Each of the five fields has persistent guidance visible while the field has a value typed into it.
- [ ] The guidance states the source/medium distinction explicitly, and marks `utm_term` as normally blank.
- [ ] Casing/hyphenation convention appears at least once in the UI.
- [ ] No change to `web/src/lib/utm.ts` composition behavior — this is presentation only, and the existing `utm.test.ts` suite must pass untouched.
- [ ] `cd web && npm run build` clean; `npm test` passes with existing tests observed in the run output.

## Out of scope

- **Validating or normalizing values** (auto-lowercasing, rejecting spaces, warning on `Email` vs `email`). Reasonable follow-up, but it changes submitted data rather than just explaining it, and it needs a decision on whether normalization is silent or a prompt. File separately if wanted.
- **A dropdown or datalist of known mediums.** Would enforce the closed vocabulary properly, but is a larger interaction change than adding hint text; the small closed set for medium makes it the obvious candidate if this is revisited.
- **Suggesting values from previously created links** (e.g. autocomplete from existing campaigns on the account). Needs an API to surface distinct prior UTM values, which the baked-into-`destination_url` storage decision from #0048 makes awkward — the values are not stored discretely.
- The link edit path. Per #0048's storage decision, UTM values are baked into `destination_url` and cannot be re-populated into discrete fields on edit, so there is no second set of UTM inputs to update.

## Notes

- All five inputs live in one block at `web/src/views/Dashboard.svelte:419-470`; each is a `.field` wrapper with a `<label>` whose key annotation already uses `<span class="text-faint">`. Adding a sibling hint element per field follows the existing structure directly.
- The `utm-fields` container styles start at `Dashboard.svelte:840`; the mobile breakpoint work for this section came from the #0052 design-system pass, so check that file's media queries before adding new vertical spacing.
- Fragmentation is not hypothetical for this project: the UTM breakdown on `LinkDetail` buckets on raw string equality (`web/src/lib/charts.ts` via `utmDimensions`), so casing variants are already silently splitting into separate bars.
