# 0114 — The links table overflows between 900px and ~944px, below the documented invariant floor

| | |
|---|---|
| **Status** | open |
| **Module** | web |
| **Platform** | All |
| **First seen** | 2026-08-08 |

## Description

`docs/campaigns.md` states [#0103](0103.md)'s zero-horizontal-scroll invariant as holding at **every width ≥900px** — 900px being the breakpoint below which the links table degrades to the stacked-card layout. It does not hold at the bottom of that range.

Measured at **901px**: `.table-scroll` is **910 / 867** — 43px of overflow, with the Remove button 31.42px outside the container and an in-container horizontal scrollbar across roughly the **901–944px** band. That band is exactly the panning [#0103](0103.md) raised the breakpoint to eliminate.

The invariant has in practice only ever been verified at 1024, 1280, 1440, and 1920. The `≥900px` phrasing was never measured at its own lower bound.

## Why this matters

Not because the band is common — it is a narrow window most users never sit in — but because **the documented invariant is what every future column addition is checked against.** [#0106](0106.md) took five review rounds precisely because the invariant kept being verified in a way that didn't mean what it claimed (first against thin data, then against a `scrollWidth` threshold rather than min-content). A stated floor of 900px that fails at 901px is the same class of problem one level up: the next person adds a column, measures at 1024+, sees green, and ships.

## Scope / deliverables

Decide between two fixes and state which and why:

- **Move the stacked-card breakpoint up** to wherever the table genuinely fits (~944px on current geometry), so the documented floor becomes true.
- **Recover the ~43px** so the table actually fits at 901px.

The first is almost certainly correct — the table has no slack to give (see below) and the cards render well — but it is a real behavioural change for viewports in that band and should be a decision, not a side effect.

Then **correct `docs/campaigns.md`** so the stated invariant matches what is verified, and make the verified width list explicit rather than implied.

## Acceptance criteria

- [ ] `.table-scroll` satisfies `scrollWidth == clientWidth` with no in-container horizontal scrollbar at **every** width from the stacked-card breakpoint upward — verified at the breakpoint itself and one pixel above it, not only at 1024+.
- [ ] `docs/campaigns.md` states the invariant's true floor and the widths it was verified at.
- [ ] The Remove button is fully inside the container at the breakpoint boundary.
- [ ] If the breakpoint moves, the stacked-card layout is checked at the new boundary — it already renders full key, title, destination, and placement, so this should be cheap.
- [ ] `cd web && npm run check` 0 errors; `npm test` passes.
- [ ] **Seen running** via `./scripts/dev.sh` at 901px and at the breakpoint boundary.

## Out of scope

- Column content problems — [#0112](0112.md) (uncapped Source/Medium) and [#0113](0113.md) (the Destination column).
- Relaxing the invariant. [#0103](0103.md) decided against horizontal panning deliberately.

## Notes

- **This is long-standing, not a [#0106](0106.md) regression** — it predates the QR column. #0106 in fact improved it substantially: pre-#0106 geometry on the same dataset measured min-content **1235.48px**, against **910.42px** after.
- There is only **15.58px** of min-content headroom at present, so "recover 43px" is not available from the table's own slack — it would have to come from [#0113](0113.md)'s Destination redesign or from dropping a column.
- Measure with `.links-table { width: min-content }` rather than reading `scrollWidth`. With `table { width: 100% }` and `table-layout: auto`, the used width is `max(container, min-content)`, so a `scrollWidth == clientWidth` match can hide a table sitting a fraction of a pixel from failure. That distinction is what [#0106](0106.md)'s fourth round turned on.
