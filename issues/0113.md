# 0113 — The Destination column shows the same useless prefix on every row

| | |
|---|---|
| **Status** | open |
| **Module** | web |
| **Platform** | All |
| **First seen** | 2026-08-08 |

## Description

In the campaign links table ([#0103](0103.md)), the **Destination** column truncates from the left of the string — which for a URL means every row renders the part that is identical across every row.

Measured on a 44-link campaign: at the current 126px cap every row reads `https://www.ex…`. At the previous 150px cap every row read `https://www.examp…`. **Zero information either way**, and identical on all 44 rows.

The column currently occupies real width in a table that has repeatedly failed the [#0103](0103.md) zero-overflow invariant ([#0106](0106.md), [#0112](0112.md)) while conveying nothing.

## Why this matters

This is the column that should answer "where does this link actually point?" — the single most important thing to know when auditing a campaign's links, and the thing the UTM builder makes easy to get subtly wrong. Instead it answers "these are all URLs."

It also distorts the layout budget. #0106's fix squeezed this column from 150px to 126px to buy space, and the honest assessment was that 126px doesn't make it meaningfully worse because it was **already dead at 150px**. A column that is useless at any width it can afford should be redesigned, not shaved.

## Scope / deliverables

- **Show the part of the URL that differs between rows.** The scheme and `www.` prefix are noise; the meaningful signal is the host's distinguishing portion and the path/query tail. Options worth weighing: strip `https://` and `www.`; truncate from the middle; show host on one line and path on another; or show the path/query and put the host in a tooltip.
- Decide what happens with the **UTM query string**, which these destinations carry ([#0099](0099.md)). It is long, it is largely predictable from the campaign's own defaults, and it may deserve to be hidden or summarized rather than shown.
- Whatever is chosen, **rows must be distinguishable from each other** — that is the entire purpose of the column.

## Acceptance criteria

- [ ] With a realistic campaign whose destinations share a scheme and host, the rendered column differs between rows.
- [ ] The full destination is recoverable in a way that **works on touch**. A hover-only `title` tooltip is not sufficient on its own — it is invisible on touch and unreliable for assistive tech.
- [ ] Whatever width the column ends up with, the [#0103](0103.md) invariant still holds: `scrollWidth == clientWidth == 926` at 1024, 1280, 1440, and 1920. Report `min-content` headroom, not just a passing threshold — see [#0112](0112.md) for why a table can measure 926/926 while sitting a fraction of a pixel from failure.
- [ ] The 375px stacked layout renders the destination usefully too, where there is more room per row and no reason to truncate as hard.
- [ ] `cd web && npm run check` 0 errors; `npm test` passes with any new pure helpers covered by name.
- [ ] **Seen running** via `./scripts/dev.sh` against a campaign whose links share a host and differ only in path and UTM values — the case that currently renders 44 identical cells.

## Out of scope

- Source/Medium column overflow — [#0112](0112.md).
- QR column sizing — [#0106](0106.md).
- Changing what is stored in `destination_url`. This is a display problem; the stored value is correct.

## Notes

- If display truncation logic is added, it belongs in a pure module with unit tests per `docs/frontend.md`, not inline in the component — `web/src/lib/` already holds this table's shaping helpers.
- Freeing width here is the least painful place to find it. [#0106](0106.md)'s verification measured the post-fix table at **0.36px of `min-content` headroom**, so [#0112](0112.md) and any future column will be competing for space this column is currently wasting.
