# 0129 — Portiko has no runtime registration policy, so ShortLinks' admin toggle and first-admin rule can't carry over

| | |

## Description

Portiko decides who may create an account from static environment settings (`REGISTRATION` = `open` / `code` / `closed`, plus `BOOTSTRAP_CODE`; see `docs/registration.md` in Portiko). ShortLinks decides at runtime: an admin turns `registrations_enabled` on and off under Admin → Settings, and it takes effect on the next request. Portiko needs an extension point, such as a `RegistrationPolicy` in `provider.Options`, that the embedding site can answer from its own data. **Most of the work happens in the Portiko repo.**

## Long Description

**ShortLinks behavior to keep:**
- Turning off `registrations_enabled` refuses new accounts immediately, with "Registration is currently closed." (`auth.ErrRegistrationsDisabled` → 403).
- **Recovery is never blocked** by that setting. Portiko already follows this rule (its `docs/recovery.md` §5).
- The #0125 signed-out home page and `Login.svelte` read `registrations_enabled` from `GET /api/public/home` to decide whether to offer sign-up.
- The first user on a new install, or a user matching `ADMIN_EMAIL`, becomes an admin. That stays in ShortLinks (Portiko does no authorization). It moves into the `OnSignIn` hook in #0132, but it depends on knowing whether this is a *new* account.

**Wanted in Portiko:** a hook called at the start of registration, with the normalized email and a context. It returns allow or deny, and the denial message is shown on Portiko's sign-in page. The static `REGISTRATION` mode remains the default when no hook is set. Recovery skips the hook.

**Alternative if Portiko won't add it:** ShortLinks refuses unknown subjects in `OnSignIn` while registration is closed. That is worse: the person still creates a Portiko account and passkey, and only then gets turned away.
