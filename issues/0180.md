# 0180 — An expired or deactivated link shows a bare 404 or 410 page instead of somewhere useful

| | |
|---|---|
| **Status** | in-progress |
| **Module** | handlers / links / campaigns / db |
| **Platform** | All |
| **Phase** | 21 — Invitation links (CoupleDozen) |
| **First seen** | 2026-11-18 |

## Description

`/u/{key}` returns a plain-text 404 for inactive links and 410 "link expired" for expired ones (`internal/handlers/redirect.go:133-142`). Someone who taps an old invitation lands on a dead page. CommunityPlatform wants late taps to reach its own "this invitation has expired" page. Add an optional fallback URL per link and per campaign.

## Long Description

Requested by the CommunityPlatform session on 2026-11-18, for CoupleDozen invitation links on the new go.coupledozen.com instance. Their plan is in CommunityPlatform `docs/Plans/2026-11-ShortInviteLinks.md`, with issues GroupsWeb #0274/#0275 and CommunityBackend #0108. Each invitation link carries a secret token that grants entry to a family group, so these links need more protection than marketing links.

**Wanted:**
- **New fields:**
  - `fallback_url` on links: create, PATCH, the list and get responses, and the MCP tools.
  - `default_fallback_url` on campaigns. A link with no fallback of its own uses its campaign's.
- **Redirect behaviour:** when a link is expired or inactive and a fallback is set, `/u/{key}` returns 302 to the fallback with `?reason=expired` or `?reason=inactive` appended, preserving any query the fallback already has. Without a fallback, today's 404 and 410 stay.
- **Denied links never use a fallback.** A link refused by the URL filter must not become a redirect anywhere.
- **Validation:** the fallback URL is validated like a destination: absolute `https` (or `http`), run through the URL filter, and not pointing at the instance's own `/u/` path.
- **Clicks:** fallback hits are recorded with `outcome=fallback` (or not recorded at all; decide and document). They must never count as clicks on the link in reports.
- **Unknown keys** still return 404. A fallback only applies to a key that exists.

## Root cause

`/u/{key}` answered a flat 404 (inactive) or 410 (expired) with nowhere to send the visitor, and links and campaigns had no field to say where late taps should go.

## Fix

- Migration `000026_fallback_urls` (up and down): `links.fallback_url`, `campaigns.default_fallback_url`, both nullable `TEXT`. (Renumbered to 000026 on the coordinator's instruction.)
- `fallback_url` on link create, PATCH, get, list and the MCP `create_link`/`update_link` tools; `default_fallback_url` on campaign create, PATCH, get, list and the MCP campaign tools. An empty string clears either.
- Redirect: an inactive or expired link with an effective fallback (own, else campaign default) answers `302` to it with `reason=inactive` or `reason=expired` added, existing query kept. No fallback keeps 404/410. Denied links and unknown keys never fall back.
- The fallback is read from Postgres per expired/inactive hit (`links.Store.FallbackURLByKey`, via the optional `handlers.FallbackResolver`), not from the redirect cache, so changing a campaign default needs no cache invalidation and the live path is untouched.
- Validation (`internal/handlers/fallback.go`) runs on every create and edit that carries the field: absolute http(s) (400), not this instance's host under `/u/` (400), not matched by a URL filter rule (422 `fallback_denied`). This avoids, for fallbacks, the edit-skips-the-filter gap #0109 describes for destinations (that issue stays open for `destination_url`).
- **Clicks: not recorded.** There is no `outcome` column, and recording would make it easy for a report to count a fallback hit as a click on the link. Not recording makes that impossible by construction, with no change to any report. The cost is no analytics on late taps, which can be added later as a separate table or column.
- **Rate limiter (#0178):** a fallback `302` is not a 404/410, so it does not charge the strict miss bucket; it still counts against the general per-IP bucket (120/min). Reasoning: the people hitting an expired link are real visitors (50 people at one venue NAT tapping an expired poster must not be locked out, and a lockout would also 429 the live links), and the scanner threat is guessing unknown keys, which still return 404 and still exhaust the burst of 10. What a scanner gains from fallback hits is learning that a key once existed; that grants no access, since the link no longer admits anyone. A test proves 50 fallback taps pass and unknown keys are still throttled afterwards.
- Docs: `docs/links.md` (redirect flow, fallback section), `docs/campaigns.md`, `docs/database.md`.
- No UI page or setting changed (API and MCP only), so no screenshots. The SPA does not expose the new fields yet.
