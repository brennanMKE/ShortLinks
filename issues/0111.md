## Description

The production database has the **same schema drift** found in `shortlinks_test` ([#0110](0110.md)): five columns across two tables are nullable and defaultless in production where a clean `migrate up` replay makes them `NOT NULL`.

| Table | Columns |
|---|---|
| `passkey_credentials` | `user_id` |
| `sessions` | `user_id`, `created_at`, `expires_at`, `last_seen_at` |

Confirmed by diffing production's `pg_dump --schema-only` against a fresh database migrated to the same version. **Nothing else differs.**

## Root cause

Not a separate cause — the same one [#0110](0110.md) identified. Commit `791e7d3` ("Fix audit findings…", 2026-05-25) **edited `migrations/000004` and `000005` after they had already been applied**, adding the `NOT NULL` constraints and `DEFAULT now()`. golang-migrate tracks version *numbers*, not file *content*, so it had no reason to re-run them. Every database created before that commit — production and `shortlinks_test` alike — kept the original permissive tables while `schema_migrations` reported a version implying otherwise.

## Why this matters

The constraint gap is **real but currently latent**: at the time of investigation, zero rows violated the intended constraints (`sessions` had 5 rows, `passkey_credentials` had 1, and the `NULL` count on all five columns was 0). The application never writes NULLs there, which is exactly why this has gone unnoticed.

That is not a reason to leave it. The database is not enforcing an invariant the schema claims, and the safety net is currently "the code happens not to do that". A NULL `sessions.user_id` or `expires_at` would mean a session row that cannot be attributed to a user or expired — an auth-adjacent failure, in the tables where it matters most. `#0110`'s new schema guard protects test runs; it does not protect production.

## Scope / deliverables

- **A new forward migration** that applies the five constraints to an existing database. **Do not edit `000004`/`000005` again** — repeating the exact mistake that caused this. `docs/database.md` now carries a "never edit an applied migration" rule as of [#0110](0110.md); this is the first work that has to honour it.
- **Backfill or reject first.** The migration must handle pre-existing NULLs deterministically rather than failing halfway. Zero rows violate the constraints *today*, but that must be re-checked at apply time, not assumed from this issue — production accumulates rows between filing and deploying.
- **A down migration** that reverses it, consistent with the rest of `migrations/`.
- **Verify the deployed application still starts and authenticates** afterwards. These are the session and passkey tables; a mistake here logs everyone out or worse.

## Acceptance criteria

- [ ] After the migration, production's `pg_dump --schema-only` and a fresh replay at the same version differ only in pg_dump's own nondeterministic tokens and known client-version output-syntax noise (see Notes).
- [ ] The migration is safe to run against a database that **does** contain violating rows — either it backfills them by a stated rule, or it fails loudly *before* making any change. Decide which, implement it, test it against a database seeded with NULLs.
- [ ] The down migration restores the prior state and is tested, not just written.
- [ ] Login, session refresh, and passkey enrolment verified working against the migrated database.
- [ ] The same replay-vs-live diff is clean for **every** table, not just the two known ones — re-run the full comparison after applying rather than checking only what this issue names.

- Any change to `000004`/`000005` themselves.
- Deploying the campaigns feature. Production is at `schema_migrations` version 9 while the repo is at 12, because [#0098](0098.md)–[#0100](0100.md) have not shipped yet. That is an expected not-yet-deployed state, **not drift**, and it is noted here only so it is not mistaken for one during the diff. That is client-version output syntax, not a schema difference — do not chase it. Matching client versions, or dumping with the server's own `pg_dump`, avoids the noise entirely.

## Root cause

Already established by [#0110](0110.md): commit `791e7d3` ("Fix audit findings…", 2026-05-25) edited `migrations/000004` and `000005` **in place, after they had already been applied**. golang-migrate tracks version *numbers*, not file *content*, so it never re-ran them. Every database created before that commit — production and `shortlinks_test` alike — kept the permissive shape while `schema_migrations` reported a version implying otherwise.

## Fix

**A new forward migration, `000013_enforce_session_passkey_not_null`** — never an edit to `000004`/`000005`, which is the mistake being repaired. `docs/database.md` now carries the rule, with the non-obvious corollary about corrective-migration `down`s.

**It refuses rather than guesses.** The `up` migration counts violating rows in both tables and `RAISE EXCEPTION`s **before any DDL**, reporting both counts in one message with the recovery command. There is no truthful value to backfill a NULL `user_id` with — it is a FK to an unknown user — and guessing or silently deleting rows in the session and passkey tables is worse than stopping. Production had zero violations when inspected, but that was point-in-time; this re-checks at apply time.

**`down` is a documented no-op.** A down migration owes the caller the state a fresh replay of the *previous* version produces; a fresh replay to 12 runs today's `000004`/`000005`, which already create these constraints. The permissive DDL is quoted in the file for deliberate manual use.

## Verification

`go build`, `go vet` clean. Full suite against a migrated-from-drifted database passes but for the pre-existing `internal/config` failure ([#0116](0116.md)), including `TestFullCeremony_EndToEnd`.

The drifted fixture was replayed from `git show 791e7d3^:` rather than hand-dropping constraints, and its `pg_dump` confirmed **byte-identical to the live `shortlinks_test`** — the real drift, not an approximation.

`pg_dump --schema-only` of migrated-from-drifted vs. a fresh clean replay at 13: **zero differences across the whole schema**, 37 `CREATE` statements, not just the two named tables. Also zero for the recovered-from-abort database and the full 9→13 path.

**Six mutants, all caught**, each by its intended check: missing `SET DEFAULT now()`, no pre-flight guard, guard checking only one table, a forgotten `last_seen_at`, the unconditional-drop `down`, and deleting violating rows instead of aborting.

Transactionality was tested directly by appending `SELECT 1/0;` after the ALTERs — all five columns rolled back. **Real passkey enrolment and login verified over HTTP** against the running binary with a `virtualwebauthn` client: register → verify → finish, logout, login → finish, `/api/me`.

## Gotchas

- **The obvious recovery advice was wrong.** The first draft told operators to "resolve the rows, then re-run `migrate up`". Executed, that fails: after an abort golang-migrate records version 13 **dirty**, and the re-run dies with `Dirty database version 13`. The correct sequence is fix rows → `migrate force 12` → `migrate up`, and `force` is safe *because* the transaction rolled back. Tested against the real 9→13 path, not just 12→13.
- **Two `RAISE EXCEPTION`s cost two maintenance windows.** Only the first table was ever named, so an operator would fix `passkey_credentials`, re-run, and only then discover `sessions` — on the auth tables.
- **A corrective migration's `down` cannot "exactly reverse" it.** Reversing to a per-database prior state is not a function of the migration files. Verified: an unconditional drop produced, on an already-clean database, a schema byte-identical to the drifted fixture — manufacturing the exact drift this migration removes.
- **The mutation harness had its own flaw.** `migrate` echoes the entire `.sql` file into stderr, so grepping raw output matched the file's own comments and the no-guard mutant passed spuriously. Fixed by asserting only against the `(details: …)` parenthetical, which is the only part originating from Postgres. Worth knowing for any future migration test here.
- **The operator runbook was invalidated and nearly shipped stale.** `DEPLOYMENT.md` said the deploy ships three migrations; it ships four, and the fourth is the only one that can abort — with the recovery sequence living only inside a `.sql` file the operator has no reason to open.

## Downstream constraints

1. **Production must still apply this.** From `/opt/shortlinks` as `ec2-user`: back up (`scripts/db/backup.sh` — auth tables), then one `migrate up` takes 9 → 13. If 13 aborts nothing changed; resolve the rows, `force 12`, `up`.
2. **`down` is intentionally a no-op.** `migrate down 1` then `up 1` is not a round-trip test for this migration. Use the quoted DDL manually if a real rollback is ever needed.
3. **Migrations 13 and 10–12 do not interact** — 13 touches only `sessions`/`passkey_credentials`, 10–12 only campaigns/links/clicks. Order is irrelevant.
4. **`docs/database.md` will conflict with [#0110](0110.md)** when that branch merges — both insert a never-edit-an-applied-migration block at the same anchor. Docs-only, a few minutes by hand. Keep this version (it documents the `down` asymmetry and is written in past tense) and drop #0110's paragraph during that branch's rebase; #0110 needs rebasing against current `main` regardless.
