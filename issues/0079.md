## Description

Stand up an automated **end-to-end test suite that drives real Safari via
WebDriver** (`safaridriver`) against the **local development build**, covering
every user-facing feature of the app. This is the umbrella issue: it fixes the
stack, the architecture, and the constraints, then breaks the actual coverage
out into one issue per feature (0080–0091). Work the harness issue (#0080) first
— every other issue depends on it.

## Chosen stack (decided)

- **Client:** Node + [`selenium-webdriver`](https://www.npmjs.com/package/selenium-webdriver),
  living inside the existing `web/` project (Vite / Vitest / TypeScript). It
  speaks W3C WebDriver to `safaridriver` directly — no extra runner.
- **Layout:**
  ```
  web/
  ├── e2e/
  │   ├── harness.ts      # safaridriver session + dev-server fixture + helpers
  │   ├── pages/          # page objects (Dashboard, LinkDetail, Admin, …)
  │   └── *.e2e.ts        # one spec file per feature issue
  └── package.json        # "test:e2e" script
  ```
- **Runner:** the existing `vitest` can execute the `*.e2e.ts` files (separate
  config/project so unit `npm test` stays fast and e2e is opt-in via
  `npm run test:e2e`). Harness (#0080) decides the exact wiring.

## Target under test

The **local dev build**, served by `scripts/dev.sh --built` on
`http://localhost:8080` (single origin, real embedded SPA bundle, `STORAGE=json`
in-memory store). Built mode is preferred over hot-reload (:5173) so tests hit
the production-like bundle at one origin.

Seed state (from the dev store): mock admin `admin@localhost`, auto-logged-in;
**2 seed links** (one is `/u/gh` → github.com, titled "GitHub"). The in-memory
store resets on every server restart, which the harness uses for test isolation.

## Key constraints (must be respected by every sub-issue)

1. **Dev mode auto-logs-in as the mock admin.** The `DevAutoLogin` middleware
   mints an admin session on any request with no session cookie, so every page
   loads authenticated as an admin. Tests of *authenticated* and *admin* surfaces
   work directly; tests of the *unauthenticated* Login view need the auto-login
   suppressed (harness concern — see #0081).
2. **Passkey / WebAuthn ceremonies are stubbed in dev.** Registration, login, and
   recovery return stubs; the credentials list is empty. The real ceremonies
   cannot be exercised against the dev build.
3. **`safaridriver` does not implement the WebDriver WebAuthn virtual-authenticator
   commands** (Chrome/Firefox do; Safari does not). So even against a non-dev
   build, a passkey ceremony cannot be driven by Safari WebDriver with a virtual
   authenticator. **Decision:** the passkey ceremony stays covered by the existing
   `web/src/lib/webauthn.test.ts` unit tests plus manual verification; the Safari
   e2e suite covers everything *post-authentication* (the app's entire feature
   surface) via the dev auto-login. #0081 documents the seam.

## Acceptance criteria (umbrella)

- [ ] `npm run test:e2e` from `web/` boots the dev build, runs the full Safari
      WebDriver suite headed against `localhost:8080`, and reports pass/fail.
- [ ] Every feature issue 0080–0091 is resolved (its scenarios automated and green
      on this machine).
- [ ] The suite is deterministic and self-isolating (fresh dev-store state per
      spec, no cross-test bleed).
- [ ] `docs/` gains a short "End-to-end tests" page: prerequisites
      (`safaridriver --enable`, Safari "Allow Remote Automation"), how to run,
      how to add a spec, and the documented passkey/safaridriver limitation.

## Out of scope

- Cross-browser (Chrome/Firefox) runs — Safari-only per the request; the harness
  shouldn't hard-code assumptions that block adding others later.
- Testing the production deployment — target is the local dev build.
- Real passkey-ceremony automation — see constraint 3.
- A hosted CI runner for Safari (needs a macOS runner); note it, don't build it.

## Notes

- Prerequisite already done by the user: `safaridriver --enable`. Safari also
  needs **Develop ▸ Allow Remote Automation** enabled once (document in #0080).
- Only one `safaridriver` session can run at a time per host — the suite must run
  specs serially (no parallel Safari sessions). The harness must enforce this.
