## Description

Fills the chart slot left by [#0103](0103.md) on the campaign detail view: clicks over time (combined and per-link) and the channel breakdown by source, medium, and content.

Inline SVG with CSS design tokens, consistent with the existing components. **No charting library** — the existing `ClicksChart.svelte` and `UTMBarChart.svelte` establish the approach and it works.

## Scope / deliverables

**Clicks over time.** Either extend `ClicksChart.svelte` to accept multiple series, or add a `CampaignClicksChart.svelte` if leaving the single-series component alone is cleaner — decide by reading it, and say which and why in the resolution. Toggle between combined total and per-link breakdown.

**Channel breakdown.** Reuse `UTMBarChart.svelte` for source, medium, and content. Keep the muted `(none)` styling.

Series data comes from `CampaignSeriesByLink` ([#0102](0102.md)), which already caps the series count and folds the remainder into "Other". **The frontend must not re-implement that cap** — if it needs a different limit, change it in the query layer so both agree.

## Acceptance criteria

- [ ] Combined and per-link modes both render, and the per-link series totals reconcile with the combined total.
- [ ] The "Other" series is visually distinguishable from named links and is not mistaken for one.
- [ ] A campaign whose window contains **zero clicks** renders an empty chart with axes, not a broken SVG or a collapsed element.
- [ ] A single-day window renders sensibly — one bucket is the case interval-based axis code usually gets wrong.
- [ ] The default window follows the campaign's own `starts_at`/`ends_at` ([#0102](0102.md)); changing it refetches rather than re-slicing stale data.
- [ ] Charts are legible in **both light and dark mode**, and colors come from design tokens rather than literals.
- [ ] **Verified at 375px** — a multi-series chart with a legend is the hardest thing in this app to fit on a phone.
- [ ] New shaping helpers are pure and DOM-free with unit tests, matching the 26-test bar on `charts.ts`.
- [ ] `cd web && npm run check` 0 errors; `npm test` passes with new tests observed by name.
- [ ] **Seen running** via `./scripts/dev.sh` with real data — including the zero-click and single-day cases, which are the ones that look fine in a unit test and wrong on screen.

## Out of scope

- Cross-campaign comparison — a campaign chart only.
- Geographic or device breakdowns.
- Any change to the stats queries themselves; if a chart needs data the API does not return, that is a change to [#0102](0102.md), not a client-side derivation.

## Notes

- `web/src/lib/charts.ts` holds the existing pure helpers with 26 unit tests; new shaping goes there.
- The existing per-link view (`LinkDetail.svelte`) already composes `UTMBarChart` over `utmDimensions(detail.utm_stats)`. The campaign view should feel like the same product, not a second charting idiom.
- Series colors need to stay stable across renders for a given campaign, or the chart appears to change meaning when data refreshes.

## Root cause

Not a defect — the charts that fill the slot [#0103](0103.md) left.

## Fix

A new `CampaignClicksChart.svelte` (combined and per-link, toggleable) plus the channel breakdown reusing `UTMBarChart`. Inline SVG with design tokens, no charting library.

**A separate component rather than extending `ClicksChart`**, and review upheld it: `ClicksChart` derives its window from `defaultDateRange(days)` — a lookback from yesterday, which cannot express a server-resolved clamped window — and it hides the whole SVG when `totalClicks === 0`, which contradicts this issue's zero-click criterion. Geometry is genuinely shared (`toPolylinePoints`, `yAxisTicks`, `yCoord`, `xCoord`, `DEFAULT_CHART_GEO` are imported, not copied).

Series colours are keyed on `link_id`, not the backend's rank order, so a link keeps its hue when totals reorder between fetches. Verified live: inserting 200 clicks to make the third link rank first re-sorted the legend while every link kept its original colour.

## Verification

`npm run check` 192 files / 0 errors; `npm test` **333 passing** (from 296); `go build`, `go vet` clean; placeholder intact; `shortlinks_test` left empty at v12.

## Gotchas

- **A chart can be wrong in exactly the mode the issue exists for, and look fine everywhere else.** `toPolylinePoints` derived its own scale privately, so in per-link mode every series was normalised to its own peak: a link with 2 clicks/day was drawn touching the gridline labelled 60, while its dot — which used the shared scale — sat at y=143 on a plot spanning y=12–148. Line and dot for the same data point, 131 units apart. With 7 series every line collapsed onto one stroke at the top. **Combined mode hid it completely**, because there the single series' own max *is* the shared max.
- **The defect was unrepresentable in the pure layer**, which is why 322 tests missed it. Scaling was private to the helper; only opening it to an explicit max made a test possible. When a bug can't be expressed as a unit test, that is information about the API's shape, not about the tests.
- **The regression guard is the rendered verification, not the suite.** Mutation-checking after the fix: reverting the *call site* to `toPolylinePoints(s.points, geo)` — the original defect, verbatim — still passes **135/135**. The test guards the helper's contract; the bug lived at the call site, and this repo has no component tests at all (10 test files, all pure modules). Standing that up is a bigger decision than this issue.
- **`toPolylinePoints`'s third parameter is load-bearing and silently optional.** Omitting it compiles, type-checks, and passes everything while drawing wrong data. Any future multi-series chart must pass a shared max — a review item, not something tooling catches.
- **Fixing an off-by-one created a backwards one.** Subtracting a day to convert the exclusive `window_to` into an inclusive caption end turns a **zero-day** window backwards: `window_from == window_to` rendered "Aug 1, 2026 – Jul 31, 2026". Reachable, not theoretical — `starts_at == ends_at` is how you enter a one-day event, `campaigns_check` permits it (`ends_at >= starts_at`), and the create form imposes no min/max.
- **A single point still draws a polygon.** The area fill fanned from a centred point to the right edge, reading as a real multi-day decline over days that don't exist — under an acceptance criterion that called out the single-day case by name.
- **A comment cited a script that has never existed in this repo** (`scripts/validate_palette.js`), attached to the palette's entire validation claim. Replaced with directly computed WCAG ratios and an explicit note recording the false citation. The same shape as the unverifiable claims [#0102](0102.md)'s review caught.
- **A legend cannot mitigate a low-contrast line**, because the swatch is the same colour at the same contrast — it says which label a line carries, not where the line is. `--series-4` at 2.17:1 was raised to 3.07:1; slots 3 and 5 (2.69–2.82:1) stay as a documented trade backed by dash patterns and dot markers, which are real redundant channels.
- **The x-position formula was hand-inlined four times** across two components — the actual drift vector, and the reason the shared helper was too closed to serve the new caller. Now `xCoord(i, n, geo)`.

## Downstream constraints

1. **An empty resolved window is a representable state** (`[X, X)` — zero days, zero windowed clicks despite non-zero all-time). [#0107](0107.md)'s CSV export faces the same window and should decide explicitly what an empty range emits.
2. **`toPolylinePoints` now takes an optional shared max.** Any future multi-series chart must pass it; omitting it silently draws per-series scales.
3. **`xCoord(i, n, geo)` is the single x-position helper.** New chart work should use it rather than re-inlining.
4. **`windowLabel` returns an inclusive end** as of this issue. Docs and exports should assume inclusive.
5. **`--series-1..6` / `--series-other` are now the app's categorical palette.** [#0106](0106.md) and [#0108](0108.md) should consume them rather than add hues. Six is at the practical limit — for a deuteranope, slots 2 (orange) and 4 (amber) are the closest pair.
6. `series_by_link` (6 + Other) and `by_link` (uncapped) are different lengths — confirmed live at 7 vs 9.

## Follow-ups

- **No component-test capability exists.** The one mutant that survives is the original defect restored at the call site. Worth its own decision.
- The palette is at six categorical slots; a seventh would need a different encoding channel rather than another hue.
