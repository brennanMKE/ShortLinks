## Description

The frontend for campaigns: a list of them, and a detail view whose centerpiece is the links table. Charts are [#0104](0104.md) — this issue delivers the plan's third question ("what links belong to this campaign, and what does each one point at?") and the summary numbers, which is the part that is useful on its own.

Svelte 5, matching `docs/frontend.md`. Any new data shaping goes in a pure, DOM-free module with unit tests, same discipline as `utm.ts` (25 tests) and `charts.ts` (26 tests).

## Scope / deliverables

**Campaigns list view.** Table or card list: name, date range, link count, total clicks, sparkline. Archived campaigns filtered out or collapsed by default — the list should stay short without anything being deleted.

**Campaign detail view**, top to bottom:

1. **Header** — name, description, date range, edit and archive controls.
2. **Summary** — total clicks in window, clicks per day average, active link count, **bots excluded count** ([#0101](0101.md)). The excluded count is shown, not hidden.
3. *(Charts slot — [#0104](0104.md).)*
4. **Links table** — every link in the campaign: short key, title, destination, source, medium, placement, clicks in window, share of campaign total, created date. Each row links to the existing link detail view. Sortable by clicks.
5. **Copy** — copy all short URLs for the campaign at once.

Also: assign and unassign links from this view, against the [#0099](0099.md) endpoints.

## Acceptance criteria

- [ ] A campaign with no links renders an empty state, not a broken table or a spinner that never resolves.
- [ ] "Share of campaign total" sums to 100% (allowing for rounding) and does not divide by zero when the campaign has no clicks.
- [ ] Sorting by clicks is stable and does not reorder rows with equal counts arbitrarily between renders.
- [ ] Archived campaigns are excluded from the default list and reachable through an explicit filter.
- [ ] The bots-excluded count is visible in the summary whenever it is non-zero.
- [ ] Long values do not break layout: a 200-character destination URL, a 60-character placement, and a campaign with 30+ links.
- [ ] **Verified at 375px width** as well as desktop — the links table has more columns than any existing table in this app, and that is where it will break.
- [ ] `cd web && npm run check` reports 0 errors; `npm test` passes with new unit tests observed by name.
- [ ] **Seen running.** Verified in the browser via `./scripts/dev.sh`, not signed off from logic alone — including the empty state and a campaign with real links.

## Fix

A campaigns list (name, date range, link count, all-time clicks, archived filtered out by default) and a campaign detail view (header with edit/archive, summary, links table, assign/unassign, copy-all). Shaping lives in a pure `web/src/lib/campaigns.ts` with unit tests, matching the `utm.ts`/`charts.ts` bar. A create-campaign form was added beyond the deliverables because no UI path to create a campaign existed anywhere — without it the views were unreachable.

One backend change came out of review: `clicks.CampaignStats` now returns **`window_from` / `window_to`**, the window the queries actually filtered on, so the UI labels and divides by the server's resolved window instead of re-deriving it. That also closes [#0102](0102.md)'s open question for the dated case.

## Gotchas

- **Date-only values wearing a timestamp corrupt data on every save.** `starts_at`/`ends_at` are calendar dates stored as `timestamptz` and serialized with a local offset (`"2026-06-30T17:00:00-07:00"` for UTC-midnight `2026-07-01`). `iso.slice(0,10)` and local-time `formatDate` both read the **previous day**, while the save wrote back UTC midnight — so opening the edit form and clicking Save **with no edits** walked the dates backward one day, every time: `2026-07-01` → `06-30` → `06-29` → `06-28` across three cycles. And because those dates *are* the default analytics window, every save silently changed the numbers the page reported.
- **The same bug then reappeared in Go, in the fix for it.** `time.Format` renders in the value's own `Location`, and pgx decodes `timestamptz` into the **process's** local zone — so `window_from` came back a day early on any server with a negative offset. `window_to` was immune only because `campaignWindow` builds `today` with `time.UTC` explicitly. The fingerprint was a one-digit disagreement between two reports of the same screen: 7.9 clicks/day (300/38, UTC) versus 7.7 (300/39, PDT).
- **A test can be blind to a timezone bug in two distinct ways.** Passing `time.Date(…, time.UTC)` values that never touch the database means pgx's decoding location never enters. Seeding a value that carries a **time-of-day** means an offset shift usually lands on the same calendar date — passing under every `TZ` at most hours, which is latently flaky rather than protective. Only a UTC-**midnight** value read back **through** the driver catches it.
- **Clamping on the server and dividing on the client is a 5× error waiting to happen.** `campaignWindow` clamps `to` at today; the UI divided by the full nominal span, so an in-flight Jul–Dec campaign reported **1.6** clicks/day where the truth was 7.7, under a label claiming five months of coverage. The fix is for the server to return the window it used — duplicating the clamp client-side would drift.
- **A denominator that differs from the number above it needs to say so.** "Share" read 71% where the true share of campaign clicks was 45%, because clicks from since-unassigned links are excluded from the denominator but not from the headline. The choice was right; the bare header was not. Now "Share of listed links", with a line accounting for the missing clicks.
- **`<tr onclick>` is not a control.** Sixteen tab stops never reached a campaign row, so the detail view was mouse-only — and `npm run check` reports zero warnings, so tooling will not catch it. The row's name cell is now a real `<button>`.
- **Ten columns do not fit anywhere.** At 375px only three were visible; Created and Remove were off-screen at *every* width, including 1440. Below 900px the table becomes stacked cards — and the sort control, which lived inside the now-clipped `<thead>`, had to be re-exposed separately or an acceptance criterion silently vanished on mobile.
- **`extractKey`'s `$` anchor dropped the whole URL when a short link carried a query string** — so pasting `…/u/abc123?utm_source=newsletter`, the single most likely thing a *campaigns* user would paste, failed with "link not found: https://…". Found by a mutation pass, not by the 264 tests.

## Downstream constraints

1. **[#0104](0104.md)** must label its axis from `window_from`/`window_to`, not the campaign's nominal dates, or the chart caption will disagree with the summary directly above it. **`window_to` is the exclusive end of a half-open range** — filling day gaps against it without accounting for that renders a phantom trailing day. Same for [#0107](0107.md)'s exported range.
2. `LinkSeries.key` is now in `types.ts`; #0104 needs it.
3. **`formatDateOnly` vs `formatDate` is a real distinction in `lib/`**: calendar dates render UTC, instants render local. Every remaining `formatDate` caller was audited and is a genuine instant (`created_at`/`expires_at`). [#0105](0105.md) and #0107 should follow it.
4. The share-denominator wording ("Share of listed links" + the unlisted-clicks note) is the same arithmetic #0104's per-link chart and #0107's CSV face — reuse it rather than inventing a second phrasing.
5. The stacked-card pattern (`data-label` + `::before`) is available for [#0106](0106.md)'s QR column and any other wide table.
6. Dev mode returns `total_clicks: 0` and empty stats always, so a UI built only against `scripts/dev.sh` cannot exercise the non-zero paths.
