# 0094 — Add "Sign out everywhere" to revoke all sessions without touching enrolled passkeys

| | |
|---|---|
| **Status** | open |
| **Module** | auth / handlers / web |
| **Platform** | All |
| **First seen** | 2026-08-04 |

## Description

Add an account action that revokes **every** active session for the signed-in user, forcing a fresh passkey ceremony on all devices. The account, its email, and every enrolled passkey are left untouched — this is a session-lifetime action, not a credential action.

Today the only revocation levers are `Logout` (`internal/auth/login.go:271`), which deletes exactly one session by its cookie token, and credential revoke (#0019), which un-enrolls a passkey permanently. There is nothing in between: if a session is live on a device you no longer control, the only remedies are revoking a passkey you still want to keep, or waiting for the session to expire.

## Does this make sense for passkeys?

Yes — and it is *more* load-bearing here than in a password app, not less.

In a password app, "sign out everywhere" is usually offered next to "change your password", because the scenario prompting it (phishing, reuse, a breach dump) means the **credential** may be compromised. Revoking sessions alone is half a remedy there; without rotating the password the attacker just signs back in.

Passkeys remove that half of the problem. The private key is non-exportable, origin-bound, and phishing-resistant — it does not leak the way a password does. So the realistic threat model for this app narrows to exactly one thing: **a live session on a device you no longer control** — a sold or lost Mac, a shared machine, a Screen Sharing session left open, an iPhone handed on. Session revocation is the complete and correct remedy for that, and because there is no password to rotate, it is the *only* self-service account-security action a user has.

The two levers are complementary and both are needed:

| Action | Effect | Use when |
|---|---|---|
| Revoke credential (#0019, exists) | That authenticator can never authenticate again | An authenticator is lost/compromised, or you removed a device from iCloud |
| **Sign out everywhere (this issue)** | All current sessions die; every credential still works | A *session* is somewhere it shouldn't be |

**"Retain the email" needs no work.** Revoking sessions deletes rows from `sessions` only. The `users` row (and its email) and every `passkey_credentials` row are untouched by construction, so the account remains fully enrolled and the next sign-in is a normal passkey ceremony. The email prefilled in the login form is browser autofill, not server state — there is nothing to preserve there either.

## Design decision: include the current session

**Recommendation: revoke *all* sessions including the caller's, then redirect to the login screen.** Not "sign out all *other* sessions".

The usual reason products spare the current session is that re-authenticating is a chore — retyping a password, maybe a TOTP code. With a passkey it is a Touch ID tap (or the Mac login password over Screen Sharing, per #0092). The cost that motivates the "keep this one" carve-out mostly does not exist here, and a user reaching for this button wants an unambiguous guarantee that *nothing* is still authenticated. Sparing the current session weakens the guarantee to buy convenience that passkeys already provide.

This is the passkey-specific part of the design: the authentication mechanism changes the right default.

## Email notification

Sending a notification on this action is worth doing: it is the one account event a user cannot see happening (every device just drops), and an unexpected one is a signal worth surfacing.

**Copy correction — the email must say "your existing passkey", not "a new passkey".** Signing out everywhere revokes *sessions*; it does not touch `passkey_credentials`. The user's enrolled passkey still works and is what they sign in with. Telling them to sign in "with a new passkey" would be wrong and actively harmful — it reads as "your passkey no longer works", which pushes people into the recovery ceremony (`/recover/verify`) to enroll a redundant credential they never needed. That is the same flow that produced the duplicate-looking entries in #0092's Passwords screenshot.

Enrolling a *new* passkey is a real follow-up, but only for the lost-device case, and it pairs with revoking the old credential (#0019). The email should mention it as a conditional second step, not the primary instruction.

Suggested body:

```
All sessions for {email} were signed out on {timestamp}.

To get back in, go to {BASE_URL} and sign in with your existing passkey —
it still works and nothing about your account has changed.

If you did this because a device was lost or is no longer yours, also open
Account settings after signing in and revoke that device's passkey. You can
enroll a replacement from the same screen.

If you did not do this, sign in and revoke your passkeys immediately.
```

Delivery rules:

- **Send after the transaction commits, and never fail the operation on a send error.** This is a security action; an SMTP hiccup must not leave sessions alive. Log the failure and return success — the same fire-and-forget precedent as the audit write in `Logout` (`internal/auth/login.go:283-292`).
- Include the timestamp. **IP is optional and probably not worth it** — the audit log for this account shows carrier-NAT addresses (`174.194.x`, `136.25.x`) that shift between sign-ins, so "from 174.194.199.208" is more likely to alarm than inform.
- No token, no link with credentials — unlike verification and recovery mail, this is a plain notification. There is nothing single-use in it, so it needs no TTL and is safe to re-read.

## Scope / deliverables

- **Store:** `DeleteSessionsForUser(ctx, q, userID) (int64, error)` in `internal/auth/store.go`, returning the number of rows deleted. Must run inside the caller's transaction alongside the audit write.
- **Service:** a method on `LoginService` (sibling to `Logout`) that revokes all sessions for the authenticated user and writes an audit entry.
- **Audit:** new `ActionSessionsRevokedAll = "session.revoked_all"` in `internal/audit/actions.go`. Record the revoked count so the log distinguishes "revoked 4 sessions" from a no-op. Actor and affected user are the same account, as with `account.logout`.
- **Handler:** `POST /auth/logout/all` (session-guarded), clearing the session cookie on the way out exactly as `Logout` does.
- **Mailer:** add `SendSessionsRevoked(ctx, toEmail string, at time.Time) error` to the `Mailer` interface (`internal/auth/mailer.go:14`). This is a **breaking interface change** — **five** implementations must be updated, two of which are outside `internal/auth`:

  | Implementation | File |
  |---|---|
  | `NoOpMailer` | `internal/auth/mailer.go:32` — log the would-be notice, as it does for the other two |
  | `SESMailer` | `internal/auth/ses_mailer.go:52` — reuse the existing `send` + `buildMessage` helpers |
  | `recordingMailer` | `internal/auth/registration_test.go:39` |
  | `recoveryRecordingMailer` | `internal/auth/recovery_test.go:38` |
  | `gateMailer` | `internal/handlers/settings_test.go:439` — easy to miss; `internal/handlers` will not compile without it |
- **Web:** a button in `Account.svelte` alongside the existing credential management, with a confirmation step (this is destructive and not undoable). Copy must state that enrolled passkeys are **not** removed, that sign-in still works with the existing passkey, and that native/iPhone clients are signed out too.

## Acceptance criteria

- [ ] A user with N sessions across devices ends with 0 after the call; a second call is a clean no-op returning 0.
- [ ] `users` and `passkey_credentials` rows are untouched — asserted explicitly, including that a normal passkey login succeeds immediately afterward.
- [ ] Sessions belonging to **other** users are untouched — asserted with a second seeded account.
- [ ] The caller's own session is revoked and its cookie cleared; the next request with the old cookie is rejected.
- [ ] An audit row with the new action and the revoked count is written in the same transaction.
- [ ] A notification email is sent to the account's address, asserted via `recordingMailer`.
- [ ] **A mailer error does not fail the operation** — asserted with a mailer stubbed to return an error: sessions are still revoked, the handler still returns 200, and the failure is logged.
- [ ] The email is sent only **after** the transaction commits — a test where the commit fails must send no mail.
- [ ] `go build ./...`, `go vet ./...`, `gofmt -l` clean; `go test ./...` passes with the new tests observed by name in the run output.

## Out of scope

- **A session list UI** ("3 sessions: MacBook, iPhone, …"). The `sessions` table (`migrations/000005_create_sessions.up.sql`) stores only `user_id`, `token`, `created_at`, `expires_at`, `last_seen_at` — there is no user-agent, IP, or device-name column, so per-session labels are not possible without a schema change. The UI can show a **count** of active sessions but nothing more. File separately if the labelled list is wanted.
- Admin-initiated revocation of *another* user's sessions. Related to the unused `account.deactivated` path (#0028); different authorization story.
- Any change to session TTL or the sliding `last_seen_at` behavior.

## Notes

- **This signs out the iPhone app too.** #0077 made `RequireSession` accept `Authorization: Bearer <token>` reusing the *same* `sessions` rows (`internal/middleware/auth.go:24`), so a bulk delete revokes native-client tokens along with browser cookies. That is the correct behavior — "everywhere" must mean everywhere — but the button's copy should say so, or a user will read it as browser-only and be surprised when the app logs out.
- `Logout` is deliberately idempotent and treats an unknown token as success. The bulk version should follow that precedent: revoking zero sessions is a 200, not an error.
- `DeleteSession` returns the affected `userID` so the audit entry can be attributed (`login.go:275-283`). The bulk version already knows the user from the session guard, so it should take `userID` directly rather than inferring it.
- The service needs the account's **email** to address the notification, which `Logout` never had to look up. Either resolve it from `userID` inside the transaction or thread it down from the session guard — the latter avoids an extra query if `SessionUser` already carries it (check `Store.ResolveSession`, `store.go:662`).
- Local testing of the email needs no SES: with no SMTP credentials configured, `cmd/shortlinks/main.go:90` falls back to `NoOpMailer`, which prints the message to the server log. That is how the registration magic link is exercised locally.
