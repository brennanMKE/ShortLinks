# 0179 — Generated keys are only 6 characters, and nothing documents that a client can choose a longer random key

| | |
|---|---|

## Description

Generated keys are 6 base-62 characters, about 36 bits. CommunityPlatform asked for longer keys, or client-chosen ones, for invitation links. Clients can **already** send a custom `key` of 1–12 characters from `[A-Za-z0-9_-]` (`validKey`, `internal/handlers/links.go:1358`). Twelve random characters is about 71 bits. That works today, but [docs/using-api-tokens.md](../docs/using-api-tokens.md) doesn't present it as a security option, and the column caps keys at `VARCHAR(12)`.

## Long Description

Requested by the CommunityPlatform session on 2026-11-18, for CoupleDozen invitation links on the new go.coupledozen.com instance. Their plan is in CommunityPlatform `docs/Plans/2026-11-ShortInviteLinks.md`, with issues GroupsWeb #0274/#0275 and CommunityBackend #0108. Each invitation link carries a secret token that grants entry to a family group, so these links need more protection than marketing links.

**Wanted:**
- **Docs now.** Document custom random keys as the way to get unguessable links. Tell CommunityPlatform that sending 12 random base-62 characters as `key` works on the current release.
- **`key_length` option.** Add `key_length` (6–32, default 6) to `POST /api/links` and batch create, so the server generates the longer key and clients don't each need a good random source. The `batch_create_campaign_links` and `create_link` MCP tools get the same field.
- **Wider column.** Widen `links.key` to `VARCHAR(32)` in a migration, and raise `validKey`'s ceiling to 32. Check every place that assumes 12, including the SPA tables (#0157) and QR filenames.
- **Collisions.** Collision handling for generated keys stays as it is.

## Root cause

Generated keys were hard-coded to 6 characters (`links.KeyLength`), `links.key` was `VARCHAR(12)` and `validKey` capped custom keys at 12. A client could already send a 12-character random `key`, but nothing documented that as the way to get an unguessable link, and there was no way to ask the server for a longer generated key.

## Fix

- Migration `000022_widen_links_key` widens `links.key` to `VARCHAR(32)` (down narrows back to 12 and fails loudly if a longer key exists).
- `internal/links/keygen.go`: `MinKeyLength` 6, `MaxKeyLength` 32, `GenerateKeyN`, `GenerateUniqueKeyN`, `ValidKeyLength`, `KeyGenerator(n)`. `GenerateKey`/`GenerateUniqueKey` keep their signatures (6 characters). Collision handling is unchanged.
- `POST /api/links` accepts `key_length` (6-32, default 6, ignored with a custom key, `400` otherwise). `POST /api/campaigns/{slug}/links/batch` accepts a top-level `key_length` for every row. The `create_link` and `batch_create_campaign_links` MCP tools gained `key_length`.
- `validKey` ceiling is now 32 (error text "custom key must be 1-32 url-safe characters"). The SPA's `MAX_KEY_LENGTH` is 32, so the New link dialog's hint now reads "Up to 32 characters" (no layout change). Table cells already ellipsize.
- A 32-character key makes a QR code version 6 (49x49); `TestLevel_TypicalShortURLStaysSmall` now pins 45 for 12 characters and 49 for 32. QR filenames use the key as-is, so no change.
- CommunityPlatform's invite request (12-character custom key, `Idempotency-Key: invite-<id>`, `expires_at`, `utm_source=invite`, `utm_medium=share`) is covered by a test and documented with a curl example in docs/using-api-tokens.md.
- OpenAPI: `key_length` on `CreateLinkRequest` and `BatchCreateRequest`, key pattern/length 32. Docs: links.md (new "Unguessable keys" section), using-api-tokens.md, mcp.md, database.md, campaigns.md.
