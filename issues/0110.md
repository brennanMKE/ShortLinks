# 0110 — The integration-test database has drifted from a clean migration replay

| | |
|---|---|
| **Status** | open |
| **Module** | db / infra |
| **Platform** | All |
| **First seen** | 2026-08-07 |

## Description

`shortlinks_test` — the database every DB-backed integration test in this repo runs against — **does not match the schema a clean `migrate up` produces.** Discovered while verifying [#0100](0100.md)'s down migration: a fresh database migrated 1→12 and then dumped differs from the live `shortlinks_test` dumped at the same version. At least two tables have columns that are **nullable in `shortlinks_test` but `NOT NULL` in a clean replay** (`user_id`, `created_at`, `expires_at`, `last_seen_at` were the ones observed).

The cause is presumably historical: the database was created before some migration was written, or was hand-patched at some point, and `schema_migrations` was left claiming a version the tables do not actually reflect.

## Why this matters

**Tests can pass against a schema no deployment will ever produce.** A `NOT NULL` constraint that exists in production but not in the test database is precisely the kind of difference that lets a bug through: code that inserts a NULL passes locally and fails on deploy, and the failure surfaces as a 500 in production rather than a red test.

It also actively costs review time. #0100's implementer diffed the down migration against the live `shortlinks_test` rather than a fresh replay, specifically because a fresh-replay baseline showed unrelated differences. That was the *correct* call given the drift — but it means the stronger verification method is unavailable while this persists, and every future migration review has to reason around the same trap. The reviewer had to run both to be sure.

## Scope / deliverables

- **Establish the true extent of the drift.** Diff `pg_dump --schema-only` of `shortlinks_test` against a freshly created database migrated to the same version. Do not assume the two tables already observed are the whole story — check constraints, defaults, indexes, and FK actions, not just nullability.
- **Decide and document the fix.** The obvious one is to drop and recreate `shortlinks_test` from migrations (`scripts/db/drop.sql` + `create.sql` exist), which is cheap because the database holds no data worth keeping — every test truncates. Confirm that is true before relying on it.
- **Make it not recur.** A test-suite guard is the durable fix: on startup, assert the connected schema matches what the migrations produce, or at minimum that `schema_migrations.version` equals the highest file in `migrations/` and the database is not dirty. Failing loudly at the start of a run beats a subtly wrong pass.
- **Check whether the production database has the same drift.** This issue is about the test database, but the same history may have produced the same divergence there — and that would be considerably more serious. Investigate; if production is also drifted, that becomes its own issue with its own urgency.

## Acceptance criteria

- [ ] `pg_dump --schema-only` of `shortlinks_test` and of a fresh replay at the same version differ only in pg_dump's own nondeterministic tokens (the `\restrict` nonces).
- [ ] The full suite passes against the rebuilt database with no test changes — if a test *relied* on the looser schema, that is a finding worth reporting rather than quietly fixing.
- [ ] A guard fails the run loudly when the connected database's version does not match the migrations directory, or is dirty.
- [ ] The production check is done and its result recorded, whichever way it comes out.
- [ ] `docs/database.md` or `docs/dev.md` states how the test database is expected to be created, so the next person does not hand-patch it.

## Out of scope

- Fixing production drift, if any is found — that gets its own issue.
- Changing any migration to match the drifted state. The migrations are the source of truth; the database is what is wrong.
- CI setup. There is no CI in this repo today; the guard should work for a local `go test` run.

## Notes

- `scripts/db/` already has `create.sql`, `drop.sql`, `backup.sh`, `restore.sh`, and `db-status.sh` — check whether one of these was the intended creation path and simply drifted out of use.
- Every DB-backed test truncates its own tables, so there is unlikely to be state worth preserving — but confirm rather than assume before dropping.
- Worth checking `git log` on `migrations/` for a migration added after the test database was first created; that would explain the specific columns observed.
