# 0080 — E2E test harness & scaffolding (safaridriver session + dev-server fixture)

## Description

Build the foundation the whole Safari WebDriver suite sits on: a reusable harness
that (a) starts and stops the local dev build, (b) opens and tears down a
`safaridriver` session via `selenium-webdriver`, (c) provides page-object scaffolding
and common helpers, and (d) exposes a `npm run test:e2e` entry point. **This issue
blocks all other e2e issues (0081–0091).** Part of the [#0079](0079.md) umbrella.

## Scope / deliverables

- **Dependencies:** add `selenium-webdriver` (+ types) as a dev dependency in
  `web/`. No global installs beyond `safaridriver` (system Safari).
- **Dev-server fixture** (`web/e2e/harness.ts`):
  - Start `scripts/dev.sh --built` (serves the embedded SPA on
    `http://localhost:8080`, `STORAGE=json`), wait until `GET /health` (or `/`)
    returns 200, yield the base URL, and shut it down + free port 8080 on teardown.
  - Because the in-memory dev store resets on restart, restarting the server is
    the isolation primitive: **fresh server (and thus fresh seed data) per spec
    file**. Provide a helper so a spec can request a clean state.
- **WebDriver session:** build a `safari` driver (W3C). Enforce **serial
  execution** — only one safaridriver session may exist per host, so the e2e
  config must not run specs in parallel.
- **Page-object scaffolding** (`web/e2e/pages/`): a `BasePage` (navigation,
  `waitForVisible`, `byTestId` helper) and one empty/stub page object per view so
  the feature issues just fill them in.
- **Selector strategy:** decide and document how elements are targeted. Prefer
  stable `data-testid` hooks; if the current SPA lacks them, note where they must
  be added (small, non-behavioral markup changes are in scope for the feature
  issues, coordinated here).
- **Runner wiring:** a separate Vitest project/config (e.g. `vitest.e2e.config.ts`)
  matching `web/e2e/**/*.e2e.ts` with a long timeout and serial execution, plus a
  `"test:e2e"` script in `web/package.json`. `npm test` (unit) stays unchanged and
  fast.
- **Smoke spec** (`web/e2e/smoke.e2e.ts`): boot server → open Safari → load
  `localhost:8080` → assert the Dashboard renders ("Create a short link" panel and
  the seeded `/u/gh` row are present) → clean shutdown. This proves the harness
  end-to-end.
- **Docs:** `docs/e2e-tests.md` (linked from `docs/README.md`) — prerequisites,
  how to run, how to add a spec, and the passkey/safaridriver limitation from the
  umbrella.

## Preconditions

- `safaridriver --enable` (done by the user).
- Safari ▸ Settings ▸ Advanced ▸ "Show Develop menu", then **Develop ▸ Allow
  Remote Automation** enabled (one-time; document it and check for a clear error
  if it's off).

## Acceptance criteria

- [ ] `npm run test:e2e` from `web/` runs the smoke spec: dev build boots, Safari
      opens via safaridriver, Dashboard asserts pass, everything tears down, port
      8080 freed.
- [ ] Harness starts/stops the dev server and yields the base URL; a spec can get
      a fresh-seed server.
- [ ] Specs run **serially** (single Safari session); a second concurrent session
      is never attempted.
- [ ] `BasePage` + per-view page-object stubs exist under `web/e2e/pages/`.
- [ ] Unit `npm test` is unaffected (does not pick up `*.e2e.ts`).
- [ ] `docs/e2e-tests.md` exists and is linked from the docs index.

## Out of scope

- Actual feature coverage — that's 0081–0091.
- CI execution (needs a macOS runner) — leave a note in the doc.

## Notes

- Server management options: shell out to `scripts/dev.sh --built` as a child
  process, or start the Go server directly with `STORAGE=json`. Reuse `dev.sh` so
  the env defaults (auto-login, RP settings) stay in one place.
- Health signal: the Go service exposes `GET /health`; wait on that rather than a
  fixed sleep.
- Keep the harness browser-agnostic enough that Chrome could be added later, but
  don't build multi-browser now.
