# 0081 — E2E: authentication, session & access control

|---|---|
| **Status** | open |

## Description

Automate the auth- and session-related behaviors that *can* be driven by Safari
WebDriver against the dev build, and clearly document the seam where passkey
ceremonies can't be. Depends on [#0080](0080.md); part of [#0079](0079.md).

## Scope / scenarios to automate

- **Auto-logged-in landing.** Loading `/` lands on the Dashboard authenticated as
  the mock admin (no login prompt) — the dev `DevAutoLogin` path. Assert the
  authenticated chrome (header with "Sign out", the Dashboard/Account/Admin nav).
- **Logout.** Clicking "Sign out" calls `POST /auth/logout` and returns the user
  to the Login view (or triggers re-auto-login — see Notes; assert the actual dev
  behavior and pin it down).
- **Session-guard redirects.** With auto-login suppressed (harness flag / no
  session), navigating directly to a protected view (`/`, `/account`, LinkDetail)
  routes to the Login view rather than rendering protected content — mirrors the
  `GET /api/me` gate in `App.svelte`.
- **Admin-only guard.** The Admin nav/view is reachable as the admin. If the
  harness can present a non-admin session, assert Admin is hidden/blocked;
  otherwise document that non-admin state isn't reachable in dev and defer to
  handler unit tests.
- **Magic-link landing routes.** `/register/verify` and `/recover/verify` render
  the `RegisterVerify` / `RecoverVerify` views (not a bounce to Login), per the
  path-first routing in `App.svelte` (#0041). The *token exchange* is stubbed in
  dev — assert the view renders and the stubbed outcome is handled gracefully.

## Passkey ceremony — explicitly out of scope here (documented)

Real WebAuthn registration/login/recovery cannot be driven by Safari WebDriver:
dev stubs the ceremonies, **and** `safaridriver` has no WebAuthn virtual-authenticator
support. These stay covered by `web/src/lib/webauthn.test.ts` (unit) + manual
device checks. This issue records that seam so it isn't mistaken for a coverage gap.

## Preconditions

- Harness ability to run **with and without** dev auto-login (a knob to suppress
  the `DevAutoLogin` middleware / clear the session cookie). If #0080 didn't
  provide it, this issue adds it — it's the crux of the unauthenticated assertions.

## Acceptance criteria

- [ ] Auto-logged-in landing on Dashboard asserted.
- [ ] Logout flow asserted (documented, deterministic dev behavior).
- [ ] Unauthenticated access to a protected view routes to Login.
- [ ] `/register/verify` and `/recover/verify` render their views directly.
- [ ] The passkey/safaridriver limitation is documented in the spec and
      `docs/e2e-tests.md`.

## Out of scope

- Passkey ceremony automation (see above).
- Rate-limit behavior on auth endpoints (backend concern; handler tests own it).

## Notes

- Confirm the real dev logout behavior first: because `DevAutoLogin` re-mints a
  session on the next request with no cookie, "logout" may immediately re-auth on
  navigation. Pin the assertion to what actually happens and note it.
