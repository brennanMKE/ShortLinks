## Description

Two changes to click recording, both required before any campaign number means anything.

**1. Denormalize `campaign_id` onto the click row.** Resolve the link's campaign at record time and store it, rather than joining `clicks → links → campaigns` at query time. Two reasons, both about history: a link can be reassigned or unassigned, and historical clicks should stay attributed to the campaign that was running when they happened — a join would silently rewrite the past. And `docs/database.md` notes `clicks.link_id` is nullable with a non-cascading FK precisely so click history outlives deleted links; campaign rollups should survive the same way.

**2. Fall back to the link's stored UTM values when the inbound query omits them.** Today `internal/handlers/redirect.go:169-173` populates the click row from `q.Get("utm_source")` and friends — the inbound short-URL query string only. A link with `utm_source=newsletter` baked into its destination, shared as a bare `https://go.sstools.co/u/ab12de`, records `NULL`. Every breakdown in the campaign view would be a single `(none)` bar. With the fallback, the stored discrete value ([#0099](0099.md)) fills the gap while **inbound values still win**, preserving the documented override behavior.

## Data model

Migration `000012_clicks_campaign_and_bot`:

```
ALTER TABLE clicks
  ADD COLUMN campaign_id BIGINT REFERENCES campaigns(id) ON DELETE SET NULL,
  ADD COLUMN is_bot      BOOLEAN NOT NULL DEFAULT FALSE;

CREATE INDEX idx_clicks_campaign_id   ON clicks(campaign_id) WHERE campaign_id IS NOT NULL;
CREATE INDEX idx_clicks_campaign_time ON clicks(campaign_id, clicked_at) WHERE campaign_id IS NOT NULL;
```

The composite index carries the campaign timeseries query in [#0102](0102.md). **Verify with `EXPLAIN` rather than assuming** it gets used.

`is_bot` is added here so there is one `clicks` migration rather than two; the classification logic that populates it is [#0101](0101.md). Until then the column stays `FALSE`.

Existing rows get `campaign_id = NULL`, which is correct — they predate campaigns. **Do not backfill by guessing from `utm_campaign` strings.**

## Both changes fit the existing INSERT — verified

`internal/clicks/recorder.go:74-79` already resolves the link inside one statement:

```sql
INSERT INTO clicks (link_id, clicked_at, ip_address, user_agent, referer,
                    utm_source, utm_medium, utm_campaign, utm_term, utm_content)
SELECT l.id, $2, $3, $4, $5, $6, $7, $8, $9, $10
  FROM links l WHERE l.key = $1
```

Adding `l.campaign_id` to the SELECT list costs no extra round trip, and the UTM fallback is expressible in the same statement as `COALESCE(NULLIF($6, ''), l.utm_source)` per key. **The redirect path must not gain a query.** Keep the recorder fire-and-forget and inside `recordTimeout`.

## Root cause

Not a defect — the recording half of the campaigns feature. Before this, `internal/handlers/redirect.go` populated the click row from `q.Get("utm_source")` and friends, i.e. the inbound short-URL query string only, so a bare short link recorded `NULL` for every UTM key and every campaign breakdown would have been a single `(none)` bar.

## Fix

Migration `000012` adds `clicks.campaign_id` (`ON DELETE SET NULL`) and `clicks.is_bot` plus two partial indexes. Both recording changes land inside the recorder's **existing single statement**:

```sql
INSERT INTO clicks (..., campaign_id)
 SELECT l.id, $2, $3, $4, $5,
        COALESCE(NULLIF($6, ''), l.utm_source),
        ...
        l.campaign_id
   FROM links l WHERE l.key = $1
```

`campaign_id` is resolved from the link in SQL and is not a field on `Click` — a caller cannot inject one. The five UTM arguments moved from `nullStr(...)` to raw Go strings so the SQL-side `NULLIF` performs the empty-to-absent fold; `nullStr` now applies only to `user_agent`/`referer`.

## Verification

`go build ./...`, `go vet ./...` clean. `go test ./... -race -count=1` green apart from the pre-existing `internal/config` failure. `gofmt -l` reports **three** files where `main` reports four — this branch incidentally formatted `recorder_test.go` (a pure `var (...)` alignment fix, confirmed by `gofmt -d` on main).

**No performance regression on the hot path**, established by `EXPLAIN VERBOSE` on the INSERT-SELECT itself rather than only on the read query: old and new plans are byte-identical at `cost=0.14..8.17`, `width=305`. The plan already fetched the whole `links` heap tuple to get `l.id`, so projecting six more columns off it is free, and the `COALESCE(NULLIF(...))` calls constant-fold. `TestRecorder_RecordIssuesExactlyOneStatement` pins the call count with a `pgx.QueryTracer`.

Nine mutants were run across implementer and reviewer, and the results have the right shape:

| Mutant | Tests that failed |
|---|---|
| Naive all-or-nothing fallback (`CASE WHEN any inbound present`) | **only** the mixed-case test |
| No fallback (pre-#0100 `NULLIF($n,'')`) | fallback, mixed, empty-string-as-absent |
| Drop `NULLIF` | empty-stored-as-null, fallback, empty-string-as-absent |
| Reversed precedence (`COALESCE(l.utm_source, NULLIF($6,''))`) | inbound-overrides, mixed |
| `l.campaign_id` → `NULL::bigint` | records-campaign-id, survives-reassignment |
| Extra `SELECT campaign_id` before the INSERT | exactly-one-statement |
| `idx_clicks_campaign_time` dropped / on wrong column / **reversed order** | index-order assertion (after the fix — see Gotchas) |

## Gotchas

- **An index test that greps the plan for the index *name* passes with the columns reversed.** `idx_clicks_campaign_time` recreated as `(clicked_at, campaign_id)` — the version that degrades in production, since the leading column would be the range predicate and the scan cannot seek to a campaign — still produced a plan containing the name, because Postgres puts both quals in `Index Cond` either way. The fix asserts column order from `pg_indexes.indexdef` and keeps `EXPLAIN` for shape. Tightening the plan string-match instead would have been brittle.
- **`SET LOCAL enable_seqscan = off` was the right technique, wrapped around the wrong assertion.** Without it the test passes even with the index dropped entirely, because the table is too small for the planner to prefer an index on cost. Forcing the choice isolates "can this index serve this shape" from "is this table big enough today" — the defect was downstream of the `SET`, not in it.
- **`TraceQueryStart` counts pgx *calls*, not protocol round trips.** The pool runs `cache statement` exec mode, so the first `Exec` of a given SQL on a connection also fires an uncounted `TracePrepareStart` Parse/Describe. Steady state is `1, 0`; first call is `1, 1`. The assertion is still correct for the question asked, but the comment claiming "round trips, not an inference" was wrong.
- **The fallback cannot resurrect a value a user cleared.** `links.utm_*` is only ever written by `nullIfEmpty`, `addNullableString` (`*v == ""` → SQL NULL), or `addForward` (skips empty) — no path writes `''`. Verified end-to-end: setting `utm_source` then clearing it records NULL on the next click. `stats.go`'s own `COALESCE(NULLIF(col,''), '(none)')` folds it a second time regardless.
- **A doc paragraph three lines from the one that replaced it survived unedited**, still describing `nullStr` as governing UTM emptiness. Same class as #0097's phantom middleware and #0099's lockstep claim: the text reads as verified because it sits next to text that is.

## Downstream constraints

1. **[#0101](0101.md) + [#0102](0102.md) index interaction.** `idx_clicks_campaign_time` is partial on `WHERE campaign_id IS NOT NULL`. Once #0101 makes stats default to `AND is_bot = FALSE`, that predicate is **not** in the index and becomes a post-scan Filter. #0102's criterion "EXPLAIN confirms the index carries the timeseries query" will still pass but with a Filter node — #0102 must not read that as a failure, and **#0101 should decide deliberately** whether to extend the partial predicate rather than add a third index.
2. **[#0102](0102.md) must group on `clicks.campaign_id`, never a join through `links`.** The denormalization is only load-bearing if the read side honors it; the tests here guard the write side only.
3. **Campaign deletion is now O(clicks in campaign)** — `DeleteCampaign` is a hard delete, so `ON DELETE SET NULL` updates every historical click row. `idx_clicks_campaign_id` serves it, but [#0103](0103.md) should not present delete as instant on a large campaign.
4. **A concurrent campaign delete can now fail a click INSERT** — the row takes a second FK check against `campaigns`. Recording is best-effort and logs on failure, so this is acceptable, but it is a new (narrow) way to drop a click.
5. **[#0108](0108.md) inherits two issues' worth of stale `docs/database.md`** — its `clicks` section still lists ten columns and two indexes, its `links` section lacks #0099's seven columns, and there is no `campaigns` section at all.
6. **[#0108](0108.md)'s "precedence stated identically" criterion** is satisfied in substance but not in wording: `analytics.md` and `utm.md` state the same three tiers in different prose, with `utm.md` cross-linking `analytics.md` as canonical. Normalize rather than assume it is done.
