## Description

Automate the Admin ▸ Audit log view (`GET /admin/audit`): rendering, and — where
possible — that actions produce audit entries. Depends on [#0080](0080.md); part
of [#0079](0079.md).

## Important dev-mode caveat

In dev mode the audit logger is wired as **`nil`** (`serveDevMode` passes no audit
logger to the settings/users/url-filters handlers). So actions taken against the
dev build **do not write audit entries**, and the audit reader reads from the
in-memory dev store. This issue therefore focuses on the **view rendering and
read path** against whatever the dev store exposes; asserting "action X wrote an
audit row" is **not reliable in dev** and is covered by the `audit` package tests.

## Scope / scenarios to automate

- **Audit view renders** for the admin without error, showing the audit table /
  empty state as the dev store provides it.
- **Pagination / ordering (if present).** If the view paginates or sorts (newest
  first), assert that UI behavior against seeded/available rows.
- **Read-path shape.** Assert the columns (timestamp, action, actor, IP) render
  for any present rows.
- **Action → entry (only if the dev store records it).** If the dev store does
  surface entries for an action, assert one end-to-end; otherwise document that
  audit writes are disabled in dev and defer to unit tests.

## Preconditions

- Fresh-seed dev server; `AuditPage` page object.

## Acceptance criteria

- [ ] Audit view renders (table or empty state) without error.
- [ ] Column/ordering behavior asserted for present rows.
- [ ] The "audit writes are disabled in dev" limitation is documented in the spec.

## Out of scope

- Verifying that specific admin actions write audit rows (not reliable in dev;
  owned by the `audit` package tests).

## Notes

- If richer audit e2e coverage is wanted, it needs a Postgres-backed run (real
  `AuditLogger`) rather than the dev store — note as a possible future harness
  mode, out of scope for the Safari-vs-dev suite.
